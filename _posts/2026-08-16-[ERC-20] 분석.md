# ERC-20 분석, 이더리움 토큰의 표준은 어떻게 만들어졌을까?

## 1. 들어가며

이더리움 생태계를 공부하다 보면 ERC-20이라는 이름을 굉장히 자주 접하게 된다.

처음에는 ERC-20을 단순히 "이더리움에서 토큰을 만드는 규칙" 정도로 생각했는데, 조금 더 살펴보니 ERC-20의 핵심은 토큰 자체보다 **서로 다른 토큰이 동일한 방식으로 동작할 수 있도록 인터페이스를 표준화한 것**에 있었다.

이더리움에서는 누구나 스마트 컨트랙트를 배포해서 자신만의 토큰을 만들 수 있다.

문제는 토큰마다 서로 다른 방식으로 구현한다면 발생한다.

예를 들어 토큰 전송 기능을 개발자가 마음대로 만든다고 가정해보자.

```
Token A → sendToken()
Token B → transferCoin()
Token C → moveToken()

```

기능은 모두 토큰 전송이지만 함수 이름과 사용 방법이 다르다.

이렇게 되면 지갑, 거래소,

DEX 같은 서비스는 새로운 토큰이 등장할 때마다 해당 토큰의 인터페이스를 따로 분석하고 지원해야 한다.

ERC-20은 이러한 문제를 해결하기 위해 등장한 **Fungible Token의 표준 인터페이스**이다.

이번 글에서는 ERC-20이 왜 등장했는지부터 시작해서 주요 함수와 동작 방식,

approve()와 transferFrom()을 이용한 권한 위임 구조, 실제 사용 사례와 보안상 주의할 점까지 정리해보았다.

---

# 2. ERC-20이란?

ERC-20은 Ethereum에서 **Fungible Token**, 즉 대체 가능한 토큰을 구현하기 위한 표준이다.

Fungible하다는 것은 같은 종류의 토큰이라면 각각의 가치가 동일하다는 의미다.

예를 들어 내가 가지고 있는 어떤 토큰 1개와 다른 사람이 가지고 있는 같은 토큰 1개는 동일한 단위로 취급할 수 있다.

```
Token 1개 = 다른 Token 1개

```

각 토큰에 별도의 고유성을 부여하는 NFT와는 이 부분에서 차이가 있다.

ERC-20의 중요한 목적은 단순히 토큰을 발행하는 것이 아니라 **토큰들이 공통된 인터페이스를 사용하도록 만드는 것**이다.

ERC-20을 따르는 토큰이라면 기본적으로 동일한 형태의 함수들을 제공한다.

```
totalSupply()
balanceOf()
transfer()
approve()
allowance()
transferFrom()

```

덕분에 지갑이나 DEX 같은 애플리케이션은

토큰마다 완전히 다른 로직을 작성할 필요 없이 ERC-20 인터페이스를 기준으로 여러 토큰과 상호작용할 수 있다.

---

# 3. ERC-20은 왜 필요했을까?

ERC-20이 없다고 가정해보았다.

개발자 A는 다음과 같은 토큰을 만들 수 있다.

```
function sendToken(address to, uint256 amount)

```

개발자 B는 동일한 기능을 다음과 같이 구현할 수도 있다.

```
function transferCoin(address receiver, uint256 value)

```

둘 다 결국 토큰을 보내는 기능이지만 외부 애플리케이션에서 바라보면 전혀 다른 인터페이스다.

DEX가 1,000개의 토큰을 지원한다고 가정하면 각각의 토큰마다 별도의 전송 방식을 구현해야 할 수도 있다.

```
Wallet
 ├─ Token A 방식
 ├─ Token B 방식
 ├─ Token C 방식
 ├─ Token D 방식
 └─ ...

```

ERC-20을 사용하면 이 구조를 다음과 같이 바꿀 수 있다.

```
                 ERC-20 Interface
                        │
           ┌────────────┼────────────┐
           ▼            ▼            ▼
        Token A      Token B      Token C

```

Wallet이나 DEX 입장에서는 ERC-20 인터페이스를 알고 있으면 여러 ERC-20 토큰을 같은 방식으로 처리할 수 있다.

결국 ERC-20의 중요한 의미는 **상호운용성(Interoperability)**에 있다고 볼 수 있다.

---

# 4. ERC-20의 핵심 함수

ERC-20의 핵심 인터페이스를 살펴보면 다음과 같다.

```
function totalSupply() external view returns (uint256);

function balanceOf(address account)
    external view returns (uint256);

function transfer(address to, uint256 value)
    external returns (bool);

function allowance(address owner, address spender)
    external view returns (uint256);

function approve(address spender, uint256 value)
    external returns (bool);

function transferFrom(
    address from,
    address to,
    uint256 value
) external returns (bool);

```

각 함수의 역할을 하나씩 살펴보았다.

---

## 4.1 totalSupply()

```
totalSupply()

```

현재 존재하는 토큰의 전체 공급량을 반환한다.

예를 들어 총 1,000,000개의 토큰이 발행되어 있다면 전체 공급량에 해당하는 값을 확인할 수 있다.

단, Solidity에서는 소수점 연산을 직접 사용하는 방식이 아니기 때문에 실제 내부 값은 decimals를 고려해서 표현된다.

---

## 4.2 balanceOf()

```
balanceOf(address account)

```

특정 주소가 보유하고 있는 토큰의 수량을 조회한다.

개념적으로는 다음과 같은 상태를 조회한다고 생각할 수 있다.

```
mapping(address => uint256) balances;

```

예를 들어

```
Alice → 100 Token
Bob   → 50 Token

```

상태에서 Alice의 주소를 balanceOf()에 전달하면 Alice의 토큰 잔액을 확인할 수 있다.

---

## 4.3 transfer()

```
transfer(address to, uint256 value)

```

자신이 가지고 있는 토큰을 다른 주소로 전송할 때 사용하는 함수다.

예를 들어 Alice가 Bob에게 10개의 토큰을 전송한다면 개념적으로 다음과 같은 변화가 발생한다.

```
Before

Alice : 100
Bob   : 50


transfer(Bob, 10)


After

Alice : 90
Bob   : 60

```

ETH를 보내는 것과 비슷해 보이지만 실제 ERC-20 토큰은 토큰 컨트랙트 내부의 상태가 변경되는 것이다.

즉,

```
Alice 지갑 안에 Token 객체가 존재

```

하는 방식이라기보다는 토큰 컨트랙트가

```
Alice 주소 → 90
Bob 주소   → 60

```

과 같은 잔액 정보를 관리한다고 이해하는 것이 더 정확하다.

---

# 5. ERC-20에서 가장 중요한 approve와 transferFrom

ERC-20을 공부하면서 가장 중요하다고 느낀 부분은 approve()와 transferFrom()이었다.

단순한 토큰 전송이라면 transfer()만 있어도 될 것처럼 보인다.

하지만 DeFi에서는 사용자가 직접 토큰을 보내는 것뿐만 아니라

**다른 스마트 컨트랙트가 사용자의 토큰을 대신 이동해야 하는 상황**이 많이 발생한다.

대표적인 예가 DEX다.

사용자가 DEX에서 토큰을 교환하려고 한다고 가정해보자.

DEX 스마트 컨트랙트가 사용자의 토큰을 가져가야 하지만,

아무런 제한 없이 사용자의 토큰을 이동할 수 있다면 심각한 문제가 발생한다.

그래서 ERC-20에는 **Allowance**라는 개념이 존재한다.

---

# 6. approve()

```
approve(address spender, uint256 value)

```

approve()는 특정 주소가 자신의 토큰을 일정량까지 사용할 수 있도록 권한을 부여하는 함수다.

예를 들어 Alice가 DEX에 100 Token의 사용 권한을 부여한다고 가정해보자.

```
token.approve(DEX, 100);

```

그러면 개념적으로 다음과 같은 권한 관계가 만들어진다.

```
Owner
Alice
  │
  │ approve 100 Token
  ▼
Spender
DEX

```

중요한 점은 approve()를 호출했다고 해서 토큰이 바로 DEX로 이동하는 것은 아니라는 것이다.

단지 DEX가 Alice의 토큰을 최대 100개까지 사용할 수 있다. 라는 권한을 기록하는 것이다.

---

# 7. allowance()

현재 얼마나 많은 토큰 사용 권한이 남아 있는지는 allowance()로 확인할 수 있다.

```
allowance(owner, spender)

```

예를 들어

```
allowance(Alice, DEX)

```

결과가 100이라면 DEX는 Alice의 토큰을 최대 100만큼 사용할 수 있다.

이를 개념적으로 표현하면 다음과 같다.

```
allowance[Alice][DEX] = 100

```

실제 구현에서도 일반적으로 owner와 spender의 관계를 저장하는 형태의 구조를 사용한다.

---

# 8. transferFrom()

승인된 spender는 transferFrom()을 사용해 owner의 토큰을 이동할 수 있다.

```
transferFrom(
    address from,
    address to,
    uint256 value
)

```

예를 들어 DEX가 Alice의 토큰 30개를 가져간다면 다음과 같은 흐름이 된다.

```
Alice
 │
 │ approve(DEX, 100)
 ▼
Token Contract
 │
 │ allowance[Alice][DEX] = 100
 ▼
DEX
 │
 │ transferFrom(Alice, DEX, 30)
 ▼
Token Contract

```

처리가 끝나면 일반적으로 남은 allowance는 다음과 같이 감소한다.

```
100 → 70

```

이 구조는 ERC-20 기반 DeFi를 이해할 때 상당히 중요하다.

---

# 9. DEX에서 ERC-20이 사용되는 과정

사용자가 어떤 ERC-20 Token A를 Token B로 교환한다고 가정해보자.

사용자는 먼저 DEX가 Token A를 사용할 수 있도록 승인한다.

```
TokenA.approve(DEX, 100);

```

그 다음 Swap을 요청한다.

```
User
 │
 │ approve()
 ▼
Token A
 │
 │ allowance
 ▼
DEX

```

DEX는 사용자가 부여한 권한을 이용해 transferFrom()을 실행할 수 있다.

```
TokenA.transferFrom(
    user,
    dex,
    100
);

```

전체 흐름을 단순화하면 다음과 같다.

```
1. User
      │
      │ approve(DEX, 100)
      ▼
   Token Contract


2. User
      │
      │ swap()
      ▼
     DEX


3. DEX
      │
      │ transferFrom(User, DEX, 100)
      ▼
   Token Contract


4. DEX
      │
      │ Token B 지급
      ▼
     User

```

처음 DeFi를 사용할 때 Swap 전에 Approve 트랜잭션이 별도로 발생하는 이유가 바로 이 구조 때문이다.

---

# 10. Transfer와 Approval 이벤트

ERC-20에서는 함수뿐만 아니라 이벤트도 중요하다.

대표적으로 다음 두 이벤트가 있다.

```
event Transfer(
    address indexed from,
    address indexed to,
    uint256 value
);

event Approval(
    address indexed owner,
    address indexed spender,
    uint256 value
);

```

Transfer는 토큰이 이동했을 때 발생한다.

```
Alice → Bob : 10 Token

```

같은 정보를 온체인 로그로 남길 수 있다.

Approval은 allowance가 설정될 때 발생한다.

```
Alice → DEX : 100 Token 사용 승인

```

블록 탐색기나 지갑 등의 서비스에서는 이러한 이벤트 로그를 이용하여 토큰의 활동을 추적할 수 있다.

---

# 11. decimals는 무엇일까?

ERC-20을 처음 볼 때 헷갈렸던 것 중 하나가 decimals였다.

Solidity의 토큰 계산에서는 일반적인 프로그램처럼 소수점 숫자를 직접 저장해서 처리하는 방식 대신 정수 단위를 사용한다.

예를 들어 decimals가 18인 토큰에서

```
1 Token

```

은 내부적으로

```
1 × 10^18

```

단위로 표현할 수 있다.

따라서 5 Token을 전송한다면 실제 전달되는 값은 다음과 같은 형태가 된다.

```
5 × 10^18

```

OpenZeppelin의 기본 ERC-20 구현에서는 decimals()가 기본적으로 18을 반환한다.

다만 모든 ERC-20 토큰이 반드시 18 decimals를 사용하는 것은 아니다.

따라서 실제 토큰을 다룰 때는 해당 토큰의 decimals 값을 확인해야 한다.

---

# 12. 직접 ERC-20 토큰 만들어보기

OpenZeppelin Contracts를 이용하면 ERC-20을 직접 전부 구현하지 않고 검증된 구현을 상속받아 토큰을 만들 수 있다.

간단한 예시는 다음과 같다.

```
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import {ERC20} from
    "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MyToken is ERC20 {

    constructor(uint256 initialSupply)
        ERC20("MyToken", "MTK")
    {
        _mint(msg.sender, initialSupply);
    }
}

```

코드는 생각보다 간단하다.

```
ERC20("MyToken", "MTK")

```

부분에서 토큰의 이름과 심볼을 지정하고,

```
_mint(msg.sender, initialSupply);

```

를 통해 배포자에게 초기 공급량을 발행한다.

중요한 점은 ERC-20 자체가 토큰의 공급 정책까지 하나로 강제하는 표준은 아니라는 것이다.

개발자는 프로젝트 목적에 따라 minting, burning, supply cap 등의 정책을 별도로 구현할 수 있다.

OpenZeppelin 역시 기본 ERC20 구현 외에 Burnable, Capped, Pausable, Permit 등 여러 확장 기능을 제공한다.

---

# 13. 실제 사용 사례 — USDC

ERC-20이 실제로 어디에서 사용되는지 확인하기 위해 대표적인 토큰 중 하나인 USDC를 살펴볼 수 있다.

USDC는 Ethereum에서 ERC-20 Token Standard를 사용한다.

따라서 Ethereum의 USDC 역시 ERC-20 생태계의 공통 인터페이스를 기반으로 다른 지갑이나 프로토콜과 상호작용할 수 있다.

이를 통해 ERC-20의 장점을 실제로 확인할 수 있다.

예를 들어 서로 완전히 다른 프로젝트인

```
Wallet
DEX
Lending Protocol
Payment Application

```

등이 동일한 ERC-20 인터페이스를 통해 USDC 같은 토큰과 상호작용할 수 있다.

ERC-20이 단순히 "토큰 만드는 방법"이 아니라 Ethereum 생태계에서

여러 서비스가 서로 호환될 수 있도록 만드는 기반이라는 점을 확인할 수 있었다.

---

# 14. 보안 관점에서 바라본 ERC-20

ERC-20을 공부하면서 특히 눈에 들어온 부분은 approve()와 allowance 구조였다.

사용자가 다음과 같이 매우 큰 allowance를 설정했다고 생각해보자.

```
approve(spender, type(uint256).max);

```

이 경우 spender에게 사실상 매우 큰 토큰 사용 권한을 부여하게 된다.

DEX를 사용할 때 매번 approve하는 것이 번거롭기 때문에 큰 금액 또는 최대 금액을 승인하는 경우가 있는데, 승인받은 컨트랙트나 관련 시스템에 문제가 발생한다면 남아 있는 allowance가 위험 요소가 될 수 있다.

따라서 ERC-20을 사용할 때는 단순히 토큰 잔액만 보는 것이 아니라

```
내 토큰을 누가 사용할 수 있는가?

얼마까지 사용할 수 있는가?

```

도 중요하다는 것을 알 수 있다.

---

# 15. approve 변경 시 주의할 점

ERC-20 공식 명세에는 allowance 변경과 관련해서도 알아둘 만한 내용이 있다.

예를 들어 기존 allowance가 100인 상황에서 이를 바로 50으로 변경하려고 한다고 생각해보자.

```
기존 allowance = 100

approve(spender, 50)

```

사용자가 보낸 allowance 변경 트랜잭션이 처리되기 전에 spender가

기존 allowance를 사용하는 식의 문제가 발생할 가능성이 있다.

이 때문에 ERC-20 명세에서는 UI가 allowance 값을 변경할 때

먼저 0으로 설정한 뒤 새로운 값을 설정하는 방식을 고려하도록 설명한다.

여기서 중요한 것은 ERC-20 자체가 이러한 사용상의 모든 위험을 자동으로 해결해주는 것은 아니라는 점이다.

표준을 사용하는 애플리케이션과 개발자 역시 allowance 관리 방식에 주의해야 한다.

---

# 16. ERC-20의 한계

ERC-20은 Ethereum 생태계에서 매우 중요한 표준이지만 모든 문제를 해결하는 것은 아니다.

대표적으로 앞에서 살펴본 승인 과정이 있다.

DEX에서 토큰을 사용하려면 일반적으로

```
1. approve()
2. swap()

```

처럼 두 단계의 작업이 필요할 수 있다.

사용자 입장에서는 실제로 하고 싶은 것은 Swap 한 번인데 이를 위해 먼저 별도의 approval transaction을 보내야 한다.

```
User
 │
 ├─ Transaction 1 → approve()
 │
 └─ Transaction 2 → swap()

```

이 과정은 추가적인 트랜잭션과 사용자 경험 문제로 이어질 수 있다.

이 문제를 개선하기 위해 등장한 표준 중 하나가 **EIP-2612 Permit**이다.

EIP-2612에서는 사용자의 서명을 이용해 allowance를 설정할 수 있도록 permit()을 추가한다.

따라서 ERC-20의 approve 구조를 이해하면 EIP-2612가 왜 등장했는지도 자연스럽게 연결해서 이해할 수 있다.

---

# 17. ERC-20을 공부하면서 이해한 점

처음에는 ERC-20을 단순히 코인을 만드는 스마트 컨트랙트 규칙이라고 생각했다.

하지만 직접 구조를 살펴보면서 가장 중요하다고 느낀 부분은 토큰 자체보다는 **인터페이스의 표준화**였다.

Ethereum에서는 누구나 스마트 컨트랙트를 만들 수 있기 때문에

개발자마다 토큰을 완전히 다른 방식으로 구현할 수도 있다.

ERC-20은

```
transfer
approve
transferFrom
balanceOf
allowance

```

같은 공통 인터페이스를 정의함으로써 Wallet, DEX, DeFi Protocol 등이

수많은 토큰과 동일한 방식으로 상호작용할 수 있도록 만들었다.

특히 approve → allowance → transferFrom 구조를 이해하면서

DEX에서 토큰을 Swap하기 전에 왜 Approve 과정이 필요한지도 이해할 수 있었다.

보안 측면에서도 allowance는 중요해 보였다.

사용자가 토큰을 가지고 있다는 사실뿐만 아니라

**어떤 주소나 컨트랙트에 얼마의 사용 권한을 부여했는지** 역시 자산의 안전성과 연결되기 때문이다.

그리고 ERC-20의 approval 방식에서 발생하는

UX 문제를 개선하기 위해 EIP-2612와 같은 새로운 표준이 등장했다는 점도 흥미로웠다.

EIP를 하나씩 따로 외우기보다는 기존 표준에서 어떤 문제가 있었고

다음 EIP가 그 문제를 어떤 방식으로 개선했는지 연결해서 공부하는 것이 더 이해하기 쉬울 것 같다.

---

# 18. 정리

ERC-20을 정리하면 다음과 같다.

항목                                                        내용

| 목적             | Fungible Token 인터페이스 표준화 |
| -------------- | ------------------------ |
| totalSupply()  | 전체 토큰 공급량 조회             |
| balanceOf()    | 주소의 토큰 잔액 조회             |
| transfer()     | 자신의 토큰 전송                |
| approve()      | spender에게 토큰 사용 권한 부여    |
| allowance()    | 남아 있는 사용 권한 조회           |
| transferFrom() | 승인받은 토큰을 대신 전송           |
| Transfer       | 토큰 전송 이벤트                |
| Approval       | 토큰 사용 승인 이벤트             |

결국 ERC-20의 핵심은 **Ethereum 위에서 발행되는**

**Fungible Token이 공통된 방식으로 동작할 수 있도록 약속을 만든 것**이라고 정리할 수 있다.

ERC-20 덕분에 개발자는 토큰마다 별도의 인터페이스를 만들 필요가 없고,

Wallet이나 DEX 같은 서비스 역시 공통된 인터페이스를 기반으로 다양한 토큰을 지원할 수 있다.

그리고 ERC-20의 구조를 이해하고 나니 다음으로 살펴볼 EIP-2612의 등장 배경도 자연스럽게 이해할 수 있었다.

다음 글에서는 ERC-20과 다른 방식으로 고유한 자산을 표현하는 **ERC-721 NFT 표준**을 분석해보려고 한다.
