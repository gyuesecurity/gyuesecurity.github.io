# ERC-4337 분석, Account Abstraction은 Ethereum 지갑을 어떻게 바꿀까?

## 1. 들어가며

지금까지 ERC-20, ERC-721, EIP-2612, EIP-1559를 공부하면서

Ethereum에서 Token과 Transaction이 어떻게 동작하는지 살펴보았다.

이번에는 조금 더 근본적인 **Account**에 대해 공부해보았다.

Ethereum을 처음 사용할 때 일반적으로 MetaMask 같은 Wallet을 생성하고 Seed Phrase와 Private Key를 관리한다.

기존 Ethereum에서는 사용자의 Private Key를 기반으로 Transaction에 서명한다.

```
Private Key
     │
     ▼
    EOA
     │
     │ Transaction
     ▼
Ethereum

```

여기서 사용자가 일반적으로 사용하는 계정을 **EOA(Externally Owned Account)**라고 한다.

EOA는 Private Key를 가지고 있고, Transaction을 직접 시작할 수 있다.

하지만 이 구조에는 여러 불편한 점이 있다.

Private Key를 잃어버리면 계정을 복구하기 어렵고, Transaction을 보내기 위해서는 ETH를 가지고 있어야 하며, 여러 Transaction을 하나로 묶거나 복잡한 인증 방식을 적용하기도 어렵다.

일반적인 Web2 서비스에서는

```
비밀번호 분실
    ↓
이메일 인증
    ↓
계정 복구

```

같은 기능이 자연스럽게 제공된다.

하지만 일반적인 EOA는 기본적으로 이러한 기능을 제공하지 않는다.

그렇다면 이런 생각을 해볼 수 있다.

계정 자체를 Smart Contract로 만들면 어떨까?

Smart Contract라면 개발자가 원하는 인증과 실행 로직을 직접 구현할 수 있다.

```
단일 Private Key

        ↓

Smart Contract 기반 Account

        ↓

다양한 인증 / 복구 / 권한 관리

```

이러한 방향을 **Account Abstraction**이라고 한다.

그리고 Ethereum의 Consensus Layer를 직접 변경하지 않고

Account Abstraction을 구현하기 위한 대표적인 표준이 **ERC-4337**이다.

이번 글에서는 EOA의 한계부터 시작해서 Smart Account, UserOperation,

Bundler, EntryPoint, Paymaster, Factory가 어떤 역할을 하는지 살펴보고

ERC-4337이 기존 Ethereum Wallet 사용 방식을 어떻게 확장하는지 정리해보았다.

---

# 2. Ethereum의 두 가지 Account

Ethereum에는 크게 두 종류의 Account가 있다.

```
Ethereum Account

├── EOA
│
└── Contract Account

```

## EOA

Externally Owned Account의 약자로 Private Key에 의해 제어되는 계정이다.

일반적인 사용자 Wallet이 여기에 해당한다.

```
Private Key
     │
     ▼
    EOA

```

EOA는 Transaction을 직접 생성하고 서명할 수 있다.

## Contract Account

Smart Contract가 배포된 주소다.

```
Contract Address
       │
       ▼
Smart Contract Code

```

Contract Account는 코드와 상태를 가지고 있기 때문에 개발자가 원하는 로직을 구현할 수 있다.

하지만 일반적인 Contract Account는 EOA처럼 스스로 Transaction을 시작하는 구조가 아니다.

다른 Transaction에 의해 호출되어 실행된다.

---

# 3. EOA 방식의 한계

EOA의 가장 큰 특징은 계정의 제어 권한이 Private Key에 강하게 연결되어 있다는 것이다.

```
Private Key
     │
     ▼
Account Control

```

이 구조는 단순하지만 여러 한계가 존재한다.

대표적으로 다음과 같다.

```
Private Key 분실 문제

Gas를 위한 ETH 필요

복잡한 인증 방식 적용 어려움

Transaction Batch 처리 제한

사용자별 권한 관리 어려움

Account Recovery 기능 구현 어려움

```

예를 들어 Private Key를 잃어버렸다고 생각해보자.

Web2 서비스라면 이메일이나 휴대전화 인증을 통해 계정을 복구할 수 있다.

하지만 일반적인 EOA에서는

```
Private Key 분실
       ↓
계정 접근 불가능

```

문제로 이어질 수 있다.

---

# 4. Account Abstraction이란?

Account Abstraction의 핵심 아이디어는 **계정의 인증과 실행 방식을 Smart Contract Logic으로 확장하는 것**이다.

기존 EOA에서는 인증 방식이 기본적으로 Private Key Signature에 의해 결정된다.

```
EOA

Private Key
     │
     ▼
ECDSA Signature
     │
     ▼
Transaction

```

Account Abstraction에서는 Account 자체가 Smart Contract이므로 인증 방법을 코드로 정의할 수 있다.

```
Smart Account
      │
      ├── Signature 검증
      ├── Multisig
      ├── Session Key
      ├── Recovery Logic
      └── Custom Authorization

```

즉

```
Account = 단순한 Key Pair

```

에서

```
Account = Programmable Smart Contract

```

로 확장하는 개념이라고 이해할 수 있다.

---

# 5. ERC-4337이란?

Account Abstraction 자체에 대한 아이디어는 ERC-4337 이전부터 존재했다.

문제는 Ethereum Protocol 자체를 변경하는 방식은 적용하기 어렵다는 점이었다.

ERC-4337은 다른 접근 방식을 사용한다.

Ethereum Consensus Layer를 직접 수정하지 않고

**Smart Contract와 별도의 UserOperation 처리 구조를 이용하여 Account Abstraction을 구현한다.**

핵심 구성 요소는 다음과 같다.

```
Smart Account

UserOperation

Bundler

EntryPoint

Paymaster

Factory

```

처음에는 용어가 많아서 복잡해 보였지만 각각의 역할을 분리해서 보면 구조를 이해하기 쉬웠다.

---

# 6. 전체 구조부터 살펴보기

ERC-4337의 전체적인 흐름은 다음과 같다.

```
User
 │
 │ UserOperation
 ▼
Bundler
 │
 │ 여러 UserOperation을 묶음
 ▼
EntryPoint
 │
 │ 검증
 ▼
Smart Account
 │
 │ 실행
 ▼
Target Contract

```

Paymaster를 사용하는 경우에는 여기에 Gas Sponsor가 추가된다.

```
User
 │
 │ UserOperation
 ▼
Bundler
 │
 ▼
EntryPoint
 │
 ├──── Paymaster
 │       │
 │       └─ Gas 지원
 │
 ▼
Smart Account
 │
 ▼
DApp

```

각 요소를 하나씩 살펴보았다.

---

# 7. Smart Account

ERC-4337에서 사용자의 Account는 Smart Contract로 구현할 수 있다.

이를 흔히

```
Smart Account

Smart Contract Wallet

Smart Contract Account

```

등으로 부른다.

Smart Contract이기 때문에 Account 내부에 다양한 로직을 구현할 수 있다.

예를 들어

```
Smart Account

├── Signature 검증
├── Transaction 실행
├── Multisig
├── Recovery
├── Spending Limit
└── Session Key

```

같은 기능을 추가할 수 있다.

기존 EOA에서는 Protocol이 정한 인증 방식을 따라야 했다면

Smart Account에서는 Contract Logic을 이용하여 더 다양한 인증 방식을 구현할 수 있다.

---

# 8. Transaction 대신 UserOperation

ERC-4337에서는 사용자가 일반 Ethereum Transaction을 바로 만드는 대신 **UserOperation**이라는 객체를 생성한다.

중요한 점은 UserOperation을 일반적인 Ethereum Transaction과 완전히 같은 것으로 보면 안 된다는 것이다.

UserOperation은 사용자가

"내 Smart Account를 이용해서 이런 작업을 실행하고 싶다." 라는 요청을 표현하는 객체라고 볼 수 있다.

개념적으로 다음과 같은 정보를 가진다.

```
UserOperation

sender

nonce

callData

gas 관련 정보

paymaster 관련 정보

signature

```

최근 명세에서는 Factory와 Paymaster 관련 값들이 보다 세분화되어 있지만 기본적인 개념은 동일하다.

---

# 9. UserOperation의 주요 정보

각 필드의 역할을 간단하게 보면 다음과 같다.

필드                                                                               역할

| sender               | Smart Account 주소      |
| -------------------- | --------------------- |
| nonce                | Replay 방지             |
| callData             | Account가 실행할 작업       |
| callGasLimit         | 실행에 사용할 Gas           |
| verificationGasLimit | 검증에 사용할 Gas           |
| preVerificationGas   | Bundler 관련 사전 처리 Gas  |
| maxFeePerGas         | 최대 Gas Fee            |
| maxPriorityFeePerGas | 최대 Priority Fee       |
| paymaster            | Gas를 대신 지불할 Paymaster |
| signature            | Account 인증 데이터        |

여기서 이전에 공부했던 내용들이 다시 등장한다.

EIP-2612에서 살펴봤던

```
nonce
signature

```

가 있고,

EIP-1559에서 살펴봤던

```
maxFeePerGas
maxPriorityFeePerGas

```

도 등장한다.

따라서 앞의 EIP들을 먼저 공부하고 ERC-4337을 보니 구조를 이해하기가 조금 더 쉬웠다.

---

# 10. UserOperation은 어디로 갈까?

일반 Ethereum Transaction은 Transaction Mempool을 통해 전달된다.

ERC-4337의 UserOperation은 별도의 **UserOperation Mempool**을 사용할 수 있다.

```
일반 Transaction

User
 │
 ▼
Transaction Mempool
 │
 ▼
Block


ERC-4337

User
 │
 ▼
UserOperation Mempool
 │
 ▼
Bundler
 │
 ▼
Ethereum Transaction
 │
 ▼
Block

```

여기서 UserOperation을 실제 Ethereum Transaction으로 연결해주는 역할을 하는 것이 **Bundler**다.

---

# 11. Bundler

Bundler는 여러 UserOperation을 수집하고 검증하여 하나의 Ethereum Transaction으로 묶어 제출하는 역할을 한다.

```
User A
 │
 └─ UserOperation A
               │
User B         │
 │             │
 └─ UserOperation B
               │
User C         │
 │             │
 └─ UserOperation C
               │
               ▼
             Bundler
               │
               ▼
          handleOps(...)
               │
               ▼
            EntryPoint

```

Bundler는 UserOperation을 무조건 받아서 Blockchain에 넣는 것이 아니다.

먼저 UserOperation이 정상적으로 실행될 수 있는지 Simulation과 Validation을 수행한다.

잘못된 UserOperation을 포함했다가 Gas 비용을 부담하고 보상을 받지 못하면 Bundler가 손해를 볼 수 있기 때문이다.

---

# 12. EntryPoint

ERC-4337에서 가장 중요한 Smart Contract 중 하나가 **EntryPoint**다.

EntryPoint는 Smart Account, Bundler, Paymaster 등을 연결하는 중심 역할을 한다.

개념적으로

```
Bundler
   │
   │ handleOps()
   ▼
EntryPoint
   │
   ├── Account Validation
   │
   ├── Paymaster Validation
   │
   ├── Gas 처리
   │
   └── UserOperation 실행

```

구조를 가진다.

Bundler는 여러 UserOperation을 모은 뒤 EntryPoint의

```
handleOps(...)

```

를 호출한다.

EntryPoint는 각 UserOperation을 검증하고 정상적인 요청을 실행한다.

---

# 13. handleOps()

EntryPoint의 핵심 함수가 handleOps()다.

개념적인 인터페이스는 다음과 같다.

```
function handleOps(
    PackedUserOperation[] calldata ops,
    address payable beneficiary
)
external;

```

Bundler가 여러 UserOperation을 ops에 넣어 전달한다.

EntryPoint는 각각의 Operation을 처리한다.

```
handleOps()

 │
 ├── UserOp #1 검증
 │
 ├── UserOp #2 검증
 │
 ├── UserOp #3 검증
 │
 ▼
실행

```

그리고 Gas 비용 등을 처리한 뒤 Bundler가 지정한 beneficiary에게 관련 비용을 지급한다.

---

# 14. Smart Account는 어떻게 검증될까?

Smart Account는 자신의 UserOperation이 정상적인지 검증해야 한다.

대표적으로

```
validateUserOp(...)

```

이라는 함수를 구현한다.

개념적으로는 다음과 같다.

```
EntryPoint
    │
    │ validateUserOp()
    ▼
Smart Account
    │
    ├── Signature 확인
    ├── 권한 확인
    └── 기타 Account 정책 확인

```

여기서 중요한 차이가 나타난다.

EOA에서는 Protocol 수준에서 Signature Validation 방식이 정해져 있다.

Smart Account에서는 Contract가 자신만의 Validation Logic을 구현할 수 있다.

---

# 15. Signature 형식도 Account가 결정할 수 있다

ERC-4337의 흥미로운 부분 중 하나다.

UserOperation에는

```
signature

```

필드가 존재하지만 ERC-4337 자체가 이 Signature의 내부 형식을 하나로 고정하지 않는다.

Smart Account 구현이 자신의 인증 방식을 결정할 수 있다.

따라서 Account에 따라

```
ECDSA Signature

Multisig

다른 Signature Scheme

Custom Authorization

```

등의 구조를 설계할 수 있다.

이 부분이 Account Abstraction의 핵심 중 하나라고 생각한다.

---

# 16. EntryPoint 전체 처리 과정

전체 과정을 단순화하면 다음과 같다.

```
1. User

UserOperation 생성
        │
        ▼

2. Bundler

UserOperation 수집
Simulation / Validation
        │
        ▼

3. EntryPoint

handleOps()
        │
        ▼

4. Smart Account

validateUserOp()
        │
        ▼

5. Validation 성공

Account 실행
        │
        ▼

6. Target Contract

Swap / Transfer / Mint 등

```

즉 사용자가 직접 Ethereum Transaction을 생성해 Blockchain에 보내는 기존 방식과 상당히 다르다.

---

# 17. Paymaster

ERC-4337에서 사용자 경험을 크게 개선할 수 있는 기능 중 하나가 **Paymaster**다.

기존 Ethereum에서는 Transaction을 실행하려면 사용자가 Gas Fee를 지불하기 위한 ETH를 가지고 있어야 한다.

예를 들어 USDC만 가지고 있는 신규 사용자가 있다고 생각해보자.

```
User

USDC : 100
ETH  : 0

```

이 사용자가 Smart Contract를 실행하려고 하면 Gas를 지불할 ETH가 없다는 문제가 발생한다.

Paymaster를 이용하면 다른 주체가 사용자의 Gas를 대신 지불하는 구조를 만들 수 있다.

```
User
 │
 │ UserOperation
 ▼
EntryPoint
 │
 ├── Smart Account
 │
 └── Paymaster
       │
       └─ Gas Sponsor

```

---

# 18. Gas Sponsorship

예를 들어 어떤 Web3 게임이 신규 사용자에게 처음 10회의 Transaction Gas를 무료로 제공한다고 생각해보자.

```
New User
   │
   │ Game Action
   ▼
Smart Account
   │
   ▼
Paymaster
   │
   │ Gas 지원
   ▼
Ethereum

```

이런 구조를 만들면 사용자가 처음부터 ETH를 구매해서 Wallet에 넣지 않아도 서비스를 이용할 수 있는 UX를 설계할 수 있다.

Web2 사용자 입장에서는 Blockchain의 Gas 개념을 몰라도 서비스를 사용할 수 있게 만들 가능성이 생긴다.

---

# 19. ERC-20으로 Gas를 낼 수도 있을까?

Paymaster를 응용하면 사용자가 ETH 대신 ERC-20 Token을 이용하는 형태의 Gas 결제 구조도 설계할 수 있다.

개념적으로

```
User

USDC : 있음
ETH  : 없음

      │
      ▼

Paymaster

      │
      ├── User에게 Token 기반 비용 처리
      │
      └── Ethereum Gas는 ETH로 지불

```

와 같은 형태다.

중요한 것은 Ethereum Protocol 자체가 Gas를 USDC로 받는다는 의미가 아니라는 점이다.

Ethereum의 실제 Gas 비용은 여전히 native currency로 처리되고,

Paymaster가 사용자와 별도의 정산 로직을 구현하는 것이다.

---

# 20. Paymaster도 아무 요청이나 대신 지불할까?

그렇지 않다.

Paymaster도 Smart Contract이므로 자신만의 정책을 구현할 수 있다.

예를 들어

```
우리 서비스의 사용자만 지원

하루 5번까지만 지원

특정 Contract 호출만 지원

특정 NFT 보유자만 지원

```

같은 정책을 만들 수 있다.

개념적으로

```
UserOperation
      │
      ▼
Paymaster
      │
      ├── 지원 조건 만족?
      │
      ├── 충분한 Deposit?
      │
      └── 정책 검증
             │
             ▼
           승인

```

과 같은 구조다.

---

# 21. Factory

ERC-4337에서 또 하나 중요한 구성 요소가 **Factory**다.

Smart Account는 Smart Contract이므로 결국 Blockchain에 배포되어야 한다.

사용자가 처음 Account를 만들 때 Factory Contract를 이용하여 Smart Account를 생성할 수 있다.

```
User
 │
 ▼
Factory
 │
 │ deploy
 ▼
Smart Account

```

ERC-4337에서는 아직 배포되지 않은 Account에 대한

Operation도 처리할 수 있도록 Account 생성 정보를 UserOperation 흐름에 포함할 수 있다.

이를 통해 Account 생성과 첫 번째 작업을 하나의 사용자 흐름으로 연결할 수 있다.

---

# 22. Counterfactual Account

Smart Account를 공부하다 보면 **Counterfactual Address**라는 개념도 접하게 된다.

Smart Contract는 아직 배포되지 않았더라도 CREATE2와 같은 방식을 이용하면 배포될 주소를 미리 계산할 수 있다.

따라서

```
아직 Account Contract 없음

        ↓

Account Address는 미리 계산 가능

```

한 구조를 만들 수 있다.

예를 들어 사용자에게

```
0xABC...

```

라는 Smart Account 주소가 먼저 생성되어 보일 수 있지만 실제 Contract는 아직 배포되지 않은 상태일 수 있다.

사용자가 처음 Operation을 실행할 때 Factory가 실제 Account Contract를 배포하는 방식으로 사용할 수 있다.

---

# 23. Transaction Batching

Smart Account를 사용하면 여러 작업을 하나의 사용자 흐름으로 묶는 것도 가능하다.

예를 들어 DEX에서 Token을 Swap한다고 생각해보자.

기존에는 상황에 따라

```
Transaction 1
approve()

Transaction 2
swap()

```

같이 여러 단계가 필요할 수 있다.

Smart Account에서는 Account가 여러 Call을 실행하는 기능을 구현하여

```
UserOperation

     │
     ├── approve()
     │
     └── swap()

```

같은 Batch Execution을 제공할 수 있다.

사용자 입장에서는 여러 번 Transaction을 승인하는 대신 하나의 작업처럼 처리할 수 있다.

---

# 24. Social Recovery

Smart Account의 장점 중 하나는 Recovery Logic을 프로그래밍할 수 있다는 점이다.

기존 EOA는

```
Private Key 분실
       ↓
계정 접근 문제

```

로 이어진다.

Smart Account에서는 예를 들어 Guardian 구조를 구현할 수 있다.

```
Smart Account

      │
      ├── Owner Key
      │
      └── Guardians
             │
             ├── Guardian A
             ├── Guardian B
             └── Guardian C

```

Owner Key를 분실한 경우

```
Guardian A
Guardian B
Guardian C

3명 중 2명 승인

      ↓

새로운 Owner Key 등록

```

같은 Recovery Logic을 설계할 수 있다.

ERC-4337이 특정 Social Recovery 방식을 강제하는 것은 아니지만

Account가 Smart Contract가 됨으로써 이러한 기능을 구현할 기반이 생긴다.

---

# 25. Multisig

Smart Account에서는 여러 Signature를 요구하도록 만들 수도 있다.

예를 들어 회사 자금을 관리하는 Wallet이라고 생각해보자.

```
CEO
CTO
CFO

3명 중 2명 서명 필요

```

Account Validation Logic을

```
Signature >= 2

       ↓

UserOperation Valid

```

와 같이 구현할 수 있다.

EOA 하나의 Private Key에 모든 권한을 집중시키는 대신 여러 Key를 이용해 Account를 관리할 수 있다.

---

# 26. Session Key

게임이나 반복적인 DApp 사용에서는 사용자가 모든 행동마다 Wallet을 열고 Signature를 승인하는 것이 불편할 수 있다.

Smart Account에서는 일정한 조건에서만 사용할 수 있는 Session Key를 구현할 수도 있다.

예를 들어

```
Session Key

Valid Time
09:00 ~ 10:00

Allowed Contract
Game Contract

Maximum Value
0.01 ETH

```

같은 제한을 둘 수 있다.

즉 Main Key의 전체 권한을 넘기는 대신

```
제한된 기간

제한된 Contract

제한된 금액

```

에 대해서만 사용할 수 있는 Key를 만드는 방식이다.

---

# 27. Spending Limit

Smart Account 내부에서 지출 제한도 구현할 수 있다.

예를 들어

```
하루 최대 사용 금액

1 ETH

```

라는 정책을 만들 수 있다.

```
Transaction 요청
      │
      ▼
Smart Account
      │
      ├── 오늘 사용 금액 확인
      │
      ├── Limit 확인
      │
      ▼
실행 / 거부

```

EOA 자체에서는 이런 정책을 Protocol 수준에서 제공하지 않지만 Smart Account에서는 Account Logic으로 구현할 수 있다.

---

# 28. 기존 EOA와 Smart Account 비교

전체적인 차이를 정리하면 다음과 같다.

구분                                                  EOA                                                    ERC-4337 Smart Account

| Account 제어      | Private Key  | Smart Contract Logic    |
| --------------- | ------------ | ----------------------- |
| 인증              | 기본 Signature | Programmable Validation |
| Recovery        | 기본 제공 없음     | 구현 가능                   |
| Multisig        | EOA 자체로는 불가  | 구현 가능                   |
| Batch           | 제한적          | 구현 가능                   |
| Gas Sponsorship | 기본 구조 없음     | Paymaster               |
| Session Key     | 기본 제공 없음     | 구현 가능                   |
| Spending Limit  | 기본 제공 없음     | 구현 가능                   |
| Gas Token UX    | ETH 필요       | Paymaster 구조 활용 가능      |

결국 Smart Account의 핵심은

```
Wallet 기능이 Protocol에 고정

        ↓

Wallet 기능을 Programmable하게

```

만드는 데 있다고 생각한다.

---

# 29. EIP-2612와 ERC-4337의 차이

앞에서 공부한 EIP-2612와 비슷하게 느껴질 수 있다.

EIP-2612는 ERC-20 Token의

```
approve()

```

문제를 Signature 기반으로 개선한다.

```
ERC-20

approve Transaction

       ↓

EIP-2612

Permit Signature

```

반면 ERC-4337은 훨씬 더 넓은 범위를 다룬다.

```
ERC-4337

Account 자체의

Authentication

Execution

Gas Payment

Recovery

Batching

등을 Programmable하게

```

만드는 구조다.

즉 EIP-2612는 Token Approval의 개선이고 ERC-4337은

**Account Layer의 사용자 경험과 기능을 확장하는 접근**이라고 볼 수 있다.

---

# 30. EIP-1559와 ERC-4337의 연결

UserOperation을 보면

```
maxFeePerGas

maxPriorityFeePerGas

```

가 존재한다.

이 값들은 이전 글에서 공부했던 EIP-1559와 연결된다.

즉 Account Abstraction을 사용한다고 해서 Ethereum의 Gas 경제가 완전히 사라지는 것이 아니다.

```
ERC-4337

UserOperation
      │
      ├── maxFeePerGas
      └── maxPriorityFeePerGas

```

등을 통해 Gas 비용을 고려한다.

Paymaster가 있다면 **누가 비용을 부담하는지**를 바꿀 수 있지만 Blockchain에서 연산 비용 자체가 없어지는 것은 아니다.

---

# 31. 보안 관점 — Smart Account의 공격 표면

Account가 Programmable해진다는 것은 장점이지만 동시에 보안 관점에서는 공격 표면이 넓어질 수도 있다.

EOA의 인증 구조는 비교적 단순하다.

```
Private Key
     ↓
Signature

```

Smart Account에서는

```
Smart Account

├── validateUserOp()
├── execute()
├── Recovery
├── Module
├── Session Key
├── Upgrade
└── Custom Authorization

```

처럼 다양한 기능이 추가될 수 있다.

기능이 많아질수록 구현 실수나 잘못된 권한 검증이 발생할 가능성도 커진다.

따라서 Account Abstraction을 보안 관점에서 볼 때

```
Signature Validation

Authorization

Replay Protection

Module Permission

Upgrade 권한

Recovery 권한

```

등을 함께 살펴볼 필요가 있다.

---

# 32. 보안 관점 — Replay Attack

UserOperation에도 nonce가 존재한다.

이유는 EIP-2612에서 공부했던 것과 비슷하다.

동일한 Operation이 반복 실행되는 것을 방지해야 한다.

```
UserOperation

Transfer 1 ETH

       │
       ├── 실행
       ├── 다시 실행?
       └── 다시 실행?

```

이런 문제가 발생하면 안 된다.

따라서 nonce를 이용하여 Operation의 재사용을 방지한다.

또한 ERC-4337 공식 명세에서는 UserOperation Signature가 **chainId와 EntryPoint 주소에 의존해야 한다.**

이를 통해 다른 Chain이나 다른 EntryPoint에서 동일한 서명이 재사용되는 Cross-chain/Cross-EntryPoint Replay를 방지한다.

---

# 33. 보안 관점 — validateUserOp()

Smart Account에서 특히 중요한 함수 중 하나가

```
validateUserOp()

```

이다.

이 함수에서 잘못된 인증 로직을 구현하면 Account의 자산이 위험해질 수 있다.

예를 들어 Signature 검증이 제대로 이루어지지 않는다면

```
Attacker
   │
   │ Fake UserOperation
   ▼
Smart Account
   │
   │ 잘못된 Validation
   ▼
Unauthorized Execution

```

이 발생할 수 있다.

따라서 Account 구현에서는 최소한

```
누가 Operation을 만들었는가?

Signature가 올바른가?

Nonce가 올바른가?

Operation의 유효 범위는 맞는가?

EntryPoint를 신뢰할 수 있는가?

```

등을 확인해야 한다.

공식 ERC-4337 명세에서도 Smart Account는 호출자가 신뢰하는 EntryPoint인지 확인해야 한다.

---

# 34. 보안 관점 — Paymaster DoS

Paymaster도 공격 대상이 될 수 있다.

Paymaster가 사용자의 Gas를 대신 지불하기 때문이다.

공격자가 대량의 UserOperation을 만들어 Paymaster의 자금을 소비하도록 유도한다면 문제가 될 수 있다.

```
Attacker

UserOp
UserOp
UserOp
UserOp
UserOp
   │
   ▼
Paymaster
   │
   ▼
Gas Deposit 고갈

```

따라서 Paymaster에서는

```
누구에게 Gas를 지원할 것인가?

어떤 Contract 호출을 허용할 것인가?

얼마까지 지원할 것인가?

얼마나 자주 사용할 수 있는가?

```

같은 정책이 중요하다.

ERC-4337에서도 악의적인 Paymaster가 Bundler를 대상으로

DoS를 일으킬 가능성을 고려해 Stake와 Reputation 관련 구조를 정의한다.

---

# 35. 보안 관점 — Bundler

Bundler도 잘못된 UserOperation을 그대로 Blockchain에 제출하면 Gas 비용을 잃을 수 있다.

그래서 Bundler는 UserOperation을 받자마자 바로 제출하지 않는다.

먼저 Simulation을 수행한다.

```
UserOperation
      │
      ▼
Bundler
      │
      ├── Validation
      ├── Simulation
      ├── Gas 확인
      └── Paymaster 확인
             │
             ▼
           Bundle

```

잘못된 UserOperation은 Mempool에서 거부할 수 있다.

이 구조를 보면서 ERC-4337은 단순히 Smart Contract Wallet 하나를 만드는 표준이 아니라

**Account, Bundler, EntryPoint, Paymaster가 함께 동작하는 별도의 실행 생태계**라는 것을 알 수 있었다.

---

# 36. Account Abstraction이라고 Private Key가 사라지는 것은 아니다

처음 Account Abstraction을 접했을 때는 "이제 Private Key가 필요 없는 건가?" 라고 생각했다.

하지만 꼭 그런 것은 아니다.

Smart Account의 인증 방식은 Programmable하기 때문에 여전히 ECDSA Private Key를 사용할 수도 있다.

```
Smart Account

Authentication
     │
     ├── ECDSA Key
     ├── Multisig
     ├── Passkey
     └── 기타 인증 방식

```

핵심은 Private Key를 반드시 없애는 것이 아니라

**Account의 인증 정책을 하나의 고정된 방식에서 벗어나 프로그래밍 가능하게 만드는 것**이다.

---

# 37. ERC-4337의 장점

지금까지 내용을 바탕으로 장점을 정리하면 다음과 같다.

### 1. Gas Sponsorship

```
User
 ↓
Paymaster
 ↓
Gas 지원

```

DApp이 사용자의 Gas를 대신 지불할 수 있다.

### 2. Flexible Gas Payment

Paymaster를 이용하여 ERC-20 Token 기반의 비용 정산 구조를 만들 수 있다.

### 3. Account Recovery

Guardian 등을 이용한 Recovery 기능을 구현할 수 있다.

### 4. Multisig

여러 Signature를 요구할 수 있다.

### 5. Batch Transaction

여러 Contract Call을 하나의 사용자 작업으로 묶을 수 있다.

### 6. Session Key

제한된 권한을 가진 임시 Key를 구현할 수 있다.

### 7. Custom Authentication

Account가 자신만의 Signature Verification Logic을 가질 수 있다.

---

# 38. ERC-4337의 단점과 고려할 점

Account Abstraction이 모든 문제를 자동으로 해결하는 것은 아니다.

구조가 복잡해지는 만큼 추가적인 고려사항이 발생한다.

```
Smart Account 구현 보안

Bundler Infrastructure

Paymaster 운영

Gas 비용

EntryPoint 의존성

Custom Validation Logic 보안

```

특히 Wallet이 단순한 Key Pair가 아니라 Smart Contract가 되기 때문에

Contract 자체에 취약점이 있다면 Account의 자산 전체에 영향을 줄 수 있다.

따라서 Smart Account 구현의 보안 검증이 중요하다.

---

# 39. ERC-4337을 공부하면서 이해한 점

처음에는 Account Abstraction이라는 이름 자체가 어려워서 굉장히 복잡한 Ethereum 내부 기술이라고 생각했다.

하지만 기본적인 문제부터 생각해보면 이해하기 쉬웠다.

기존 EOA는

```
Private Key

     ↓

Account

```

라는 구조가 강하게 고정되어 있다.

ERC-4337은 이를

```
Smart Contract

     ↓

Account Logic

```

으로 확장한다.

그 결과 Account에

```
Recovery

Multisig

Session Key

Batch Transaction

Gas Sponsorship

Custom Signature

```

같은 기능을 추가할 수 있게 된다.

특히 흥미로웠던 점은 Ethereum Consensus Layer를 직접 변경하지 않고 이를 구현했다는 것이다.

```
UserOperation

      ↓

Bundler

      ↓

EntryPoint

      ↓

Smart Account

```

라는 별도의 구조를 만들어 기존 Ethereum 위에서 Account Abstraction을 구현한다.

또 앞에서 공부했던 EIP들이 여기서 다시 연결되는 점도 흥미로웠다.

EIP-2612에서 공부한

```
Signature
Nonce
Replay Protection

```

과

EIP-1559에서 공부한

```
Max Fee
Priority Fee
Gas

```

개념이 ERC-4337의 UserOperation에서도 다시 등장한다.

따라서 각각의 EIP가 완전히 독립적인 기술이라기보다

Ethereum의 여러 문제를 해결하면서 서로 연결되어 있다는 것을 알 수 있었다.

---

# 40. 정리

ERC-4337의 핵심 구성 요소를 정리하면 다음과 같다.

구성 요소                                             역할

| Smart Account    | Programmable Account               |
| ---------------- | ---------------------------------- |
| UserOperation    | 사용자가 실행하고 싶은 작업                    |
| Bundler          | UserOperation을 수집하고 Bundle 생성      |
| EntryPoint       | UserOperation 검증 및 실행의 중심 Contract |
| Paymaster        | 사용자 대신 Gas 비용 부담 가능                |
| Factory          | Smart Account 생성                   |
| validateUserOp() | Account의 Operation 검증              |
| handleOps()      | 여러 UserOperation 처리                |
| nonce            | Replay Attack 방지                   |

전체적인 구조는 다음과 같다.

```
                     User
                       │
                       │ UserOperation
                       ▼
                    Bundler
                       │
                       │ Bundle
                       ▼
                   EntryPoint
                       │
             ┌─────────┴─────────┐
             │                   │
             ▼                   ▼
       Smart Account          Paymaster
             │                   │
      validateUserOp()       Gas Sponsor
             │
             └─────────┬─────────┘
                       │
                       ▼
                    Execute
                       │
                       ▼
                Target Contract

```

결국 ERC-4337의 핵심은

```
EOA

Account = Private Key 중심

            ↓

ERC-4337

Account = Programmable Smart Contract

```

라고 정리할 수 있다.

단순히 Wallet UI를 편하게 만드는 것이 아니라 **Account의 인증, 실행,**

**Gas Payment, Recovery 등의 로직 자체를 Smart Contract로 프로그래밍할 수 있도록 만드는 구조**라는 점이 중요하다.

ERC-4337을 공부하면서 Account Abstraction이 왜 Ethereum UX를

개선하는 핵심 기술 중 하나로 자주 언급되는지 이해할 수 있었다.

동시에 Account 자체가 Smart Contract가 되면서

새로운 공격 표면도 생기기 때문에 앞으로 Web3 보안을 공부할 때

Smart Account의 validateUserOp(), Paymaster, EntryPoint와 같은 부분도 함께 분석해보면 좋을 것 같다.

---

# 41. 이번 EIP 미션을 마치며

이번 미션에서는 총 5개의 EIP/ERC를 공부했다.

```
ERC-20
│
├─ Fungible Token 표준
│
▼
ERC-721
│
├─ Non-Fungible Token 표준
│
▼
EIP-2612
│
├─ Signature 기반 Token Approval
│
▼
EIP-1559
│
├─ Ethereum Fee Market
│
▼
ERC-4337
   │
   └─ Account Abstraction

```

처음에는 각각의 EIP가 별개의 표준이라고 생각했지만 하나씩 공부하면서 서로 연결되는 부분을 확인할 수 있었다.

ERC-20의 approve() 구조를 이해하니 EIP-2612의 permit()이 왜 등장했는지 알 수 있었고,

EIP-2612에서 Signature와 Nonce를 공부한 뒤 ERC-4337을 보니 UserOperation의 인증 구조를 이해하기 쉬웠다.

또 EIP-1559에서 Gas Fee를 공부한 뒤 ERC-4337을 살펴보니

UserOperation에 maxFeePerGas, maxPriorityFeePerGas가 왜 존재하는지도 자연스럽게 이해할 수 있었다.

이번 미션을 통해 EIP를 공부할 때 단순히 "이 EIP에는 이런 기능이 있다." 정도로 외우는 것보다

```
기존에는 어떤 문제가 있었는가?

        ↓

왜 새로운 EIP가 필요했는가?

        ↓

어떤 방식으로 해결했는가?

        ↓

새로운 구조에는 어떤 보안 문제가 생길 수 있는가?

```

순서로 살펴보는 것이 훨씬 이해하기 쉽다는 것을 알 수 있었다.

앞으로 Smart Contract나 DeFi 취약점을 분석할 때도 해당 Contract가

어떤 EIP/ERC를 기반으로 구현되어 있는지 먼저 확인하고,

표준에서 정의한 정상적인 동작과 실제 구현의 차이를 비교해보는 방식으로 공부하면 도움이 될 것 같다.
