# ARM PAC (Pointer Authentication Code) 보호 기법 분석

## 개요

PAC(Pointer Authentication Code)는 ARMv8.3-A에서 도입된 AArch64 하드웨어 보안 기능이다.

PAC의 목적은 포인터의 무결성(Integrity)을 보호하는 것이다. 프로그램에서 사용되는 포인터가 정상적으로 생성된 값인지 검증하여 공격자가 포인터 값을 임의로 변조하는 행위를 차단한다.

메모리 손상 취약점은 현대 소프트웨어 공격에서 가장 자주 활용되는 취약점 중 하나이다.

대표적인 취약점은 다음과 같다.

- Stack Buffer Overflow
- Heap Overflow
- Use-After-Free (UAF)
- Double Free
- Arbitrary Write

이러한 취약점의 공통적인 목표는 프로그램의 제어 흐름(Control Flow)을 탈취하는 것이다.

공격자는 함수의 반환 주소(Return Address)를 덮어쓰거나 함수 포인터(Function Pointer)를 변조하여 프로그램이 의도하지 않은 코드 흐름을 실행하도록 만든다.

대표적인 공격 기법이 ROP(Return-Oriented Programming)이다.

ROP는 프로그램 내부에 이미 존재하는 코드 조각(Gadget)을 `ret` 명령어를 기준으로 연결하여 공격자가 원하는 흐름을 구성하는 코드 재사용 공격(Code-Reuse Attack) 기법이다.

NX(Non-Executable Memory)와 같은 보호 기법으로 직접적인 쉘코드 실행이 어려워지면서 기존 코드 조각을 재활용하는 ROP 공격이 널리 활용되기 시작했다.

PAC는 이러한 공격을 완화하기 위한 하드웨어 기반 보호 기법이다.

---

## PAC가 필요한 이유

기존 시스템에서는 CPU가 메모리에 저장된 포인터 값을 별도의 검증 없이 그대로 사용한다.

예를 들어 Stack Buffer Overflow가 발생하면 함수의 Return Address를 덮어쓸 수 있다.

```c
void vuln() {
    char buf[64];
    gets(buf);
}
```

스택 구조는 다음과 같다.

```text
[ local buffer ]
[ saved frame pointer ]
[ return address ]
```

버퍼를 초과하는 데이터를 입력하면 Return Address 영역까지 덮어쓰기가 가능하다.

공격자가 위조된 Return Address를 삽입하면 함수 종료 시 CPU는 해당 주소로 점프한다.

이 과정에서 CPU는 Return Address가 정상적인 값인지 확인하지 않는다.

함수 포인터 역시 동일하다.

```c
struct obj {
    void (*fn)(void);
};
```

Heap Overflow가 발생하면 함수 포인터를 공격자가 원하는 주소로 덮어쓸 수 있다.

```c
obj->fn = attacker_controlled;
```

이후 함수 호출 시:

```c
obj->fn();
```

공격자가 원하는 코드가 실행된다.

기존 구조의 문제는 CPU가 포인터 자체를 신뢰한다는 점이다.

PAC는 이러한 신뢰 구조를 제거하고 포인터 검증을 강제한다.

---

## PAC 원리

PAC의 핵심 개념은 포인터에 암호학적 인증 코드(Authentication Code)를 삽입하는 것이다.

기존 포인터 구조:

```text
Pointer = Address
```

PAC 적용 후:

```text
Signed Pointer = Pointer + PAC
```

PAC는 포인터 사용 시 다음 요소를 기반으로 생성된다.

```text
PAC = MAC(Key, Pointer, Context)
```

구성 요소는 다음과 같다.

- Key
- Pointer
- Context

---

### Key

PAC 생성에 사용되는 비밀 키이다.

ARM CPU 내부에서 관리되며 사용자 공간에서 직접 접근할 수 없다.

사용되는 키는 다음과 같다.

| Key | Description |
|-----|------------|
| APIAKey | Instruction A Key |
| APIBKey | Instruction B Key |
| APDAKey | Data A Key |
| APDBKey | Data B Key |
| APGAKey | Generic Key |

Key 크기는 128bit이다.

Instruction Key는 제어 흐름 관련 포인터 보호에 사용된다.

대표적으로:

- Return Address
- Function Pointer

Data Key는 데이터 포인터 보호에 사용된다.

A/B Key는 서로 다른 독립 키이며 동일한 포인터라도 어떤 키를 사용하느냐에 따라 PAC 값이 달라진다.

---

### Pointer

서명할 실제 포인터 값이다.

대표적인 예시는 다음과 같다.

- LR(Link Register)
- Function Pointer
- Data Pointer

---

### Context

PAC 생성에 사용되는 추가 입력값이다.

같은 포인터라도 Context가 다르면 PAC 값이 달라진다.

예:

```text
Pointer = 0x400123
Context = SP = 0x7fff0000
```

과

```text
Pointer = 0x400123
Context = SP = 0x7fff1000
```

는 서로 다른 PAC 값을 가진다.

이 구조는 다른 함수에서 유출된 PAC 값을 재사용하는 Replay 공격을 어렵게 만든다.

일반적으로 Stack Pointer(SP)가 Context로 사용된다.

---

## PAC 저장 위치

AArch64는 64bit 아키텍처이지만 실제 virtual address space 전체 64bit를 모두 사용하는 것은 아니다.

일반적으로 일부 상위 비트는 사용되지 않는다.

구조:

```text
[ unused bits ][ actual address ]
```

PAC는 이 사용되지 않는 상위 비트 영역에 저장된다.

즉:

```text
[ PAC ][ Actual Pointer ]
```

별도의 추가 메모리 없이 기존 포인터 내부에 인증 정보를 포함시키는 방식이다.

---

## PAC 인증 과정

PAC 동작은 PAC Instruction과 AUT Instruction으로 구성된다.

### PAC Instruction

PAC 생성 과정이다.

대표 명령어:

```asm
PACIA
PACIB
PACDA
PACDB
```

예:

```asm
PACIASP
```

의미:

- PACIA → Instruction Address PAC 생성
- SP → Context 사용

동작:

- LR(Return Address) 추출
- Key + LR + SP 기반 PAC 생성
- 생성된 PAC를 LR 상위 비트에 삽입

---

### AUT Instruction

PAC 검증 과정이다.

대표 명령어:

```asm
AUTIA
AUTIB
AUTDA
AUTDB
```

예:

```asm
AUTIASP
```

동작:

- LR 내부 PAC 추출
- 동일한 조건으로 PAC 재계산
- PAC 비교

검증 성공:

- PAC 제거
- 원래 Pointer 복원

검증 실패:

- Invalid Pointer 생성
- 정상적인 제어 흐름 유지 불가

---

## 함수 호출 흐름

PAC는 함수 진입(Function Prologue)과 종료(Function Epilogue) 시 동작한다.

함수 진입:

```asm
PACIASP
STP x29, x30, [sp, #-16]!
```

동작:

- LR(Return Address)에 PAC 생성
- 서명된 LR 저장

함수 종료:

```asm
LDP x29, x30, [sp], #16
AUTIASP
RET
```

동작:

- 서명된 LR 복원
- PAC 검증
- 검증 성공 시 원래 Return Address로 복귀

전체 흐름:

```text
Function Call
→ PAC 생성
→ Return Address 서명
→ Stack 저장
→ 함수 실행
→ Return Address 복원
→ PAC 검증
→ RET
```

## 방어 가능한 공격

PAC는 포인터 위변조 기반 공격을 완화한다.

대상:

- Return Address Overwrite
- Function Pointer Overwrite
- ROP
- 일부 Code-Reuse Attack

### Return Address Overwrite

공격자가 Return Address를 위조하더라도 정상 PAC를 생성할 수 없다.

AUT 검증 실패로 인해 정상적인 복귀가 불가능하다.

---

### Function Pointer Overwrite

함수 포인터를 위조하더라도 PAC 검증을 통과하지 못한다.

---

### ROP

ROP는 위조된 Return Address를 연결하여 Gadget Chain을 구성하는 공격이다.

PAC는 Return Address의 무결성을 검증하므로 Gadget Chain 구성이 매우 어려워진다.

---

## PAC 한계

PAC는 완전한 보호 기법이 아니다.

### Memory Corruption 자체는 방지하지 못함

PAC는 메모리 손상 취약점을 제거하지 않는다.

Exploit 난이도를 높이는 보호 기법이다.

---

### Data-only Attack 대응 불가

예:

```c
is_admin = 1;
```

포인터를 조작하지 않는 공격은 PAC 보호 대상이 아니다.

---

### Pointer Reuse

정상적인 Signed Pointer가 유출되면 재사용 가능성이 존재한다.

---

### PACMAN Attack

PAC 우회 사례이다.

PACMAN은 speculative execution 기반 side-channel 공격이다.

공격 흐름:

- 메모리 손상 취약점 확보
- speculative execution 내부에서 AUT 검증 수행
- architectural crash 없이 side-channel 정보만 획득
- PAC brute-force oracle 구성

PACMAN은 AUT 실패 결과를 speculative execution 내부에 숨기고 cache timing 정보를 통해 PAC 값을 추측한다.

---

## 추가 보호 기법

PAC 단독으로 모든 Control Flow 공격을 방어할 수 없다.

ARM은 BTI(Branch Target Identification)를 함께 제공한다.

BTI는 간접 분기 대상 검증을 수행한다.

보호 대상:

- JOP
- Indirect Branch Abuse

구조:

```text
PAC → Pointer Integrity
BTI → Branch Control Protection
```

PAC와 BTI를 함께 사용하는 것이 일반적이다.

---

## 결론

PAC는 ARM의 하드웨어 기반 포인터 무결성 보호 기법이다.

핵심 특징:

- 포인터 암호학적 서명
- CPU 직접 검증
- Return Address 보호
- Function Pointer 보호
- ROP 완화

한계:

- Memory Corruption 자체는 방지하지 못함
- Data-only Attack 대응 불가
- PACMAN 우회 가능성 존재

PAC는 취약점을 제거하는 기술이 아니라 Exploitation 난이도를 높이는 현대 ARM 보안 보호 기법이다.
