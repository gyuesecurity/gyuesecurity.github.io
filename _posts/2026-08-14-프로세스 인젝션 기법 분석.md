# 프로세스 인젝션 기법 및 백신의 인젝션 방지 원리 분석

## 1. 프로세스 인젝션이란

프로세스 인젝션(Process Injection)은 실행 중인

다른 프로세스의 주소 공간이나 실행 흐름을 이용해 자신의 코드를 실행시키는 기법이다.

일반적인 프로그램은 자신에게 할당된 가상 메모리 공간에서 자신의 코드를 실행한다.

```
Program A

┌───────────────────────┐
│ Process A             │
│                       │
│ Code                  │
│ Heap                  │
│ Stack                 │
│ Loaded DLL            │
└───────────────────────┘

```

하지만 프로세스 인젝션에서는 Process A가 Process B의 메모리나 스레드 상태에 영향을 준다.

```
Process A
   │
   │ 다른 프로세스 접근
   │
   │ 메모리 또는 실행 흐름 변경
   ▼
Process B
   │
   └── Process A가 전달한 코드 실행

```

즉 핵심은 단순히 코드를 실행하는 것이 아니라,

코드가 원래 생성된 프로세스가 아닌 다른 프로세스의 실행 문맥(Context)에서 동작하도록 만드는 것이다.

MITRE ATT&CK에서는 이러한 공격 계열을 **T1055 Process Injection**으로 분류하고 있다.

프로세스 인젝션 아래에는 DLL Injection, APC Injection,

Thread Execution Hijacking, Process Hollowing 등 다양한 하위 기법이 존재한다.

---

# 2. 프로세스를 이해해야 하는 이유

프로세스 인젝션을 이해하기 위해서는 먼저 운영체제에서 프로세스가 무엇인지 이해할 필요가 있다.

프로그램과 프로세스는 서로 다른 개념이다.

프로그램은 디스크에 존재하는 실행 가능한 파일이다.

예를 들어 다음은 프로그램이다.

```
notepad.exe
chrome.exe
explorer.exe
calc.exe

```

이 프로그램을 운영체제가 실행하면 프로세스가 생성된다.

```
explorer.exe
      ↓
Windows Loader
      ↓
Process 생성
      ↓
Virtual Address Space 할당
      ↓
Thread 생성
      ↓
프로그램 실행

```

따라서

```
Program = 실행되기 전의 코드

Process = 실제 메모리에서 실행되고 있는 프로그램

```

이라고 볼 수 있다.

프로세스에는 단순히 실행 코드만 존재하는 것이 아니다.

프로세스는 다음과 같은 여러 구성 요소를 가지고 있다.

```
Process

├── Virtual Address Space
├── Executable Image
├── Loaded DLL
├── Heap
├── Stack
├── Thread
├── Handle
├── Security Token
└── Process Environment Block

```

프로세스 인젝션은 이러한 구성 요소 중 특히

```
Memory
Thread
Execution Context
Module
Handle

```

을 조작하는 공격 기법이라고 볼 수 있다.

---

# 3. Virtual Address Space

Windows의 각 프로세스에는 독립적인 가상 주소 공간(Virtual Address Space)이 존재한다.

예를 들어 다음과 같은 두 개의 프로세스가 존재한다고 가정할 수 있다.

```
Process A
Virtual Address Space

0x00000000
     │
     ├── Code
     ├── DLL
     ├── Heap
     ├── Stack
     │
     ▼


Process B
Virtual Address Space

0x00000000
     │
     ├── Code
     ├── DLL
     ├── Heap
     ├── Stack
     │
     ▼

```

두 프로세스에서 같은 주소가 사용되더라도 실제 물리 메모리에서는 서로 다른 영역으로 매핑될 수 있다.

즉 기본적으로 Process A가 자신의 코드에서 단순한 메모리 접근을 수행한다고

해서 Process B의 메모리를 바로 변경할 수 있는 것은 아니다.

Windows는 이러한 프로세스 격리를 통해 하나의 프로그램이 다른 프로그램의 메모리를 무작위로 변경하지 못하도록 한다.

하지만 디버거, 보안 프로그램, 관리 프로그램 등은 정상적인 목적으로 다른 프로세스를 조사해야 하는 경우가 있다.

따라서 Windows에는 프로세스 간 메모리 접근을 가능하게 하는 기능이 존재한다.

공격자는 이러한 정상 기능을 악용할 수 있다.

---

# 4. 프로세스 인젝션의 기본 구조

프로세스 인젝션 기법은 종류마다 세부 과정이 다르지만 대부분 다음과 같은 공통 구조를 가진다.

```
1. Target Process 선택
          ↓
2. Target Process 접근
          ↓
3. Target Process 상태 변경
          ↓
4. Data 또는 Code 전달
          ↓
5. 실행 흐름 변경
          ↓
6. Target Process 안에서 코드 실행

```

이를 조금 더 단순화하면 세 가지 핵심 단계가 된다.

```
Access
   ↓
Modify
   ↓
Execute

```

즉

### Access

다른 프로세스에 접근한다.

### Modify

해당 프로세스의 메모리 또는 실행 상태를 변경한다.

### Execute

변경된 상태를 이용해 코드가 실행되도록 한다.

백신과 EDR 역시 이러한 세 단계에서 발생하는 이상 행동을 관찰한다.

---

# 5. 공격자는 왜 Process Injection을 사용하는가

프로세스 인젝션을 처음 보면 다음과 같은 의문이 생길 수 있다.

악성 프로그램을 그냥 실행하면 되는데 왜 굳이 다른 프로세스에 코드를 집어넣는가?

여기에는 여러 이유가 있다.

---

## 5.1 정상 프로세스의 실행 문맥 이용

악성 프로그램이 직접 실행된 경우 다음과 같은 구조를 가진다.

```
malware.exe
    │
    ├── 악성 코드
    ├── 파일 접근
    ├── 네트워크 통신
    └── 시스템 조작

```

보안 프로그램에서는

```
새로운 Process 생성

+

의심스러운 행동

```

이라는 관계를 쉽게 관찰할 수 있다.

반면 프로세스 인젝션에서는

```
malware.exe
      │
      ▼
explorer.exe
      │
      └── Injected Code

```

와 같은 구조가 만들어질 수 있다.

즉 코드의 실제 작성 주체와 실행되는 프로세스가 분리된다.

---

# 5.2 새로운 프로세스 생성 감소

많은 보안 시스템에서는 프로세스 생성 이벤트를 중요하게 분석한다.

예를 들어

```
Word
 ↓
PowerShell
 ↓
cmd
 ↓
unknown.exe

```

같은 비정상 프로세스 트리는 강한 탐지 신호가 될 수 있다.

하지만 기존 프로세스 내부에서 실행이 발생하면 새로운 프로세스를 만들지 않고도 코드 실행이 가능할 수 있다.

따라서 공격자는 기존 프로세스의 실행 흐름을 이용하려고 시도한다.

---

# 5.3 정상 프로세스에 섞이기

Windows에서는 항상 매우 많은 정상 프로세스가 실행된다.

예를 들어

```
explorer.exe
svchost.exe
runtimebroker.exe
dllhost.exe
chrome.exe

```

등이다.

공격자의 코드가 이러한 정상 프로세스 내부에서 실행된다면

단순히 프로세스 이름만 확인해서는 정상 코드와 비정상 코드를 구분하기 어렵다.

따라서

```
Process Name = 정상

```

이라고 해서

```
Process 내부에서 실행되는 모든 Code = 정상

```

이라는 의미는 아니다.

---

# 5.4 권한과 리소스 이용

프로세스마다 가지고 있는 권한과 접근 가능한 자원이 다르다.

Windows에서는 Security Token을 통해 프로세스의 권한이 결정된다.

```
Process

└── Security Token
        ├── User SID
        ├── Group SID
        ├── Privileges
        └── Integrity Level

```

특정 프로세스의 실행 문맥을 이용하면 그 프로세스가 가지고 있는 자원이나 권한을 활용하려는 공격이 가능할 수 있다.

다만 모든 프로세스에 무조건 접근할 수 있는 것은 아니다.

Windows의 권한 검사와 Protected Process 같은 보호 기능이 존재한다.

---

# 6. Process Handle

Windows에서 프로세스 인젝션을 이해할 때 중요한 개념 중 하나가 **Handle**이다.

Handle은 운영체제 객체를 참조하기 위한 식별자라고 볼 수 있다.

Windows에서는 다음과 같은 다양한 대상이 Kernel Object로 관리된다.

```
Process
Thread
File
Registry Key
Event
Mutex
Token

```

프로그램이 다른 프로세스에 접근하려면 일반적으로 해당 프로세스에 대한 Handle이 필요하다.

```
Process A

   │

Process Handle

   │

   ▼

Process B

```

Handle에는 접근 권한도 연결되어 있다.

예를 들어 개념적으로

```
Read
Write
Execute-related operation
Query

```

등이 있다.

따라서 보안 프로그램에서는 어떤 프로세스가 어떤 프로세스에 어떤 권한으로 접근하는가? 를 중요한 탐지 정보로 사용할 수 있다.

---

# 7. Memory Protection

프로세스 메모리에는 각각 접근 권한이 존재한다.

대표적으로 다음과 같은 권한이 있다.

```
R = Read
W = Write
X = Execute

```

예를 들어 프로그램의 일반적인 코드 영역은 다음과 같다.

```
.text

Read
Execute

```

데이터 영역은 보통

```
.data

Read
Write

```

형태를 가진다.

보안 관점에서 특히 중요한 부분은

```
Write
+
Execute

```

권한이다.

공격 코드가 실행되기 위해서는 결국 CPU가 해당 메모리 영역을 실행 가능한 영역으로 인식해야 하는 경우가 많기 때문이다.

따라서 보안 프로그램에서는 다음과 같은 변화가 중요한 신호가 될 수 있다.

```
Writable Memory
       ↓
Data 기록
       ↓
Executable Memory
       ↓
Code 실행

```

---

# 8. Thread란 무엇인가

프로세스는 실행 환경이고 실제 CPU에서 실행되는 단위는 Thread이다.

```
Process

├── Thread 1
├── Thread 2
├── Thread 3
└── Thread 4

```

각 Thread에는 CPU 실행 상태가 존재한다.

대표적으로 다음 정보가 포함된다.

```
Instruction Pointer
Stack Pointer
CPU Registers
Thread State

```

x64 환경에서 Instruction Pointer 역할을 하는 대표적인 레지스터가 RIP이다.

```
RIP
 ↓
현재 CPU가 실행할 코드 주소

```

따라서 Process Injection의 많은 기법은 결국

Target Process 내부의 Thread가 공격자가 원하는 코드 주소를 실행하도록 만드는 것이라고 해석할 수도 있다.

---

# 9. DLL Injection

DLL Injection은 가장 대표적인 Process Injection 기법이다.

Windows 프로그램은 여러 DLL을 동적으로 로드한다.

예를 들어 프로그램 실행 중 다음과 같은 DLL들이 사용될 수 있다.

```
kernel32.dll
user32.dll
ntdll.dll
advapi32.dll

```

DLL Injection에서는 대상 프로세스가 공격자가 원하는 DLL을 로드하도록 유도한다.

개념 구조는 다음과 같다.

```
Injector
   │
   │ DLL 관련 정보 전달
   ▼
Target Process
   │
   ▼
DLL Load
   │
   ▼
DLL Code Execution

```

핵심은 Windows의 정상적인 DLL 로딩 기능을 악용한다는 것이다.

---

# 10. DLL Injection의 특징

DLL Injection에서는 대상 프로세스 내부에 새로운 DLL Module이 나타날 수 있다.

정상적인 프로그램에서도 DLL은 계속 로드되므로

```
DLL Load 발생

```

자체만으로 악성이라고 판단하기는 어렵다.

따라서 보안 시스템은 다음과 같은 관계를 함께 분석한다.

```
Process A

      ↓

Process B 접근

      ↓

Process B Memory 변경

      ↓

Process B에 새로운 DLL Load

      ↓

실행 흐름 변화

```

즉 단일 이벤트가 아니라 이벤트들의 연속성을 보는 것이다.

---

# 11. APC Injection

APC는 **Asynchronous Procedure Call**의 약자이다.

Windows Thread에는 APC라는 메커니즘이 존재한다.

간단히 말하면 특정 Thread가 나중에 실행할 작업을 Queue에 등록할 수 있는 구조이다.

```
Thread

└── APC Queue

      ├── APC 1
      ├── APC 2
      └── APC 3

```

Thread가 특정 실행 상태에 들어가면 Queue에 등록된 APC가 실행될 수 있다.

APC Injection에서는 이 구조를 악용한다.

```
Attacker
    │
    ▼
Target Thread APC Queue
    │
    └── Injected Routine
               │
               ▼
          Code Execution

```

즉 별도의 새로운 프로세스를 만드는 대신 기존 Thread가 가지고 있는 APC 메커니즘을 이용하는 방식이다.

---

# 12. Thread Execution Hijacking

Thread Hijacking은 기존 Thread의 실행 흐름을 바꾸는 방식이다.

정상 상태에서는

```
Thread

RIP
 │
 ▼
Normal Code

```

형태로 코드가 실행된다.

공격자는 Thread의 실행 상태를 변경하여

```
Thread

RIP
 │
 ▼
Injected Code

```

로 실행 흐름을 바꾸려고 시도한다.

이 방식의 중요한 특징은

새로운 Thread를 생성하지 않고 기존 Thread를 사용할 수 있다는 것이다.

따라서 단순히

```
새로운 Thread가 만들어졌는가?

```

만 감시하는 보안 방식으로는 충분하지 않다.

Thread Context 변화까지 살펴봐야 한다.

---

# 13. Process Hollowing

Process Hollowing은 정상 프로세스를 만든 뒤 그 내부 실행 내용을 변경하는 방식이다.

개념적으로는 다음 구조이다.

```
정상 Process 생성
        ↓
Process 실행 일시 중지
        ↓
기존 Image 또는 Memory 변경
        ↓
다른 Code 배치
        ↓
Execution Context 변경
        ↓
Process 실행

```

겉으로 보면 정상적인 실행 파일에서 만들어진 프로세스처럼 보일 수 있다.

하지만

```
Disk에 존재하는 Program

≠

Memory에서 실제 실행되는 Code

```

라는 상태가 나타날 수 있다.

이러한 특징 때문에 보안 제품에서는 Memory와 Disk Image의 일치 여부도 중요한 분석 대상이 된다.

---

# 14. PE Injection

Windows 실행 파일은 일반적으로 PE(Portable Executable) 형식을 사용한다.

대표적으로

```
.exe
.dll
.sys

```

등이 PE 구조를 가진다.

PE Injection 계열은 PE 데이터를 다른 프로세스의 메모리 안에 배치하고 실행시키는 방식이다.

DLL Injection에서는 일반적인 Loader의 DLL Loading 기능을 적극적으로 이용한다.

반면 일부 PE Injection 계열에서는 정상적인 Module Load 흔적을

최소화하면서 메모리에서 실행 가능한 구조를 구성하려고 한다.

따라서 보안 프로그램에서는

```
Module List

```

만 검사하는 것으로 충분하지 않을 수 있다.

---

# 15. Reflective DLL Loading

일반적인 DLL은 Windows Loader를 통해 로드된다.

```
DLL
 ↓
Windows Loader
 ↓
Memory Mapping
 ↓
Relocation
 ↓
Import Resolution
 ↓
Execution

```

Reflective DLL Loading은 이러한 Loader 역할의 일부를 코드 자체가 수행하도록 하는 방식이다.

개념적으로

```
DLL Data
     ↓
Memory
     ↓
Custom Loader
     ↓
DLL 구조 구성
     ↓
Execution

```

형태가 된다.

이러한 기법이 등장하면서 단순한

```
정상 DLL Load 이벤트

```

만 감시하는 방어 방식으로는 충분하지 않게 되었다.

---

# 16. Manual Mapping

Manual Mapping 역시 Windows Loader를 직접 사용하지 않고 PE 구조를 메모리에 구성하는 기법이다.

PE 파일에는 여러 정보가 존재한다.

```
PE Header

Sections

Import Table

Relocation Table

Export Table

```

정상 Windows Loader가 수행하는 작업 중 일부를 직접 구현하여 메모리에서 실행 가능한 형태를 만드는 것이다.

따라서 정상 Module 목록에서는 쉽게 확인되지 않는 실행 코드가 존재할 가능성이 생긴다.

이를 탐지하기 위해 EDR은

```
Executable Private Memory

PE Header Pattern

Memory Permission

Thread Start Address

```

등을 함께 분석할 수 있다.

---

# 17. Process Doppelgänging

Process Doppelgänging은 Process Hollowing과 비슷하게 정상 프로세스 생성 메커니즘을 악용하는 계열의 기법이다.

다만 내부적으로 Windows의 Transaction 기능 및 Process 생성 특성을 악용하는 방식이라는 차이가 있다.

큰 관점에서는

```
정상적인 Process 생성 구조

+

비정상적인 Image 상태

```

를 만드는 공격이라고 이해하면 된다.

---

# 18. Early Bird APC Injection

Early Bird APC Injection은 APC Injection 계열의 변형이다.

일반적인 APC Injection에서는 이미 실행 중인 Thread를 이용한다.

Early Bird 방식은 Process가 본격적으로 실행되기 이전 단계의 Thread에 APC를 등록하는 개념을 이용한다.

구조를 단순화하면

```
Process 생성
     ↓
Main Thread
     ↓
APC 등록
     ↓
Thread 실행
     ↓
APC Code 선행 실행
     ↓
정상 Process 실행

```

형태가 된다.

이름의 Early Bird 역시 정상 프로그램 실행보다 먼저 코드가 실행되는 특성에서 나온 것이다.

---

# 19. Module Stomping

Module Stomping은 이미 로드되어 있는 정상 Module의 메모리 일부를 다른 코드로 변경하는 계열의 기법이다.

일반적인 Injection에서는 새로운 메모리 또는 Module이 등장할 수 있다.

하지만 Module Stomping에서는

```
Existing DLL
     ↓
Memory 일부 변경
     ↓
Injected Code

```

처럼 기존 Module 영역을 이용할 수 있다.

따라서 단순히

```
Unknown DLL 존재 여부

```

만 확인하는 방식으로 탐지하기 어려울 수 있다.

대신

```
Disk DLL

vs

Memory DLL

```

내용을 비교하는 방식이 중요해진다.

---

# 20. 프로세스 인젝션 기법들의 공통점

기법은 다양하지만 대부분 다음 요소 중 하나 이상을 사용한다.

```
Process Access

Memory Allocation

Memory Write

Memory Permission Change

Thread Creation

Thread Context Modification

Module Load

Execution Flow Modification

```

결국 모든 Process Injection은

```
다른 프로세스의

Memory

또는

Execution Context

를 변경한다.

```

라는 공통점을 가진다.

따라서 백신과 EDR에서도 개별 공격 기법을 하나하나 외우기보다는 이러한 공통 행위 특성을 탐지하는 방향으로 발전하고 있다.

---

# 21. 인젝션 없는 실행과 인젝션의 차이

정상적인 프로그램 실행을 보면 다음과 같다.

```
Program.exe
     ↓
Process 생성
     ↓
Program Image Mapping
     ↓
Thread 생성
     ↓
자신의 Address Space에서 실행

```

반면 Process Injection에서는

```
Injector.exe
      ↓
Target Process 접근
      ↓
Target Process Memory 변경
      ↓
Target Process Execution 변경
      ↓
Target Process에서 Code 실행

```

과 같은 추가적인 Cross-Process Activity가 발생한다.

가장 중요한 차이는

```
Normal

Process A
   ↓
Process A Memory


Injection

Process A
   ↓
Process B Memory

```

이다.

따라서 Process Injection 탐지의 중요한 기준 중 하나가 바로 **Cross-Process Behavior**이다.

---

# 22. 백신은 왜 특정 API 하나만 차단하지 않는가

Process Injection을 처음 공부하면

> 다른 프로세스를 변경하는 API를 전부 차단하면 되는 것 아닌가?

라는 생각을 할 수 있다.

하지만 현실적으로는 불가능하다.

다른 프로세스의 메모리를 읽거나 변경하는 기능은 정상 프로그램에서도 사용하기 때문이다.

대표적인 예로

```
Debugger
Security Software
Accessibility Software
Monitoring Software
Game Overlay
System Management Tool

```

등이 있다.

따라서

```
다른 Process 접근
      =
Malware

```

라고 판단할 수 없다.

대신 여러 행동의 관계를 분석해야 한다.

---

# 23. 행동 기반 탐지

현대 백신과 EDR에서는 행동 기반 탐지가 중요하다.

예를 들어 하나의 Process가 다음 행동을 했다고 가정한다.

```
Process A

      ↓

Process B Open

      ↓

Process B Memory Write

      ↓

Memory Permission Change

      ↓

Thread Execution 변화

```

각 행동 하나만 보면 정상 프로그램에서도 발생할 수 있다.

하지만 이러한 행동이 짧은 시간 안에 연속적으로 발생한다면 위험도가 증가한다.

이를

```
Behavior Correlation

```

이라고 볼 수 있다.

---

# 24. Process Access Monitoring

첫 번째 방어 포인트는 Process 간 접근이다.

보안 제품에서는 다음 정보를 관찰할 수 있다.

```
Source Process

Target Process

Requested Permission

User

Integrity Level

Process Reputation

```

예를 들어

```
Unknown.exe
     ↓
explorer.exe

```

에 매우 높은 접근 권한을 요청한다면 일반적인 프로그램보다 더 많은 관심을 받을 수 있다.

---

# 25. Memory Write Detection

프로세스 인젝션에서는 다른 프로세스의 메모리에 데이터를 전달해야 하는 경우가 많다.

따라서

```
Process A

writes

Process B memory

```

라는 Cross-Process Memory Write는 중요한 신호이다.

하지만 이 역시 정상 프로그램에서 사용될 가능성이 존재한다.

따라서 Memory Write 하나로 악성 여부를 결정하지 않는다.

---

# 26. Executable Memory Detection

보안 관점에서 특히 관심을 받는 메모리는 실행 가능한 Private Memory이다.

정상 프로그램의 코드는 일반적으로 실행 파일 또는 DLL과 연결된 메모리에 존재하는 경우가 많다.

```
File

Program.exe

     ↓

Memory Mapped Image

     ↓

Executable Code

```

반면 인젝션된 코드에서는

```
Private Memory
     ↓
Code Data
     ↓
Executable Permission
     ↓
Execution

```

같은 형태가 나타날 수 있다.

따라서 EDR에서는

```
MEM_PRIVATE

+

Executable

```

형태의 메모리를 중요한 조사 대상으로 볼 수 있다.

---

# 27. RWX Memory

특히 의심을 받을 수 있는 메모리 속성이

```
Read
Write
Execute

```

즉 RWX이다.

일반적인 보안 원칙에서는

```
W^X

```

개념이 중요하다.

이는 Writable 메모리와 Executable 메모리를 가능하면 분리한다. 는 원칙이다.

이유는 간단하다.

```
Write 가능
+
Execute 가능

```

하면 데이터를 작성한 뒤 바로 코드로 실행할 수 있기 때문이다.

따라서 RWX 메모리는 보안 제품이 관찰하는 중요한 휴리스틱 중 하나가 될 수 있다.

단, RWX 메모리 자체가 반드시 악성이라는 의미는 아니다.

JIT Compiler처럼 정상 프로그램에서도 사용할 수 있기 때문이다.

---

# 28. Thread Start Address 분석

새로운 Thread가 생성되었다면 EDR은 Thread가 어느 주소에서 실행되는지 확인할 수 있다.

정상적인 경우에는

```
Thread

 ↓

Program Module

또는

Loaded DLL

```

내부의 코드에서 시작되는 경우가 많다.

반면 의심스러운 상황에서는

```
Thread
 ↓
Private Executable Memory

```

에서 시작될 수 있다.

따라서

```
Thread Start Address

+

Memory Type

```

의 관계는 중요한 탐지 요소가 된다.

---

# 29. Memory Image와 Disk Image 비교

Process Hollowing이나 Module Stomping 같은 공격을 탐지하기 위해서는

메모리에 존재하는 코드와 디스크 파일을 비교할 수 있다.

정상적인 경우

```
Disk

Program.exe

≈

Memory

Program Image

```

여야 한다.

하지만 변조가 발생하면

```
Disk Image

≠

Memory Image

```

상태가 나타날 수 있다.

이를 통해

```
Code modification

Process Hollowing

Module Stomping

```

등을 탐지할 수 있다.

---

# 30. Call Stack 분석

EDR에서는 Thread가 어떤 경로를 통해 현재 코드에 도달했는지를 분석할 수도 있다.

이를 Call Stack이라고 한다.

정상적인 프로그램에서는 대체로

```
Program Module

↓

System DLL

↓

Function

↓

Function

```

과 같은 자연스러운 Call Chain이 존재한다.

하지만 비정상 실행에서는

```
Unknown Memory

↓

Unexpected Address

↓

System Function

```

같은 형태가 나타날 수 있다.

따라서

```
Call Stack Anomaly

```

역시 Process Injection 탐지에 활용될 수 있다.

---

# 31. API Hooking

전통적인 보안 프로그램에서는 API Hooking을 이용해 중요한 함수 호출을 감시하기도 한다.

구조는 다음과 같다.

```
Application

   ↓

Windows API

   ↓

Security Hook

   ↓

Original Function

```

보안 제품은 이를 통해

```
Process Access
Memory Allocation
Memory Write
Thread Operation

```

등을 관찰할 수 있다.

하지만 공격 코드가 더 낮은 레벨의 System Call을 사용하거나

Hook을 우회하려는 기법을 사용할 수 있기 때문에 이것만으로 완전한 방어는 어렵다.

---

# 32. System Call Monitoring

Windows 프로그램이 Kernel 기능을 사용하려면 결국 System Call을 수행해야 한다.

구조를 단순화하면

```
Application

↓

Windows API

↓

ntdll.dll

↓

System Call

↓

Windows Kernel

```

이다.

따라서 높은 수준의 API 호출만 우회하더라도 Kernel Level에서 발생하는 실제 Process/Memory 작업은 남을 수 있다.

이 때문에 현대 EDR은 Kernel Telemetry를 중요하게 사용한다.

---

# 33. Kernel Callback

Windows Kernel은 보안 프로그램이 특정 시스템 이벤트를 관찰할 수 있도록 여러 Callback 메커니즘을 제공한다.

보안 제품에서는 이를 이용해

```
Process Creation

Thread Creation

Image Load

Handle Operation

```

같은 이벤트를 수집할 수 있다.

즉 Process Injection 방어가 단순히 사용자 모드의 API Monitoring만으로 이루어지는 것은 아니다.

---

# 34. ETW

ETW는 **Event Tracing for Windows**이다.

Windows 내부의 다양한 Component가 Event를 기록할 수 있는 Telemetry Framework이다.

개념적으로

```
Windows Components

     ↓

ETW Event

     ↓

Security Product

     ↓

Behavior Analysis

```

형태이다.

EDR은 ETW를 통해 Process, Thread, Image Load 등 여러 실행 정보를 확보할 수 있다.

---

# 35. 인젝션 탐지에서 중요한 것은 Chain이다

프로세스 인젝션 탐지를 이해할 때 가장 중요한 개념 중 하나이다.

다음 이벤트 하나만 존재한다고 가정해 보자.

```
Process Handle Open

```

이것만으로는 악성 여부를 판단하기 어렵다.

하지만

```
Unknown Process

      ↓

Sensitive Process Open

      ↓

Memory Allocation

      ↓

Memory Write

      ↓

Permission Change

      ↓

Thread Execution

```

이라는 연속적인 행동이 나타난다면 의심도가 크게 증가한다.

즉 현대 보안 제품은

```
Event

Event

Event

Event

```

를 각각 독립적으로 보는 것이 아니라

```
Event Chain

```

으로 분석하려고 한다.

---

# 36. 탐지 Score

행동 기반 엔진에서는 각 행동에 위험도를 부여하는 방식을 사용할 수 있다.

개념적인 예를 들면

```
Unknown Process        +10

Sensitive Process Open +10

Remote Memory Write    +20

Executable Memory      +30

Suspicious Thread      +30

```

같은 형태이다.

그리고

```
Risk Score

      ↓

Threshold

```

를 넘으면 탐지하는 방식으로 이해할 수 있다.

실제 제품 내부 알고리즘은 제조사마다 다르고 공개되지 않는 경우가 많지만,

여러 행동을 종합해 위험도를 판단하는 방식은 현대 Behavior Detection의 핵심 개념이다.

---

# 37. Static Detection과 Behavioral Detection

백신 탐지는 크게 정적 탐지와 행동 기반 탐지로 구분해서 이해할 수 있다.

## Static Detection

파일을 실행하기 전 또는 파일 자체를 분석한다.

```
File

 ↓

Hash

Signature

PE Structure

String

Known Pattern

 ↓

Detection

```

장점은 빠르다는 것이다.

하지만 새로운 샘플이나 변형된 파일에는 한계가 존재할 수 있다.

---

## Behavioral Detection

실제로 실행되면서 나타나는 행동을 분석한다.

```
Program 실행

 ↓

Process Activity

 ↓

Memory Activity

 ↓

Thread Activity

 ↓

File / Registry / Network Activity

 ↓

Behavior Correlation

 ↓

Detection

```

프로세스 인젝션 방어에서는 특히 Behavioral Detection이 중요하다.

---

# 38. Memory Scanning

백신과 EDR은 실행 중인 프로세스 메모리를 검사할 수도 있다.

디스크 파일에서는 아무것도 발견하지 못했더라도 실제 실행 중 메모리에 의심스러운 코드가 존재할 수 있기 때문이다.

```
Disk

Clean

     ↓

Program 실행

     ↓

Memory

Malicious Code

```

따라서

```
Memory Scanner

```

가 필요하다.

Memory Scanner는 다음과 같은 정보를 검사할 수 있다.

```
Executable Memory

Known Byte Pattern

PE Structure

Shellcode-like Pattern

Abnormal Memory Region

```

---

# 39. AMSI와의 차이

AMSI는 Anti-Malware Scan Interface이다.

PowerShell, JavaScript 등 Script 기반 콘텐츠를 보안 제품에서 검사할 수 있도록 지원하는 Windows Interface이다.

AMSI는 Process Injection 자체를 탐지하는 기술과는 조금 다르다.

```
AMSI

→ Script / Content Inspection


EDR Memory Monitoring

→ Process / Thread / Memory Behavior

```

따라서 둘은 역할이 다르지만 실제 Endpoint Protection 환경에서는 여러 보호 기술이 함께 사용된다.

---

# 40. Exploit Protection

일부 Process Injection은 취약점 악용과 결합된다.

예를 들어 취약점 공격 이후

```
Exploit

↓

Code Execution

↓

Process Injection

↓

Payload Execution

```

구조가 나타날 수 있다.

따라서 백신에서는 Process Injection을 단독으로만 방어하는 것이 아니라 Exploit Protection과 함께 방어한다.

대표적인 메모리 보호 기술에는 다음과 같은 개념이 존재한다.

```
DEP

ASLR

CFG

ACG

CIG

```

---

# 41. DEP

DEP는 Data Execution Prevention이다.

기본 아이디어는

```
Data Memory

≠

Executable Memory

```

이다.

즉 데이터 저장을 위해 사용되는 메모리 영역에서 임의 코드가 실행되는 것을 제한한다.

프로세스 인젝션을 완전히 방지하는 기능은 아니지만 메모리 기반 공격을 어렵게 만드는 중요한 보호 기술이다.

---

# 42. ASLR

ASLR은 Address Space Layout Randomization이다.

프로세스나 DLL이 메모리에 로드되는 주소를 랜덤화한다.

```
실행 1

Module → 0x12340000


실행 2

Module → 0x7A230000

```

이를 통해 공격자가 특정 코드나 함수 주소를 예측하기 어렵게 만든다.

---

# 43. CFG

CFG는 Control Flow Guard이다.

프로그램의 간접 호출이 허용된 코드 위치로만 이동하도록 제한하는 기술이다.

```
Indirect Call

     ↓

Valid Target ?

 ┌───────┴────────┐
Yes               No

 ↓                 ↓

Execute          Block

```

Thread Hijacking이나 Control Flow Manipulation 계열 공격의 난이도를 높이는 역할을 할 수 있다.

---

# 44. ACG

ACG는 Arbitrary Code Guard이다.

동적으로 생성되는 실행 코드를 제한하기 위한 기술이다.

개념적으로

```
Writable Memory

↓

Executable Memory


```

로 변경하는 것을 제한한다.

따라서 메모리에 데이터를 기록한 뒤 실행 권한을 부여하는 형태의 공격을 어렵게 만든다.

---

# 45. CIG

CIG는 Code Integrity Guard이다.

프로세스에 로드되는 Binary의 무결성과 서명을 제한하는 보호 기술이다.

이를 통해 신뢰되지 않은 Code가 특정 보호 프로세스에 로드되는 것을 제한할 수 있다.

---

# 46. Protected Process

Windows에는 일반적인 Process보다 강하게 보호되는 Process가 존재한다.

대표적으로

```
Protected Process

Protected Process Light

```

개념이 있다.

이러한 Process는 일반 Process가 자유롭게

```
Memory Read

Memory Write

Handle Access

Thread Manipulation

```

을 수행하지 못하도록 제한할 수 있다.

보안 프로그램 역시 자신의 핵심 Process를 Self-Protection 기능으로 보호하는 경우가 많다.

---

# 47. 보안 제품의 Self-Protection

공격자는 백신 자체를 종료하거나 조작하려고 시도할 수도 있다.

따라서 백신 제품에서는 자신의 프로세스를 별도로 보호한다.

개념적으로

```
AV Process

     ↓

Protected

     ↓

Unauthorized Process

     ↓

Access Denied

```

형태가 된다.

Self-Protection에는 다음과 같은 영역이 포함될 수 있다.

```
Process Protection

Service Protection

Driver Protection

Registry Protection

File Protection

```

---

# 48. Avast 계열의 방어 개념

Avast는 행동 기반 보호 기능을 통해 실행 중인 프로세스의 행동을 분석하는 구조를 제공한다.

Process Injection 관점에서는 다음과 같은 행동의 조합이 중요한 분석 대상이 된다.

```
Process Access

+

Memory Manipulation

+

Execution Behavior

+

후속 행동

```

즉 파일의 Signature만 확인하는 것이 아니라 프로그램이 실제로 어떤 행동을 수행하는지 분석하는 것이 핵심이다.

---

# 49. Kaspersky 계열의 방어 개념

Kaspersky 역시 Behavior Detection을 중요한 방어 요소로 사용한다.

Behavior Detection에서는 실행 중인 Application에서 발생하는 Event를 수집하고 특정 위험 행동 Pattern과 비교한다.

개념적으로 보면

```
Application Activity

      ↓

Behavior Events

      ↓

Behavior Pattern

      ↓

Risk Decision

      ↓

Allow / Block

```

형태이다.

Process Injection은 Process, Memory, Thread와 관련된 여러 행동이

동시에 나타날 수 있기 때문에 행동 분석 시스템에서 중요한 탐지 대상이 된다.

---

# 50. Bitdefender 계열의 방어 개념

Bitdefender는 Advanced Threat Control과 같은 행동 기반 보호 기술을 제공한다.

핵심 개념은 실행 중인 Process를 지속적으로 모니터링하면서 여러 위험 행동을 종합적으로 평가하는 것이다.

Process Injection 관점에서는

```
Process Manipulation

Memory Modification

Code Injection

Suspicious Execution

```

같은 행동들이 분석 대상이 될 수 있다.

---

# 51. Antivirus와 EDR의 차이

프로세스 인젝션을 분석하면서 Antivirus와 EDR의 차이도 이해해야 한다.

전통적인 Antivirus의 핵심 목적은

```
Malware

↓

Detection

↓

Blocking

```

이었다.

반면 EDR은

```
Endpoint

↓

Telemetry Collection

↓

Process Analysis

↓

Behavior Correlation

↓

Detection

↓

Investigation

↓

Response

```

까지 포함한다.

따라서 Process Injection 분석에서는 EDR이 훨씬 다양한 정보를 기록할 수 있다.

예를 들어

```
Source Process

Target Process

Parent Process

Process Hash

Process Signature

Memory Activity

Thread Activity

Network Activity

File Activity

```

등을 연결해 볼 수 있다.

---

# 52. Process Tree 분석

EDR에서 매우 중요한 정보 중 하나가 Process Tree이다.

예를 들어

```
explorer.exe
      │
      └── chrome.exe

```

는 흔히 볼 수 있는 정상 실행 구조일 수 있다.

반면

```
winword.exe
     │
     └── powershell.exe
              │
              └── unknown.exe

```

는 환경과 상황에 따라 더 면밀한 확인이 필요한 구조가 될 수 있다.

Process Injection에서는 새로운 Process가 나타나지 않더라도

```
Process A

→

Process B에 비정상적인 Access

```

관계를 추적하는 것이 중요하다.

---

# 53. Process Injection 방어의 핵심

Process Injection 방어는 하나의 기술로 이루어지는 것이 아니다.

여러 보호 계층이 동시에 적용된다.

```
                  Process Injection

                         │

        ┌────────────────┼────────────────┐

        │                │                │

Process Monitoring   Memory Monitoring   Thread Monitoring

        │                │                │

        └────────────────┼────────────────┘

                         │

                Behavior Correlation

                         │

                   Risk Analysis

                         │

             ┌───────────┴───────────┐

             │                       │

           Allow                   Block
                                     │
                                Alert / Kill

```

---

# 54. 공격과 방어의 핵심 차이

공격자는 다음과 같은 목표를 가진다.

```
정상 Process처럼 보이기

Cross-Process Activity 줄이기

새로운 Process 생성을 줄이기

Memory 흔적 줄이기

정상 실행 흐름 이용하기

```

반면 방어자는 다음을 찾는다.

```
비정상 Process 관계

비정상 Memory

비정상 Thread

비정상 Module

비정상 Call Stack

Disk와 Memory의 차이

```

결국 양쪽은

```
Process의 정상적인 상태가 무엇인가?

```

라는 문제를 두고 경쟁한다고 볼 수 있다.

---

# 55. 프로세스 이름만으로 판단할 수 없는 이유

explorer.exe가 실행되고 있다고 가정해 보자.

단순히 Process 목록만 보면

```
explorer.exe

```

라는 정상적인 이름만 확인할 수 있다.

하지만 실제로는 다음과 같은 상태가 존재할 수도 있다.

```
explorer.exe

├── Normal Module
├── Normal Thread
├── Normal Memory
│
└── Abnormal Memory
        │
        └── Unexpected Execution

```

따라서 현대 Endpoint Security에서는

```
Process Name

```

보다

```
Process 내부 상태

+

Process 행동

```

이 훨씬 중요하다.

---

# 56. 가장 중요한 개념: Code와 Identity의 분리

Process Injection을 공부하면서 가장 중요하게 볼 수 있는 개념은

**실행 중인 코드와 프로세스의 Identity가 반드시 일치하지 않을 수 있다는 것**이다.

일반적으로 사람은

```
chrome.exe → Chrome Code

explorer.exe → Windows Explorer Code

```

라고 생각한다.

하지만 Process Injection이 발생하면

```
explorer.exe

├── Explorer Code
│
└── Injected Code

```

처럼 하나의 프로세스 안에서 서로 다른 출처의 코드가 실행될 수 있다.

따라서 보안 제품에서는

```
누가 실행되고 있는가?

```

뿐만 아니라

```
어떤 코드가

어떤 메모리에서

어떤 경로를 통해

어떤 Thread에서

실행되고 있는가?

```

를 분석해야 한다.

---

# 57. 프로세스 인젝션 기법 비교

기법핵심 특징

| DLL Injection          | 대상 Process가 외부 DLL을 로드하도록 함               |
| ---------------------- | ----------------------------------------- |
| APC Injection          | Thread의 APC Queue를 이용                     |
| Thread Hijacking       | 기존 Thread의 실행 Context 변경                  |
| Process Hollowing      | 정상 Process의 Memory Image를 변경              |
| PE Injection           | PE 데이터를 다른 Process에서 실행                   |
| Reflective DLL Loading | Windows Loader 의존도를 줄여 DLL을 Memory에서 Load |
| Manual Mapping         | PE 구조를 직접 Memory에 구성                      |
| Early Bird APC         | Process 초기 Thread에서 APC 실행                |
| Module Stomping        | 기존 정상 Module Memory를 변경                   |
| Process Doppelgänging  | Process 생성 구조의 특성을 악용                     |

중요한 점은 각각의 세부 구현 방법보다

```
Target Process 상태 변경

+

비정상적인 Code Execution

```

이라는 공통적인 특징이다.

---

# 58. 백신이 보는 주요 Indicators

Process Injection 탐지에서 중요한 Indicator를 정리하면 다음과 같다.

분류주요 관찰 대상

| Process   | 비정상 Process 관계            |
| --------- | ------------------------- |
| Handle    | 다른 Process에 대한 높은 접근 권한   |
| Memory    | Remote Memory Write       |
| Memory    | Executable Private Memory |
| Memory    | RWX Memory                |
| Memory    | Permission Change         |
| Thread    | Remote/Unexpected Thread  |
| Thread    | Abnormal Start Address    |
| Thread    | Context Modification      |
| Module    | 비정상 DLL Load              |
| Module    | Disk와 Memory 불일치          |
| Execution | 비정상 Call Stack            |
| Behavior  | 여러 의심 행동의 연속 발생           |

따라서

```
Process Injection Detection

```

은 실제로는

```
Process
+
Memory
+
Thread
+
Module
+
Execution
+
Behavior

```

을 함께 분석하는 문제이다.

# 59. 탐지와 차단은 다른 개념이다

보안 프로그램의 동작을 이해할 때 Detection과 Prevention을 구분해야 한다.

### Detection

```
의심 행동 발견
     ↓
Alert 생성

```

### Prevention

```
의심 행동 발견
     ↓
행동 차단
     ↓
Process 종료

```

즉 어떤 보안 프로그램이 Process Injection을 탐지하더라도 반드시 즉시 Process를 종료하는 것은 아니다.

제품 정책과 위험도에 따라

```
Monitor

Alert

Block

Terminate

Quarantine

Rollback

```

등 서로 다른 대응이 가능하다.

---

# 60. 왜 Process Injection을 100% 차단하기 어려운가

Process Injection에 이용되는 많은 기능이 Windows의 정상 기능이기 때문이다.

```
Process Memory Access

Thread Manipulation

DLL Loading

Debugging

Memory Allocation

```

자체를 전부 막으면 정상 프로그램도 제대로 동작하지 않을 수 있다.

따라서 방어자는

```
정상 행동

vs

악성 행동

```

을 구분해야 한다.

이 문제 때문에 Process Injection 방어는 단순한 Blacklist 방식보다 Behavior Analysis가 중요하다.

---

# 61. False Positive 문제

보안 제품이 너무 민감하면 정상 프로그램을 공격으로 판단할 수 있다.

이를 False Positive라고 한다.

예를 들어

```
Debugger

Monitoring Tool

Game Anti-Cheat

Security Software

```

역시 다른 프로세스의 Memory나 Thread에 접근할 수 있다.

따라서

```
Remote Memory Access 발견
        ↓
무조건 Block

```

같은 정책은 현실적으로 어렵다.

결국

```
Process Reputation

Digital Signature

Parent Process

Target Process

Access Rights

Memory Behavior

Thread Behavior

후속 Behavior

```

등을 종합해야 한다.

# 62. 최종적으로 정리한 백신의 인젝션 방지 구조

프로세스 인젝션 방어를 전체적으로 정리하면 다음과 같다.

```
              실행 파일 분석
                    │
           Signature / Reputation
                    │
                    ▼
                Process 실행
                    │
          ┌─────────┼─────────┐
          │         │         │
       Handle     Memory    Thread
       Monitor    Monitor   Monitor
          │         │         │
          └─────────┼─────────┘
                    │
             Module Monitoring
                    │
                    ▼
            Behavior Correlation
                    │
                    ▼
               Risk Scoring
                    │
          ┌─────────┴─────────┐
          │                   │
        Normal             Suspicious
          │                   │
        Allow             Alert / Block

```

즉 현대의 백신과 EDR은

```
"Process Injection API를 사용했는가?"

```

하나만 확인하는 것이 아니다.

실제로는

```
어떤 Process가

어떤 Process를 대상으로

어떤 권한을 얻었으며

어떤 Memory를 변경했고

어떤 Thread가

어느 Memory에서

어떠한 Code를 실행했으며

그 이후 어떤 행동을 했는가

```

라는 전체적인 Context를 분석한다고 볼 수 있다.

# 63. 결론

프로세스 인젝션은 다른 프로세스의 주소 공간이나 실행 흐름을 이용하여 코드를 실행하는 기술이다.

DLL Injection, APC Injection, Thread Hijacking, Process Hollowing,

Reflective DLL Loading, Manual Mapping 등 다양한 기법이 존재하지만 모든 기법은 본질적으로

```
Target Process의 상태를 변경하여

원래 존재하지 않았던 Code Execution을 발생시킨다.

```

라는 공통점을 가지고 있다.

초기 백신에서는 악성 파일의 Signature를 찾는 방식이 중요한 역할을 했다.

하지만 Process Injection과 같은 기술이 발전하면서 파일 자체만 분석하는 방식에는 한계가 발생했다.

따라서 현대의 Endpoint Security에서는

```
Process Monitoring

Memory Monitoring

Thread Monitoring

Module Monitoring

Call Stack Analysis

Behavior Correlation

Memory Scanning

Exploit Protection

```

등 여러 보호 기술을 결합한다.

특히 Process Injection 방어에서 가장 중요한 부분은 **Cross-Process Behavior**이다.

정상 프로그램에서도 다른 프로세스에 접근하는 경우가 존재하기 때문에

단순히 하나의 API나 하나의 이벤트를 기준으로 차단하는 것은 어렵다.

따라서 여러 행동을 시간 순서와 관계성에 따라 분석해야 한다.

최종적으로 Process Injection과 이에 대한 방어 기술을 다음과 같이 정리할 수 있다.

```
공격자

정상 Process의 Identity를 이용하여
비정상 Code를 실행하려고 한다.

            ↕

방어자

Process 내부의 Memory,
Thread, Module, Execution Flow를 분석하여
정상 Process 안에 존재하는 비정상 Code를 찾으려고 한다.

```

결국 프로세스 인젝션 방어의 핵심은 단순히

**“어떤 프로세스가 실행되고 있는가” **를 확인하는 것이 아니라,

**“그 프로세스 내부에서 실제로 어떤 코드가 어떤 메모리와 어떤 실행 흐름을 통해 동작하고 있는가”**

를 파악하는 것이라고 정리할 수 있다.
