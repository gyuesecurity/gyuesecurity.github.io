# EIP-2612 분석, 서명만으로 ERC-20 Approve를 처리하는 Permit

## 1. 들어가며

이전 ERC-20 글에서는 Ethereum에서 Fungible Token을 어떻게 표준화했는지 살펴보았다.

ERC-20에서 특히 중요했던 기능 중 하나가 approve()였다.

사용자가 DEX와 같은 스마트 컨트랙트에 자신의 토큰을 사용하도록 허용하려면 먼저 다음과 같은 Transaction을 실행해야 한다.

```
token.approve(spender, amount);

```

그리고 승인된 Contract는

```
token.transferFrom(
    user,
    receiver,
    amount
);

```

을 이용하여 사용자의 Token을 이동할 수 있다.

구조 자체는 간단하지만 실제 서비스를 사용하는 입장에서 보면 한 가지 불편한 점이 있다.

사용자가 원하는 것은 Token Swap 한 번인데 실제로는

```
1. approve()
2. swap()

```

두 단계가 필요할 수 있다는 것이다.

특히 approve() 자체도 Ethereum Transaction이기 때문에 Gas가 필요하다.

이러한 ERC-20의 승인 방식을 개선하기 위해 등장한 것이 **EIP-2612 Permit**이다.

EIP-2612에서는 사용자가 직접 approve() Transaction을 실행하는 대신

**Off-chain Signature를 생성하여 Token 사용 권한을 부여할 수 있도록 한다.**

이번 글에서는 EIP-2612가 왜 등장했는지부터 시작해서 permit(), EIP-712 Signature, nonce, deadline, DOMAIN_SEPARATOR가 어떤 역할을 하는지 살펴보고 보안 관점에서 Replay Attack을 어떻게 방지하는지도 정리해보았다.

---

# 2. 기존 ERC-20 Approve의 구조

먼저 기존 ERC-20의 Token 승인 구조를 다시 살펴보자.

Alice가 DEX에서 100 Token을 사용하고 싶다고 가정한다.

먼저 Alice는 DEX에 Token 사용 권한을 부여해야 한다.

```
token.approve(
    DEX,
    100
);

```

그러면 Token Contract 내부에는 개념적으로 다음과 같은 상태가 저장된다.

```
allowance[Alice][DEX] = 100

```

DEX는 이후 다음 함수를 사용할 수 있다.

```
token.transferFrom(
    Alice,
    DEX,
    100
);

```

전체 흐름을 정리하면 다음과 같다.

```
Alice
  │
  │ Transaction 1
  │ approve(DEX, 100)
  ▼
ERC-20 Token
  │
  │ allowance = 100
  ▼
DEX

Alice
  │
  │ Transaction 2
  │ swap()
  ▼
DEX
  │
  │ transferFrom()
  ▼
ERC-20 Token

```

여기서 중요한 것은 approve()가 별도의 Transaction이라는 점이다.

---

# 3. 기존 방식의 문제점

사용자 입장에서 하고 싶은 것은 단순히 Token을 Swap하는 것이다.

하지만 실제로는

```
approve()
   ↓
swap()

```

두 개의 Transaction을 처리해야 할 수 있다.

Ethereum Transaction을 발생시키려면 Gas가 필요하다.

즉 Token을 가지고 있더라도 Gas 비용으로 사용할 ETH가 없다면

approve() Transaction을 실행하지 못하는 상황이 발생할 수 있다.

이를 단순화하면 다음과 같다.

```
User

ERC-20 Token : 있음
ETH          : 없음

        ↓

approve() 실행 필요

        ↓

Gas 비용을 지불할 ETH 없음

```

이 문제에서 중요한 부분은 Token 사용을 허용한다는 행위 자체를

반드시 Token 소유자가 On-chain Transaction으로 실행해야 하는가?라는 것이다.

Token 소유자는 Private Key를 가지고 있다.

그렇다면 Private Key로 DEX가 내 Token 100개를 사용하도록 허용한다.

라는 메시지에 서명하고, 다른 사람이 이 서명을 Blockchain에 제출하는 방식도 생각할 수 있다.

이 아이디어가 EIP-2612의 핵심이다.

---

# 4. EIP-2612란?

EIP-2612는 기존 ERC-20에 permit()이라는 기능을 추가한다.

핵심적인 차이는 다음과 같다.

기존 ERC-20:

```
User
 │
 │ On-chain Transaction
 ▼
approve()
 │
 ▼
Allowance 변경

```

EIP-2612:

```
User
 │
 │ Off-chain Signature
 ▼
Signature
 │
 │ 다른 주소가 제출 가능
 ▼
permit()
 │
 ▼
Allowance 변경

```

즉 사용자가 직접 approve() Transaction을 보내는 대신 **서명된 메시지를 통해 allowance를 변경할 수 있다.**

---

# 5. permit()

EIP-2612의 핵심 함수는 다음과 같다.

```
permit(
    address owner,
    address spender,
    uint256 value,
    uint256 deadline,
    uint8 v,
    bytes32 r,
    bytes32 s
)

```

각 값의 의미를 살펴보면 다음과 같다.

Parameter                                    의미

| owner    | Token 소유자            |
| -------- | -------------------- |
| spender  | Token 사용 권한을 받을 주소   |
| value    | 승인할 Token 수량         |
| deadline | Signature 만료 시간      |
| v, r, s  | owner가 생성한 Signature |

예를 들어 Alice가 DEX에 100 Token 사용 권한을 부여하려고 한다.

개념적으로 Alice는 다음 정보를 서명한다.

```
Owner    : Alice
Spender  : DEX
Value    : 100
Nonce    : 0
Deadline : 1800000000

```

그리고 생성된 Signature를 이용하여 permit()을 호출한다.

정상적인 Signature라면

```
allowance[Alice][DEX]

```

가 100으로 변경된다.

---

# 6. 중요한 차이, 서명은 Transaction이 아니다

여기서 가장 중요한 부분이다.

Wallet에서 메시지에 Signature를 생성하는 것과 Ethereum Transaction을 전송하는 것은 다르다.

Transaction은 Blockchain에 기록되며 Gas를 소비한다.

```
Transaction

Wallet
  ↓
Ethereum Network
  ↓
Validator
  ↓
Blockchain

Gas 필요

```

반면 메시지 Signing은 기본적으로 사용자의 Wallet에서 이루어진다.

```
Signature

Message
   +
Private Key
   ↓
Signature

```

이 과정 자체는 Blockchain Transaction이 아니다.

따라서 사용자가 메시지를 서명하는 것 자체에는 Ethereum Transaction Gas가 필요하지 않는다.

이러한 특성을 이용하여 Token 사용 권한을 Signature로 표현하는 것이 EIP-2612이다.

---

# 7. Permit 전체 동작 과정

Alice가 DEX에서 Token을 사용한다고 가정해보자.

먼저 Alice의 Wallet이 Permit 데이터를 만든다.

```
Owner    = Alice
Spender  = DEX
Value    = 100
Nonce    = 0
Deadline = ...

```

Alice는 자신의 Private Key로 해당 데이터에 서명한다.

```
Permit Data
     │
     │ Sign
     ▼
Alice Private Key
     │
     ▼
Signature

```

이 Signature를 DEX 또는 다른 Relayer가 전달받을 수 있다.

```
Alice
 │
 │ Signature
 ▼
DEX / Relayer

```

그리고 해당 주체가 Token Contract의

```
permit(...)

```

을 실행한다.

Token Contract는 Signature가 실제 Alice가 생성한 것인지 검증한다.

정상적인 경우

```
allowance[Alice][DEX] = 100

```

으로 변경된다.

---

# 8. 그렇다면 아무나 permit을 제출해도 되는가?

처음에는 이 부분이 이상하게 느껴졌다.

Alice가 Signature를 만들었는데 Bob이 해당 Signature를 가지고 permit()을 호출하면 어떻게 될까?

EIP-2612에서는 **permit Transaction을 누가 제출하는지는 핵심이 아니다.**

중요한 것은 Signature가 실제 owner가 생성한 것인지다.

```
Bob
 │
 │ Alice Signature
 ▼
permit()
 │
 ▼
Token Contract
 │
 │ Signature 검증
 ▼
Alice가 실제 서명했는가?

```

Signature가 정상이라면 Bob이 Transaction을 제출해도 Alice가 지정한 allowance가 설정될 수 있다.

Bob이 Signature 내용을 마음대로 수정하면 Signature 검증이 실패한다.

---

# 9. 그런데 Signature를 재사용하면 어떻게 될까?

여기서 중요한 보안 문제가 발생한다.

Alice가 다음 메시지를 서명했다고 생각해보자.

```
Alice → DEX

100 Token 사용 허용

```

공격자가 이 Signature를 얻었다고 가정한다.

만약 아무런 Replay Protection이 없다면 동일한 Signature를 반복해서 사용할 가능성이 생긴다.

```
Signature
   │
   ├── permit()
   ├── permit()
   ├── permit()
   └── permit()

```

이러한 문제를 방지하기 위해 EIP-2612에는 **nonce**가 존재한다.

---

# 10. Nonce

EIP-2612에는 다음 함수가 있다.

```
nonces(address owner)

```

각 owner마다 현재 nonce 값을 관리한다.

예를 들어 Alice의 현재 nonce가 0이라고 가정한다.

Alice가 다음 데이터를 서명한다.

```
Owner   : Alice
Spender : DEX
Value   : 100
Nonce   : 0

```

Signature가 성공적으로 사용되면 Alice의 nonce가 증가한다.

```
Before

nonces[Alice] = 0

       ↓

permit()

       ↓

After

nonces[Alice] = 1

```

공격자가 기존 Signature를 다시 제출하면 기존 Signature에는

```
nonce = 0

```

이 포함되어 있다.

하지만 현재 Contract 상태는

```
nonce = 1

```

이다.

따라서 기존 Signature를 다시 사용할 수 없다.

---

# 11. Replay Attack 방지

Nonce가 없다면 다음과 같은 상황이 가능할 수 있다.

```
Alice Signature

"DEX에게 100 Token 승인"

        │
        ├── 사용
        ├── 다시 사용
        ├── 다시 사용
        └── 다시 사용

```

Nonce를 포함하면

```
Permit #1

nonce = 0
    ↓
사용 성공
    ↓
nonce = 1

```

이 된다.

기존 Signature는

```
nonce = 0

```

을 대상으로 생성되었으므로 다시 사용할 수 없다.

즉 Nonce는 **동일한 Permit Signature의 재사용을 방지하는 역할**을 한다.

---

# 12. Deadline은 왜 필요할까?

EIP-2612에는 또 하나 중요한 값이 있다.

```
deadline

```

Signature의 유효기간이다.

예를 들어 Alice가 오늘 DEX 사용을 위해 Permit Signature를 만들었다고 생각해보자.

그런데 해당 Signature가 몇 년 뒤에도 사용할 수 있다면 보안상 좋지 않다.

따라서

```
현재 시간 < deadline

```

일 때만 Signature를 허용하도록 한다.

예를 들어

```
Signature 생성

        ↓

Valid
Valid
Valid

        ↓

Deadline

        ↓

Expired

```

와 같은 구조가 된다.

따라서 Signature가 유출되더라도 유효 기간이 지나면 사용할 수 없다.

---

# 13. EIP-712

EIP-2612를 이해하려면 **EIP-712**도 알아야 한다.

단순히 문자열을 서명한다고 생각하면 사용자가 자신이 무엇에 서명하는지 이해하기 어려울 수 있다.

예를 들어 Wallet에 다음과 같은 값만 나타난다면

```
0x8f19d4a98c...

```

사용자는 자신이 무엇을 승인하고 있는지 알기 어렵다.

EIP-712는 **Typed Structured Data Signing**을 정의한다.

Permit 데이터는 개념적으로 다음처럼 구조화할 수 있다.

```
Permit

owner    : 0xAlice...
spender  : 0xDEX...
value    : 100
nonce    : 0
deadline : ...

```

이를 통해 구조화된 데이터를 대상으로 Signature를 생성한다.

---

# 14. Permit 구조체

EIP-2612에서 Permit의 핵심 데이터 구조는 개념적으로 다음과 같다.

```
Permit(
    address owner,
    address spender,
    uint256 value,
    uint256 nonce,
    uint256 deadline
)

```

여기서 다시 보면 모든 값에 이유가 있다.

```
owner
 └─ 누가 승인하는가?

spender
 └─ 누구에게 권한을 주는가?

value
 └─ 얼마를 승인하는가?

nonce
 └─ Signature 재사용 방지

deadline
 └─ Signature 유효기간

```

---

# 15. DOMAIN_SEPARATOR

EIP-2612에서 상당히 중요한 또 하나의 개념이

```
DOMAIN_SEPARATOR()

```

이다.

처음에는 왜 Signature에 Domain이 필요한지 이해하기 어려웠다.

Signature가 특정 Contract에서 사용하도록 만들어졌는데

동일한 Signature가 다른 Contract에서도 유효해진다면 문제가 발생할 수 있다.

예를 들어

```
Token Contract A

Alice Permit Signature

```

를

```
Token Contract B

```

에서도 그대로 사용할 수 있다면 예상하지 못한 권한 승인이 발생할 가능성이 있다.

따라서 Signature가 **어떤 Domain에 속하는지 구분할 필요가 있다.**

---

# 16. Domain에는 어떤 정보가 들어갈까?

EIP-712 Domain은 일반적으로 다음과 같은 정보를 이용할 수 있다.

```
name
version
chainId
verifyingContract

```

예를 들면

```
name              = MyToken
version           = 1
chainId           = 1
verifyingContract = 0x1234...

```

같은 구조다.

이를 통해 Signature가

```
어떤 Token Contract를 위한 것인지

어떤 Chain을 위한 것인지

```

등을 구분할 수 있다.

---

# 17. Cross-Contract Replay 방지

Domain이 없다면 개념적으로

```
Signature
   │
   ├── Contract A
   ├── Contract B
   └── Contract C

```

와 같은 문제가 발생할 여지가 있다.

Domain을 포함하면

```
Signature

Chain ID : 1
Contract : Token A

        ↓

Token A에서는 검증 성공

Token B에서는 Domain 불일치

```

와 같은 방식으로 Signature의 사용 범위를 제한할 수 있다.

따라서 DOMAIN_SEPARATOR 역시 Signature 기반 시스템에서 중요한 Replay Protection 요소다.

---

# 18. Permit Signature는 어떻게 검증할까?

Ethereum의 일반적인 EOA Signature에서는 ecrecover를 이용하여 Signature에서 signer 주소를 복구할 수 있다.

개념적으로는 다음과 같다.

```
Permit Data
     │
     ▼
Hash
     │
     + Signature
     │
     ▼
ecrecover()
     │
     ▼
Signer Address

```

그리고

```
Signer Address == owner

```

인지 확인한다.

일치하면 실제 Token owner가 생성한 Signature라고 판단할 수 있다.

OpenZeppelin 같은 검증된 구현에서는 Signature 검증과

EIP-712 처리 등을 직접 처음부터 구현하지 않고 관련 라이브러리와 구현을 사용할 수 있다.

---

# 19. EIP-2612의 핵심 보안 구조

지금까지 살펴본 내용을 정리하면 EIP-2612에는 여러 보호 장치가 존재한다.

```
Signature
   │
   ├── owner
   ├── spender
   ├── value
   │
   ├── nonce
   │      └─ Replay Attack 방지
   │
   ├── deadline
   │      └─ 오래된 Signature 사용 제한
   │
   └── DOMAIN_SEPARATOR
          └─ Domain 구분

```

이 구조를 보고 나니 Signature 기반 인증에서 단순히

```
Signature가 맞는가?

```

만 확인하면 되는 것이 아니라는 것을 알 수 있었다.

Signature가

```
누구의 것인지
무엇을 승인했는지
언제까지 유효한지
이미 사용된 것인지
어떤 Contract와 Chain을 위한 것인지

```

까지 함께 검증해야 한다.

---

# 20. OpenZeppelin으로 ERC20Permit 구현하기

EIP-2612를 처음부터 직접 구현할 수도 있지만 실제 개발에서는 OpenZeppelin의 구현을 사용할 수 있다.

간단한 Token을 만들어보면 다음과 같다.

```
// SPDX-License-Identifier: MIT

pragma solidity ^0.8.20;

import {
    ERC20
} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";

import {
    ERC20Permit
} from "@openzeppelin/contracts/token/ERC20/extensions/ERC20Permit.sol";

contract MyToken is ERC20, ERC20Permit {

    constructor()
        ERC20("MyToken", "MTK")
        ERC20Permit("MyToken")
    {
        _mint(
            msg.sender,
            1_000_000 ether
        );
    }
}

```

기존 ERC-20에

```
ERC20Permit

```

을 추가했다.

이를 통해 Token에서 EIP-2612 Permit 기능을 사용할 수 있다.

---

# 21. ERC20Permit에서 사용할 수 있는 기능

ERC20Permit을 적용하면 대표적으로 다음 기능을 사용할 수 있다.

```
permit()

nonces()

DOMAIN_SEPARATOR()

```

즉

```
기존 ERC-20
│
├── transfer()
├── approve()
├── transferFrom()
└── allowance()

        +

ERC20Permit
│
├── permit()
├── nonces()
└── DOMAIN_SEPARATOR()

```

와 같은 구조가 된다.

중요한 점은 EIP-2612가 ERC-20을 완전히 대체하는 것이 아니라

**ERC-20에 Signature 기반 Approval 기능을 확장하는 것**이라는 점이다.

---

# 22. 기존 Approve와 Permit 비교

두 방식을 비교하면 차이가 명확하다.

항목                                                     approve                                                      permit

| 방식                | On-chain Transaction | Off-chain Signature |
| ----------------- | -------------------- | ------------------- |
| Token owner의 Gas  | 필요                   | 서명 자체에는 필요 없음       |
| Private Key 사용    | Transaction 서명       | Typed Data 서명       |
| Allowance 설정      | 가능                   | 가능                  |
| Replay Protection | Transaction nonce    | Permit nonce        |
| 만료 시간             | 기본 approve에는 없음      | deadline            |
| EIP-712           | 필요 없음                | 사용                  |

기존 방식은

```
User
  │
  │ Transaction
  ▼
approve()

```

이고 Permit 방식은

```
User
  │
  │ Signature
  ▼
Relayer / DApp
  │
  │ Transaction
  ▼
permit()

```

이다.

---

# 23. Permit을 이용한 DEX 흐름

기존 DEX 사용 흐름은 다음과 같을 수 있다.

```
User

 │
 │ approve()
 ▼

Token Contract

 │
 │ allowance
 ▼

DEX

 │
 │ swap()
 ▼

Swap 실행

```

Permit을 지원하는 Token에서는 DApp이 Signature를 받아 이를 다른 작업과 결합하는 구조를 만들 수 있다.

```
User
 │
 │ Permit Signature
 ▼
DEX / Router
 │
 ├── permit()
 │
 └── swap()
 ▼
Token Contract

```

사용자는 별도의 Approval Transaction을 직접 제출하지 않고 Signature를 통해 Token 사용 권한을 표현할 수 있다.

---

# 24. Permit이라고 Gas가 사라지는 것은 아니다

여기서 한 가지 주의할 점이 있다.

EIP-2612를 흔히 **Gasless Approval**이라고 표현하지만

Blockchain 상태를 변경하는 permit() 실행 자체가 계산 없이 이루어지는 것은 아니다.

사용자가 Signature를 만드는 과정이 Off-chain이기 때문에

**Token owner가 approve Transaction을 직접 보내고 Gas를 지불할 필요가 없다는 의미**에 가깝다.

결국 누군가는 Signature를 Blockchain에 제출해야 한다.

```
User

Signature 생성
Gas X

      ↓

Relayer / DApp

permit() Transaction
Gas O

```

즉 Gas 비용 자체가 마법처럼 사라지는 것이 아니라

**Gas를 지불하는 주체와 Transaction 흐름을 다르게 설계할 수 있게 되는 것**이다.

---

# 25. 보안 관점 — Signature Phishing

EIP-2612를 공부하면서 가장 중요하다고 느낀 부분이다.

Permit은 Transaction이 아니라 Signature를 사용한다.

사용자 입장에서는

```
Transaction 전송이 아니네?
Gas도 안 드네?

```

라고 생각하면서 Signature 요청을 상대적으로 가볍게 승인할 수도 있다.

하지만 Permit Signature는 실제 Token 사용 권한을 부여할 수 있다.

예를 들어 악성 사이트가

```
spender = attacker
value   = 매우 큰 값

```

을 포함한 Permit을 사용자에게 서명하도록 유도한다면 문제가 발생할 수 있다.

따라서

```
Sign ≠ 항상 안전

```

이다.

Signature도 자산에 대한 중요한 권한을 표현할 수 있다.

---

# 26. 보안 관점 — Nonce 검증

Permit을 직접 구현한다면 Nonce 관리가 특히 중요하다.

잘못된 구현으로

```
Signature 사용

       ↓

Nonce 증가 안 함

```

과 같은 상황이 발생한다면 동일 Signature를 반복 사용할 가능성이 생긴다.

정상적인 구조에서는

```
Nonce 0
 │
 │ Permit 사용
 ▼
Nonce 1

```

이 되어야 한다.

따라서 Signature 기반 기능을 분석할 때는

```
Nonce가 존재하는가?

Signature 사용 후 증가하는가?

Nonce가 Signature 데이터에 포함되는가?

```

를 확인할 필요가 있다.

---

# 27. 보안 관점 — Deadline 검증

Deadline 역시 단순히 데이터에 포함시키는 것만으로는 충분하지 않다.

Contract에서 실제로

```
block.timestamp <= deadline

```

과 같은 유효성 검사가 이루어져야 한다.

그렇지 않다면 Signature에 deadline 필드가 존재하더라도 오래된 Signature를 계속 사용할 수 있게 된다.

따라서 Permit 구현을 분석한다면

```
Signature 검증

Nonce 검증

Deadline 검증

Domain 검증

```

을 함께 확인하는 것이 중요하다.

---

# 28. 보안 관점 — Permit Front-running

Permit은 유효한 Signature를 가지고 있다면 특정 사용자만 제출해야 하는 구조가 아니다.

따라서 Signature가 공개된 이후 다른 사람이 먼저 해당 Permit을 제출할 수도 있다.

그렇다고 해서 공격자가 Signature 내용을 마음대로 바꿀 수 있는 것은 아니다.

하지만 Protocol에서

```
permit() 성공

      ↓

다음 로직 실행

```

을 강하게 전제로 만들어버리면 이미 Permit이 사용된 경우 예상치 못한 문제가 발생할 수 있다.

따라서 Permit을 사용하는 Protocol에서는 Permit 호출 실패 가능성과

이미 적용된 allowance 상태 등을 고려하여 설계할 필요가 있다.

---

# 29. Permit과 Permit2는 같은 것일까?

EIP-2612를 검색하다 보면 **Permit2**라는 이름도 자주 등장한다.

처음에는 EIP-2612의 다음 버전이라고 생각했지만 서로 구분할 필요가 있다.

EIP-2612는 **Token Contract 자체가 permit()을 구현해야 한다.**

```
ERC-20 Token
     │
     └── permit()

```

즉 기존 Token이 EIP-2612를 구현하지 않았다면 바로 사용할 수 없다.

Permit2는 별도의 Token Approval Contract를 이용하는 방식이다.

개념적으로

```
ERC-20 Token
      │
      │ approve
      ▼
   Permit2
      │
      │ Signature 기반 권한
      ▼
     DApp

```

과 같은 구조를 사용할 수 있다.

따라서 EIP-2612와 Permit2는 Signature 기반 Token Approval이라는 비슷한 문제를 다루지만 동일한 것은 아니다.

---

# 30. 실제 사용 사례 — Uniswap Permit2와 비교해보기

Signature 기반 Token 권한 관리가 실제 서비스에서 어떻게 발전했는지

살펴볼 수 있는 좋은 사례가 Uniswap의 Permit2다.

EIP-2612는 Token Contract가 직접 permit()을 구현해야 한다.

하지만 모든 ERC-20 Token이 EIP-2612를 구현하고 있는 것은 아니다.

Permit2는 별도의 Contract를 두어 이러한 문제를 다른 방식으로 해결한다.

사용자는 Token Contract에서 Permit2 Contract에 대한 Approval을 설정한 뒤,

이후 세부적인 권한을 Signature를 통해 관리할 수 있다.

```
User
 │
 │ 최초 Approval
 ▼
ERC-20
 │
 ▼
Permit2
 │
 │ Signature
 ▼
DApp

```

이를 보면서 ERC-20의 단순한 approve() 구조에서 시작해 EIP-2612와

Permit2처럼 사용자 경험과 권한 관리 방식을 개선하려는 시도가 계속 이어지고 있다는 것을 알 수 있었다.

---

# 31. EIP-2612를 공부하면서 이해한 점

처음에는 EIP-2612를 단순히 approve를 Signature로 바꾼 것 정도로 생각했다.

하지만 자세히 살펴보니 중요한 부분은 Signature 자체보다

**Signature를 안전하게 권한으로 사용하는 방법**에 있었다.

단순히

```
Alice가 서명했다.

```

만 확인해서는 충분하지 않았다.

다음과 같은 정보가 모두 필요했다.

```
누가 서명했는가?
      ↓
owner

누구에게 권한을 주는가?
      ↓
spender

얼마를 허용하는가?
      ↓
value

이미 사용된 Signature인가?
      ↓
nonce

언제까지 사용할 수 있는가?
      ↓
deadline

어떤 Contract를 위한 Signature인가?
      ↓
DOMAIN_SEPARATOR

```

특히 nonce, deadline, DOMAIN_SEPARATOR가 각각 다른 형태의 Replay 문제를 막기 위한 중요한 요소라는 점이 흥미로웠다.

ERC-20의 approve()만 공부했을 때는 단순히 Token 사용 권한을 부여하는 기능이라고 생각했는데 EIP-2612까지 공부하면서 **Blockchain에서 Signature 자체가 하나의 권한으로 사용될 수 있다**는 점을 이해할 수 있었다.

---

# 32. 정리

EIP-2612의 주요 내용을 정리하면 다음과 같다.

항목                                                                          역할

| permit()         | Signature를 이용한 Allowance 설정 |
| ---------------- | --------------------------- |
| owner            | Token 소유자                   |
| spender          | Token 사용 권한을 받을 주소          |
| value            | 승인할 Token 수량                |
| nonce            | Signature Replay 방지         |
| deadline         | Signature 만료 시간             |
| DOMAIN_SEPARATOR | Signature Domain 구분         |
| EIP-712          | Structured Data Signing     |
| v, r, s          | ECDSA Signature             |

전체 흐름은 다음과 같이 정리할 수 있다.

```
ERC-20

approve()
   │
   │ On-chain Transaction
   ▼
Allowance


EIP-2612

Permit Data
   │
   │ EIP-712 Signing
   ▼
Signature
   │
   │ permit()
   ▼
Signature Verification
   │
   ├── owner
   ├── nonce
   ├── deadline
   └── domain
   │
   ▼
Allowance

```

결국 EIP-2612는 ERC-20을 대체하는 새로운 Token 표준이라기보다

**ERC-20의 Approval 방식을 Signature 기반으로 확장한 표준**이라고 볼 수 있다.

ERC-20을 공부하면서 approve()가 왜 필요한지를 이해했다면 EIP-2612에서는 한 단계 더 나아가

꼭 Token 소유자가 직접 Approval Transaction을 전송해야 하는가? 라는 문제를 해결하는 방식을 볼 수 있었다.

그리고 이 과정에서 EIP-712, Nonce, Deadline, Domain Separator 등

Blockchain의 Signature 기반 인증에서 중요한 보안 개념들도 함께 이해할 수 있었다.

다음 글에서는 Token 표준에서 잠시 벗어나 Ethereum Transaction의 수수료 구조를 크게 변경한 **EIP-1559**를 살펴보려고 한다.
