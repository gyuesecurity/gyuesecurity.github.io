# ERC란 무엇인가? — 이더리움 표준을 이해해보자

## 1. 들어가며

Ethereum과 Smart Contract를 공부하다 보면 굉장히 자주 접하게 되는 단어가 있다.

바로 **ERC**다.

대표적으로 다음과 같은 이름들을 많이 볼 수 있다.

```text
ERC-20
ERC-721
ERC-1155
ERC-4626
ERC-4337

```

처음에는 ERC를 단순히

> Ethereum에서 Token을 만드는 규칙

정도로 생각했다.

실제로 ERC-20이나 ERC-721이 워낙 유명하기 때문에 ERC라고 하면 Token Standard부터 떠올리기 쉽다.

하지만 ERC를 조금 더 찾아보니 ERC는 Token에만 사용되는 개념이 아니었다.

Token뿐만 아니라 Smart Contract Interface, NFT, Vault, Account Abstraction 등 **Ethereum Application들이 서로 호환될 수 있도록 만드는 여러 표준과 규칙**이 ERC에 포함될 수 있다.

그리고 ERC를 제대로 이해하려면 먼저 **EIP**가 무엇인지 알아야 한다.

이번 글에서는

```text
EIP란 무엇인가?

ERC란 무엇인가?

EIP와 ERC는 어떤 관계인가?

왜 ERC 같은 표준이 필요한가?

ERC 번호는 무엇을 의미하는가?

대표적인 ERC에는 무엇이 있는가?

```

를 순서대로 정리해보았다.

---

# 2. ERC란 무엇인가?

ERC는 일반적으로 **Ethereum Request for Comments**라고 부른다.

Ethereum 생태계에서 Application Level의 표준과 규칙을 정의하기 위해 사용된다.

대표적인 예가 ERC-20이다.

ERC-20은 Ethereum에서 Fungible Token을 구현할 때 사용할 수 있는 공통 Interface를 정의한다.

예를 들어 ERC-20에는 다음과 같은 함수들이 존재한다.

```solidity
totalSupply()

balanceOf()

transfer()

approve()

allowance()

transferFrom()

```

개발자들이 이 Interface를 기준으로 Token을 구현하면 Wallet이나 DEX 같은 다른 Application도 해당 Token과 정해진 방식으로 상호작용할 수 있다.

하지만 여기서 한 가지 알아둘 점이 있다.

ERC는 EIP와 완전히 별개의 시스템이 아니다.

현재 Ethereum 표준 구조에서 ERC는 **Standards Track EIP의 한 Category**다.

따라서 ERC를 이해하기 위해서는 먼저 EIP를 알아볼 필요가 있다.

---

# 3. EIP란 무엇인가?

EIP는

**Ethereum Improvement Proposal**

의 약자다.

우리말로 표현하면

> Ethereum 개선 제안

정도로 볼 수 있다.

Ethereum에 새로운 기능이나 표준을 추가하거나 기존 구조를 변경하려는 아이디어가 있다고 생각해보자.

단순히

```text
"이 기능 추가하면 좋을 것 같은데?"

```

라고 이야기하는 것만으로 Ethereum 전체에 적용할 수는 없다.

어떤 문제를 해결하려는지, 어떤 방식으로 구현할 것인지, 기존 시스템에는 어떤 영향을 주는지 등을 기술적으로 정리할 필요가 있다.

이러한 제안을 문서화하는 것이 EIP다.

단순화하면

```text
아이디어

   ↓

기술적인 내용 정리

   ↓

EIP 작성

   ↓

커뮤니티 논의 및 검토

   ↓

표준 또는 Network Upgrade 등에 반영

```

과 같은 흐름으로 생각할 수 있다.

---

# 4. EIP에는 무엇이 들어갈까?

EIP는 단순히 아이디어만 적어놓은 문서가 아니다.

일반적으로

```text
어떤 문제가 있는가?

왜 이 변경이 필요한가?

어떤 방식으로 해결할 것인가?

기술적인 Specification은 무엇인가?

보안상 고려할 부분은 무엇인가?

```

등을 설명한다.

실제 EIP 문서를 살펴보면 다음과 같은 항목들을 자주 볼 수 있다.

```text
Abstract

Motivation

Specification

Rationale

Backwards Compatibility

Security Considerations

```

따라서 Smart Contract나 Ethereum 기술을 공부할 때 블로그나 다른 사람의 설명만 보는 것보다 원본 EIP를 같이 확인하면 해당 기능이 **왜 만들어졌고 원래 어떤 동작을 의도했는지** 파악하는 데 도움이 된다.

---

# 5. EIP의 종류

모든 EIP가 같은 종류의 변경을 다루는 것은 아니다.

크게 보면 EIP는 다음과 같은 종류로 나뉜다.

```text
EIP

├── Standards Track
│
├── Meta
│
└── Informational

```

각각을 살펴보았다.

---

# 6. Standards Track

Standards Track은 Ethereum 구현이나 상호운용성 등에 영향을 주는 변경을 다룬다.

그리고 Standards Track 안에서도 다시 여러 Category로 나뉜다.

```text
Standards Track

├── Core
├── Networking
├── Interface
└── ERC

```

여기서 우리가 자주 보는 **ERC가 등장한다.**

즉 구조적으로 보면

```text
EIP
 │
 └── Standards Track
        │
        ├── Core
        ├── Networking
        ├── Interface
        │
        └── ERC

```

라고 이해할 수 있다.

ERC는 EIP와 완전히 별개의 것이 아니라 **EIP 표준 체계 안에 있는 Application Level Standard Category**인 것이다.

---

# 7. Core

Core는 Ethereum Protocol 자체에 영향을 주는 변경을 다룬다.

대표적으로 이전에 공부한 **EIP-1559**가 있다.

EIP-1559는 Ethereum의 Transaction Fee Market을 변경했다.

```text
기존

gasPrice

      ↓

EIP-1559

Base Fee
+
Priority Fee
+
Max Fee

```

이처럼 Ethereum Protocol 자체의 동작에 영향을 주는 변경은 ERC보다는 Core 영역에서 다루게 된다.

따라서

```text
EIP-1559

```

는 ERC-1559라고 부르지 않는다.

---

# 8. Networking

Networking Category는 Ethereum Node 사이의 Network Protocol과 관련된 개선을 다룬다.

예를 들어

```text
Node 간 통신

Network Protocol

devp2p

```

등 Ethereum의 Networking Layer와 관련된 내용이 여기에 포함될 수 있다.

Application 개발자가 ERC-20처럼 자주 직접 다루는 영역은 아니지만 Ethereum 전체 구조에서는 중요한 부분이다.

---

# 9. Interface

Interface Category는 Client API, RPC Specification, ABI 등 Interface와 관련된 표준을 다룬다.

즉 Ethereum Client나 개발 도구가 서로 통신하고 기능을 사용하는 방법을 표준화하는 영역이라고 이해할 수 있다.

---

# 10. ERC

마지막이 이번 글에서 가장 중요한 ERC다.

ERC는 **Application Level의 표준과 규칙**을 다룬다.

대표적으로

```text
Token Standard

NFT Standard

Smart Contract Interface

Vault Standard

Account Abstraction

```

등이 포함될 수 있다.

따라서 ERC를 단순히

```text
ERC = Token Standard

```

라고 생각하면 범위가 너무 좁다.

Token Standard가 ERC에서 굉장히 유명할 뿐 ERC 자체는 더 넓은 Application Level Standard를 다룬다.

---

# 11. Meta EIP

Meta EIP는 Ethereum의 Protocol 기능 자체보다는 **Ethereum을 둘러싼 Process나 절차**와 관련된 내용을 다룬다.

예를 들어

```text
EIP Process

개발 절차

의사결정 절차

Tool 관련 Process

```

등이 해당될 수 있다.

즉

```text
Ethereum 기능을 어떻게 바꿀 것인가?

```

보다는

```text
Ethereum 관련 Process를 어떻게 운영할 것인가?

```

에 조금 더 가깝다.

---

# 12. Informational EIP

Informational EIP는 Ethereum과 관련된 설계 문제나 일반적인 지침, 정보를 제공하기 위한 문서다.

새로운 기능을 반드시 Ethereum에 적용하기 위한 제안이라기보다는

```text
Design Issue

Guideline

Information

```

을 공유하기 위한 목적을 가진다.

따라서 모든 EIP가

```text
Ethereum에 새로운 기능 추가

```

를 의미하는 것은 아니다.

---

# 13. EIP와 ERC의 관계

여기가 처음 공부할 때 가장 헷갈렸던 부분이다.

예를 들어

```text
ERC-20

```

이라고도 하고

```text
EIP-20

```

이라고도 하는 자료를 볼 수 있다.

처음에는

> ERC-20과 EIP-20은 다른 건가?

라고 생각했다.

하지만 현재 분류를 기준으로 ERC는 Standards Track EIP의 Category다.

따라서 ERC-20은 EIP 번호 20번인 표준이면서 Category가 ERC인 것이다.

개념적으로

```text
EIP-20

Type
└── Standards Track

Category
└── ERC

따라서

ERC-20

```

이라고 이해할 수 있다.

마찬가지로 ERC-721도 EIP 체계에서는 EIP-721 문서이며 ERC Category에 속한다.

---

# 14. 그런데 왜 ERC라는 이름을 더 많이 사용할까?

Token이나 Application Standard에서는 ERC라는 이름이 훨씬 익숙하다.

예를 들어 보통

```text
EIP-20 Token

```

이라고 하기보다는

```text
ERC-20 Token

```

이라고 한다.

NFT 역시

```text
EIP-721 NFT

```

보다는

```text
ERC-721 NFT

```

라는 표현을 훨씬 많이 사용한다.

ERC라는 이름을 통해 해당 EIP가 **Application Level Standard**라는 것을 쉽게 구분할 수 있기 때문이다.

반대로 EIP-1559처럼 Core Protocol을 변경하는 제안은 ERC라고 부르지 않는다.

---

# 15. 왜 ERC가 필요할까?

ERC가 왜 중요한지 이해하려면 표준이 없는 상황을 생각해보면 된다.

Ethereum에서 여러 개발자가 각자 Token을 만든다고 가정해보자.

개발자 A는 Token 전송 함수를

```solidity
sendToken()

```

이라고 만들었다.

개발자 B는

```solidity
moveCoin()

```

이라고 만들었다.

개발자 C는

```solidity
sendAsset()

```

이라고 만들었다.

기능은 모두 Token을 전송하는 것이지만 사용 방법이 전부 다르다.

```text
Token A → sendToken()

Token B → moveCoin()

Token C → sendAsset()

```

이런 상황에서 Wallet을 만드는 개발자는 Token마다 다른 코드를 작성해야 한다.

```text
Wallet

├── Token A 처리 코드
├── Token B 처리 코드
├── Token C 처리 코드
├── Token D 처리 코드
└── ...

```

Token이 수천 개가 된다면 관리하기가 굉장히 어려워진다.

---

# 16. 표준을 만들면 어떻게 달라질까?

모든 Token이 ERC-20이라는 공통 Interface를 사용한다고 생각해보자.

```text
                  ERC-20

                     │
          ┌──────────┼──────────┐
          │          │          │
          ▼          ▼          ▼
       Token A    Token B    Token C

```

각 Token은 동일하게

```solidity
transfer()

approve()

transferFrom()

balanceOf()

```

같은 Interface를 제공한다.

그러면 Wallet은 ERC-20 Interface를 기준으로 Token과 상호작용할 수 있다.

```text
Wallet

   │

ERC-20 Interface

   │

   ├── Token A
   ├── Token B
   ├── Token C
   └── Token D

```

이것이 **표준화의 가장 큰 장점 중 하나**다.

---

# 17. 상호운용성

ERC를 공부하면서 가장 중요하다고 느낀 개념이 **Interoperability**, 즉 상호운용성이다.

Ethereum에는 다양한 Application이 존재한다.

```text
Wallet

DEX

Lending Protocol

NFT Marketplace

Game

DAO

```

각 Application이 서로 완전히 다른 방식으로 구현되어 있다면 다른 프로젝트와 연결하기 어렵다.

하지만 공통된 Standard를 사용하면

```text
Wallet
   │
   │
ERC Standard
   │
   ├──── DEX
   ├──── Lending
   ├──── Marketplace
   └──── Game

```

처럼 서로 다른 서비스가 동일한 규칙을 기준으로 상호작용할 수 있다.

Ethereum에서 흔히 말하는 **Composability**와도 연결되는 부분이다.

---

# 18. ERC 번호는 무엇을 의미할까?

처음 ERC를 접했을 때

```text
ERC-20

ERC-721

ERC-1155

```

의 숫자가 Version이나 기능 수준을 의미한다고 생각했다.

예를 들어

```text
ERC-20
   ↓
ERC-721
   ↓
ERC-1155

점점 최신 버전?

```

처럼 생각할 수 있다.

하지만 그렇지 않다.

ERC 뒤에 붙는 숫자는 기본적으로 해당 Proposal에 부여된 번호다.

따라서

```text
ERC-721이 ERC-20의 721번째 버전

```

이라는 의미가 아니다.

각각 서로 다른 목적의 Standard다.

---

# 19. 대표적인 ERC 살펴보기

Ethereum에는 굉장히 많은 ERC가 존재한다.

그중 자주 접할 수 있는 몇 가지를 살펴보았다.

---

## ERC-20

### Fungible Token Standard

가장 유명한 Ethereum Token Standard 중 하나다.

```text
1 Token = 다른 1 Token

```

처럼 서로 대체 가능한 Token을 구현한다.

대표적인 기능은

```solidity
transfer()

balanceOf()

approve()

allowance()

transferFrom()

```

등이다.

주로

```text
Utility Token

Governance Token

Stablecoin

DeFi Token

```

등에서 사용된다.

---

# 20. ERC-721

### Non-Fungible Token Standard

각각의 Token을 `tokenId`로 구분한다.

```text
NFT #1

NFT #2

NFT #3

```

각 Token이 서로 다른 자산으로 취급된다.

대표적인 기능은

```solidity
ownerOf()

balanceOf()

transferFrom()

safeTransferFrom()

approve()

setApprovalForAll()

```

등이다.

NFT, 게임 아이템, 디지털 자산 등을 표현할 때 사용할 수 있다.

---

# 21. ERC-1155

ERC-1155는 하나의 Smart Contract에서 여러 종류의 Token을 관리할 수 있도록 설계된 Multi Token Standard다.

예를 들어 게임을 만든다고 생각해보자.

게임에는

```text
Gold Coin

Sword

Shield

Potion

```

같은 여러 자산이 존재할 수 있다.

ERC-20과 ERC-721을 각각 여러 개 배포하는 대신 ERC-1155에서는 하나의 Contract 안에서 여러 Token ID를 관리할 수 있다.

```text
ERC-1155 Contract

├── ID 1 → Gold
├── ID 2 → Sword
├── ID 3 → Shield
└── ID 4 → Potion

```

Fungible한 자산과 Non-Fungible한 자산을 모두 표현할 수 있다는 특징이 있다.

---

# 22. ERC-4626

ERC-4626은 **Tokenized Vault Standard**다.

DeFi를 공부하다 보면 Vault라는 구조를 자주 볼 수 있다.

사용자가 자산을 Vault에 예치하면 Vault가 전략에 따라 자산을 운용하고 사용자는 자신의 지분을 나타내는 Share를 받을 수 있다.

```text
User

 │
 │ USDC Deposit
 ▼

Vault

 │
 │ Strategy
 ▼

Yield

 │
 ▼

Share Value 증가

```

ERC-4626은 이러한 Tokenized Vault의 기본적인 Interface를 표준화한다.

DeFi Protocol끼리 Vault를 쉽게 연동할 수 있도록 만드는 것이 중요한 목적 중 하나다.

---

# 23. ERC-4337

ERC-4337은 **Account Abstraction**과 관련된 표준이다.

기존 Ethereum의 EOA는 Private Key를 중심으로 동작한다.

```text
Private Key
     │
     ▼
    EOA

```

ERC-4337에서는 Smart Contract Account를 이용하여 Account의 동작을 Programmable하게 만들 수 있다.

```text
Smart Account

├── Custom Authentication
├── Recovery
├── Multisig
├── Session Key
├── Batch Transaction
└── Gas Sponsorship

```

즉 ERC가 Token만을 위한 Standard가 아니라는 것을 보여주는 대표적인 사례라고 볼 수 있다.

---

# 24. ERC는 반드시 따라야 하는 법칙일까?

ERC를 처음 공부할 때는

> Ethereum에서 Token을 만들려면 ERC-20을 반드시 사용해야 하나?

라는 의문이 들었다.

Smart Contract 개발자가 자신만의 Interface를 만드는 것 자체가 불가능한 것은 아니다.

예를 들어

```solidity
function myCustomTransfer(
    address receiver,
    uint256 value
)
external;

```

같은 자신만의 Token 구조를 만들 수도 있다.

문제는 **호환성**이다.

기존 Wallet이나 DEX가

```text
transfer()

approve()

transferFrom()

```

같은 ERC-20 Interface를 기준으로 만들어져 있다면 Custom Interface를 사용하는 Token은 별도의 지원 없이는 기존 생태계와 바로 호환되지 않을 수 있다.

따라서 ERC의 힘은

```text
강제로 사용해야 한다.

```

보다는

```text
같은 표준을 사용하면
기존 Ethereum 생태계와 쉽게 연결할 수 있다.

```

에 있다고 생각한다.

---

# 25. ERC가 있다고 구현이 모두 같은 것은 아니다

여기서 또 하나 중요한 점이 있다.

같은 ERC를 따른다고 해서 모든 Smart Contract의 내부 코드가 동일한 것은 아니다.

ERC는 주로 외부에서 어떻게 상호작용할 것인지에 대한 Interface와 동작 규칙을 정의한다.

예를 들어 두 ERC-20 Token이 있다고 생각해보자.

```text
Token A

transfer()
approve()
balanceOf()


Token B

transfer()
approve()
balanceOf()

```

외부 Interface는 비슷하지만 내부 구현에는 차이가 있을 수 있다.

```text
Token A

├── Mint
├── Burn
└── Pause


Token B

├── Fee
├── Blacklist
└── Supply Cap

```

따라서

```text
ERC-20 Token이다.

```

라는 사실만으로 해당 Contract의 모든 동작을 알 수 있는 것은 아니다.

실제 보안 분석에서는 Standard Interface뿐만 아니라 프로젝트가 추가한 Custom Logic도 확인해야 한다.

---

# 26. ERC와 Smart Contract 보안

ERC를 공부하는 것이 Smart Contract 보안에서도 중요한 이유가 있다.

어떤 Contract를 분석할 때 해당 Contract가 따르는 Standard를 알고 있다면 **정상적인 동작이 무엇인지 기준을 잡을 수 있기 때문**이다.

예를 들어 ERC-20을 분석한다면

```text
transfer

approve

transferFrom

allowance

```

의 정상적인 관계를 알고 있어야 한다.

ERC-721을 분석한다면

```text
ownerOf

approve

setApprovalForAll

safeTransferFrom

```

등의 정상적인 동작을 알고 있어야 한다.

그 후 실제 구현과 비교한다.

```text
Standard Specification
          │
          ▼
실제 Smart Contract
          │
          ▼
차이점 확인

```

이 과정에서 잘못된 구현이나 예상하지 못한 동작을 찾을 수 있다.

---

# 27. 표준을 따르더라도 취약점은 존재할 수 있다

ERC Standard를 사용한다고 해서 Smart Contract가 자동으로 안전해지는 것은 아니다.

예를 들어 ERC-20을 기반으로 만든 Token에

```solidity
function mint(...)

```

기능을 추가했다고 생각해보자.

`mint()`의 Access Control을 잘못 구현하면 공격자가 임의로 Token을 발행할 수 있는 취약점이 발생할 수 있다.

```text
ERC-20

      +

Custom mint()

      ↓

Access Control 오류

      ↓

Unauthorized Mint

```

즉 ERC는 **호환성을 위한 표준**이지 모든 보안 문제를 해결해주는 보안 인증 같은 것은 아니다.

---

# 28. EIP 문서의 Status

EIP를 살펴볼 때는 Status도 확인할 필요가 있다.

대표적으로 다음과 같은 상태들이 존재한다.

```text
Draft

Review

Last Call

Final

Stagnant

Withdrawn

Living

```

예를 들어 `Final`은 최종 표준 상태를 의미한다.

반면 `Draft`는 아직 개발 및 논의 단계에 있는 Proposal이다.

따라서 어떤 EIP를 프로젝트에 적용하거나 기술 분석을 할 때는 번호와 내용만 볼 것이 아니라

```text
현재 Status가 무엇인가?

```

도 확인하는 것이 중요하다.

---

# 29. 새로운 ERC는 어떻게 만들어질까?

새로운 Standard가 필요하다고 해서 바로 ERC 번호를 만들어 사용하는 것은 아니다.

대략적인 흐름을 단순화하면 다음과 같이 볼 수 있다.

```text
문제 발견

   ↓

새로운 Standard 아이디어

   ↓

EIP 작성

   ↓

Discussion

   ↓

EIP Repository

   ↓

Review

   ↓

표준화 과정

```

작성자는

```text
Motivation

Specification

Rationale

Security Considerations

```

등을 문서화하고 커뮤니티와 논의한다.

즉 ERC는 특정 기업이 마음대로 결정해서 배포하는 표준이 아니라 Ethereum의 EIP Process를 통해 논의되고 발전하는 표준이다.

---

# 30. 지금까지 공부한 EIP/ERC를 분류해보기

이번 미션에서 공부한 내용을 기준으로 분류해보면 이해하기 쉽다.

```text
Ethereum Improvement Proposals

│
├── Standards Track
│
│
│   ├── Core
│   │     │
│   │     └── EIP-1559
│   │           Fee Market
│   │
│   └── ERC
│         │
│         ├── ERC-20
│         │     Fungible Token
│         │
│         ├── ERC-721
│         │     NFT
│         │
│         └── ERC-4337
│               Account Abstraction
│
├── Meta
│
└── Informational

```

그리고 앞에서 공부한 EIP-2612는 ERC-20의 Permit Extension으로 Token Application Standard와 연결된다.

이렇게 분류해서 보니 단순히 번호만 외우는 것보다 각각의 Proposal이 Ethereum의 어느 부분을 다루는지 이해하기 쉬웠다.

---

# 31. ERC를 공부하는 방법

ERC를 공부할 때 처음부터 Specification 전체를 읽으면 내용이 어렵게 느껴질 수 있다.

개인적으로는 다음 순서로 보는 것이 이해하기 쉬웠다.

```text
1. 기존에 어떤 문제가 있었는가?

              ↓

2. 왜 새로운 ERC가 필요했는가?

              ↓

3. 핵심 Interface는 무엇인가?

              ↓

4. 실제로 어떻게 동작하는가?

              ↓

5. 실제 프로젝트에서는 어디에 사용하는가?

              ↓

6. 보안상 주의할 부분은 무엇인가?

```

예를 들어 ERC-20이라면

```text
Token마다 Interface가 다름

        ↓

Token Interface 표준화 필요

        ↓

ERC-20

        ↓

transfer
approve
transferFrom

        ↓

Wallet / DEX / DeFi에서 활용

```

순서로 보면 된다.

ERC-721도 마찬가지다.

```text
각각 다른 자산을 표현해야 함

        ↓

tokenId 필요

        ↓

ERC-721

        ↓

ownerOf
safeTransferFrom
approve

        ↓

NFT / Game / Digital Asset

```

이런 방식으로 **문제 → 표준 → 동작 → 실제 활용** 순서로 공부하면 단순히 함수 목록을 외우는 것보다 이해하기 쉬웠다.

---

# 32. ERC를 공부하면서 이해한 점

처음에는 ERC를

> Ethereum Token을 만들기 위한 규칙

이라고 생각했다.

ERC-20과 ERC-721을 가장 먼저 접했기 때문에 자연스럽게 ERC와 Token을 같은 개념처럼 생각했던 것 같다.

하지만 실제 EIP 구조를 살펴보니 ERC는

```text
EIP

└── Standards Track

       └── ERC

```

라는 구조에 속해 있었고, Token뿐만 아니라 Ethereum Application Level에서 사용되는 다양한 표준과 규칙을 다룬다는 것을 알 수 있었다.

그리고 ERC의 가장 중요한 목적 중 하나는 **Interoperability**라고 생각한다.

Ethereum에는 수많은 개발자와 프로젝트가 존재한다.

각 프로젝트가 모두 자신만의 방식으로 Contract를 만든다면 다른 Application과 연결하기 굉장히 어려워진다.

ERC라는 공통 규칙을 사용함으로써

```text
Token

Wallet

DEX

DeFi

NFT Marketplace

Smart Account

```

등 서로 다른 Application이 같은 규칙을 기준으로 상호작용할 수 있다.

결국 ERC는 단순한 Smart Contract 작성 규칙이 아니라 **Ethereum 생태계가 서로 연결될 수 있도록 만들어주는 공통 언어와 비슷한 역할**을 한다고 이해할 수 있었다.

---

# 33. 정리

이번 글의 핵심 내용을 정리하면 다음과 같다.

| 개념의미            |                                    |
| --------------- | ---------------------------------- |
| EIP             | Ethereum Improvement Proposal      |
| Standards Track | Ethereum 표준과 관련된 EIP               |
| Core            | Ethereum Protocol 수준의 개선           |
| Networking      | Network Protocol 관련 개선             |
| Interface       | Client API/RPC, ABI 등 Interface 관련 |
| ERC             | Application Level의 표준 및 규칙         |
| Meta            | Ethereum Process 관련 Proposal       |
| Informational   | 정보 및 Guideline 제공                  |
| ERC 번호          | Proposal에 부여된 번호                   |
| ERC 목적          | 호환성과 상호운용성 확보                      |

가장 중요한 관계는 다음과 같다.

```text
EIP
│
├── Standards Track
│      │
│      ├── Core
│      ├── Networking
│      ├── Interface
│      └── ERC
│
├── Meta
│
└── Informational

```

따라서 ERC는 EIP와 완전히 별개의 개념이 아니라 **Ethereum Improvement Proposal 체계 안에서 Application Level Standard를 담당하는 Category**라고 이해하면 된다.

그리고 ERC의 핵심적인 가치는 표준화에 있다.

```text
각자 다른 구현

      ↓

공통 Standard

      ↓

Interoperability

      ↓

Wallet
DEX
DeFi
NFT
DApp

```

이러한 구조 덕분에 Ethereum의 수많은 Smart Contract와 Application이 서로 연결될 수 있다.

앞으로 ERC를 공부할 때는 단순히

```text
ERC-20 = Token
ERC-721 = NFT

```

처럼 외우는 것보다

> 기존에 어떤 문제가 있었고, 이 ERC가 어떤 공통 규칙을 만들어 그 문제를 해결했는가?

를 중심으로 살펴보면 각각의 ERC가 등장한 이유를 훨씬 쉽게 이해할 수 있을 것 같다.
