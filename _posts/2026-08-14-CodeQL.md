# CodeQL 원리와 사용법 분석 및 실습

## 1. 시작하며

이번 미션에서는 정적 분석 도구인 **CodeQL의 원리와 사용법에 대해 공부하고 직접 실습을 진행해보았다.**

CodeQL이라는 이름 자체는 GitHub의 Code Scanning이나 취약점 분석 자료를 보면서 몇 번 접해본 적이 있었지만,

실제로 어떤 원리로 취약점을 찾아내는지는 제대로 알지 못했다.

처음에는 CodeQL도 Semgrep이나 일반적인 SAST 도구처럼

소스 코드에서 위험한 함수나 특정 코드 패턴을 찾아주는 도구라고 생각했다.

하지만 CodeQL에 대해 찾아보면서 가장 먼저 알게 된 것은 CodeQL의 접근 방식이 단순한 문자열 검색과는 다르다는 것이었다.

CodeQL은 소스 코드를 분석하여 **CodeQL Database를 생성하고,**

**생성된 데이터베이스에 QL Query를 실행하여 코드의 구조나 데이터 흐름을 분석한다.**

전체적인 구조는 다음과 같다.

```
Source Code
    ↓
Extractor
    ↓
CodeQL Database
    ↓
QL Query
    ↓
Code Structure / Data Flow Analysis
    ↓
Security Finding

```

이번 실습에서는 이 과정을 직접 확인하기 위해 간단한 Python 취약 코드를 작성하고 CodeQL을 이용하여 분석해보았다.

또한 단순히 위험한 함수를 찾는 것에서 끝내지 않고, 사용자 입력값이

위험한 함수까지 전달되는 **Data Flow와 Taint Tracking**을 직접 확인해보았다.

마지막에는 Flask 기반의 간단한 웹 애플리케이션을 작성하고, CodeQL에서 제공하는 공식 Security Query를 이용하여 Command Injection과 SQL Injection을 실제로 탐지한 뒤 코드를 수정하고 다시 분석하여 취약점이 사라지는 것까지 확인하였다.

---

## 2. CodeQL이란?

CodeQL은 소스 코드를 분석 가능한 데이터 형태로 변환한 뒤

쿼리를 이용하여 프로그램의 구조와 데이터 흐름을 분석하는 정적 분석 기술이다.

처음에는 "소스 코드를 데이터베이스로 만든다"는 개념이 잘 이해되지 않았다.

예를 들어 다음과 같은 Python 코드가 있다고 생각해보았다.

```
def hello(name):
    print(name)

user = input()
hello(user)

```

사람이 이 코드를 보면 다음과 같은 내용을 쉽게 이해할 수 있다.

```
hello라는 함수가 존재한다.

hello 함수는 name이라는 매개변수를 가진다.

input()으로 사용자 입력을 받는다.

input()의 결과가 user 변수에 저장된다.

user가 hello() 함수의 인자로 전달된다.

```

일반적인 문자열 검색에서는 hello, input, print와 같은 문자열을 찾을 수 있다.

하지만 보안 분석에서는 단순히 특정 문자열이 존재하는지만 확인하는 것으로는 부족하다.

예를 들어 다음과 같은 질문이 필요할 수 있다.

\- 이 프로젝트에는 어떤 함수가 존재하는가?
\- 특정 함수는 어디에서 호출되는가?
\- 사용자 입력을 받는 부분은 어디인가?
\- 사용자 입력값은 어떤 변수로 전달되는가?

외부에서 들어온 데이터가 위험한 함수까지 전달되는가?

CodeQL은 소스 코드를 분석하여 이러한 코드의 구조와 관계를

데이터 형태로 만들기 때문에 이런 질문을 QL Query로 표현할 수 있다.

이 부분을 이해하면서 CodeQL을 단순히 "취약점을 자동으로 찾아주는 도구"라기보다는 **소스 코드 자체를 Query할 수 있도록 만들어주는 분석 플랫폼**에 가깝다고 생각하게 되었다.

---

## 3. 정적 분석과 CodeQL

CodeQL은 프로그램을 직접 실행하지 않고 소스 코드를 분석하는 **정적 분석(Static Analysis)** 방식이다.

예를 들어 다음 코드가 있다고 생각해보았다.

```
import os

command = input("command: ")
os.system(command)

```

이 코드는 실제로 실행하지 않더라도 사용자 입력값이 os.system()으로 전달된다는 것을 확인할 수 있다.

반대로 동적 분석은 프로그램을 직접 실행하면서 입력값을 전달하고 실제 동작이나 응답을 확인하는 방식이다.

웹 보안에서 Burp Suite 등을 이용하여 실제 SQL Injection Payload를 전송하는 방식이 동적 분석에 해당한다.

이번 실습에서는 실제 공격을 수행하는 것이 아니라

**소스 코드만을 이용하여 위험한 코드 구조와 데이터 흐름을 찾아내는 과정**에 집중하였다.

## 4. 실습 환경 구성

이번 CodeQL 실습은 별도의 VM을 구성하지 않고 **Windows 11의 WSL2 Ubuntu 환경**에서 진행하였다.

CodeQL은 정적 분석 도구이기 때문에 이번 Python 코드 분석 실습에서는 별도의 가상 머신이 필요하지 않았다.

먼저 현재 환경을 확인하였다.

```
whoami
python3 --version
git --version

```

확인 결과는 다음과 같았다.

```
사용자 : cyh
Python : 3.12.3
Git    : 2.43.0

```

Python과 Git이 정상적으로 설치되어 있었기 때문에 CodeQL 설치를 바로 진행하였다.

## 5. CodeQL CLI 설치

CodeQL을 사용하기 위해 Linux용 CodeQL Bundle을 다운로드하였다.

```
cd ~

wget https://github.com/github/codeql-action/releases/download/codeql-bundle-v2.26.3/codeql-bundle-linux64.tar.gz

```

다운로드한 파일의 압축을 해제하였다.

```
tar -xzf codeql-bundle-linux64.tar.gz

```

설치가 정상적으로 되었는지 확인하기 위해 다음 명령을 실행하였다.

```
~/codeql/codeql version

```

결과는 다음과 같이 출력되었다.

```
CodeQL command-line toolchain release 2.26.3.
Unpacked in: /home/cyh/codeql

```

CodeQL 2.26.3 버전이 정상적으로 실행되는 것을 확인하였다.

다만 실행할 때 다음과 같은 경고가 반복적으로 나타났다.

```
This CodeQL Distribution is installed in '/home/cyh',
which is the home directory.
This could cause performance issues.

```

처음에는 설치가 잘못된 것인지 생각했지만 분석 자체에는

영향을 주지 않는 설치 위치 관련 성능 경고였기 때문에 이번 실습에서는 그대로 진행하였다.

매번 /home/cyh/codeql/codeql 경로를 입력하지 않기 위해 PATH도 설정하였다.

```
echo 'export PATH="$HOME/codeql:$PATH"' >> ~/.bashrc
source ~/.bashrc

```

이후에는 다음과 같이 바로 CodeQL을 실행할 수 있었다.

```
codeql version

```

## 6. Python 분석 환경 확인

CodeQL 설치 후 Python 분석에 필요한 환경이 정상적으로 포함되어 있는지 확인하였다.

먼저 지원 언어를 확인하였다.

```
codeql resolve languages

```

결과에서 다음과 같이 Python Extractor가 존재하는 것을 확인하였다.

```
python (/home/cyh/codeql/python)

```

이후 Python Query Pack도 확인하였다.

```
codeql resolve packs | grep python

```

결과는 다음과 같았다.

```
codeql/python-all@7.2.3
codeql/python-examples@0.0.0
codeql/python-queries@1.8.8

```

이를 통해 Python 코드를 분석하기 위한 Extractor와 기본 Query Pack이 정상적으로 준비되어 있는 것을 확인하였다.

## 7. 실습용 취약 코드 작성

CodeQL의 원리를 직접 확인하기 위해 처음부터

복잡한 오픈소스 프로젝트를 분석하기보다 간단한 Python 코드를 직접 작성하기로 했다.

먼저 실습 디렉터리를 생성하였다.

```
cd ~
mkdir -p codeql-lab
cd codeql-lab

```

그리고 vulnerable.py 파일을 작성하였다.

```
import os
import sqlite3


def command_injection():
    host = input("Host: ")

    command = "ping " + host

    os.system(command)


def sql_injection():
    username = input("Username: ")

    conn = sqlite3.connect("test.db")
    cursor = conn.cursor()

    query = "SELECT * FROM users WHERE username = '" + username + "'"

    cursor.execute(query)


command_injection()
sql_injection()

```

이번 코드에는 의도적으로 Command Injection과 SQL Injection이 발생할 가능성이 있는 구조를 넣었다.

Command Injection 부분은 다음과 같다.

```
input()
   ↓
host
   ↓
"ping " + host
   ↓
command
   ↓
os.system()

```

SQL Injection은 다음과 같은 구조이다.

```
input()
   ↓
username
   ↓
SQL 문자열 결합
   ↓
query
   ↓
cursor.execute()

```

CodeQL을 실행하기 전에 먼저 사람이 봤을 때 어떤 흐름이 존재하는지 정리하였다.

이후 Python 문법에 문제가 없는지 확인하였다.

```
python3 -m py_compile vulnerable.py

```

별도의 오류가 발생하지 않아 정상적으로 작성된 것을 확인하였다.

## 8. CodeQL Database 생성

CodeQL 실습에서 처음 알게 된 중요한 부분은 QL Query를 소스 코드 파일에 바로 실행하는 것이 아니라는 점이었다.

먼저 분석 대상 코드를 **CodeQL Database로 변환하는 과정**이 필요했다.

처음에는 다음과 같이 실행하였다.

```
codeql database create ~/codeql-db \
  --language=python \
  --source-root=~/codeql-lab

```

하지만 다음과 같은 오류가 발생했다.

```
Invalid source root: /home/cyh/~/codeql-lab

```

\--source-root에 지정한 \~가 원하는 방식으로 처리되지 않으면서 잘못된 경로가 만들어진 것이었다.

따라서 절대 경로를 사용하도록 수정하였다.

```
rm -rf /home/cyh/codeql-db

codeql database create /home/cyh/codeql-db \
  --language=python \
  --source-root=/home/cyh/codeql-lab

```

이번에는 CodeQL Database 생성이 정상적으로 진행되었다.

실행 도중 다음 메시지도 나타났다.

```
python2: not found

```

하지만 이후 CodeQL이 Python 3을 자동으로 선택하였다.

```
Wanted to run Python 2, but it is not available.
Using Python 3 instead

```

그리고 실제로 작성한 파일이 추출되는 것을 확인하였다.

```
Extracted file /home/cyh/codeql-lab/vulnerable.py

```

이후 TRAP 파일 Import 및 Relation 병합 과정이 진행되고 마지막에는 다음 결과가 출력되었다.

```
Successfully created database at /home/cyh/codeql-db.

```

이 로그를 보면서 CodeQL이 단순히 Python 파일을 복사하여

저장하는 것이 아니라 소스 코드의 구조를 분석하여 Database를 만든다는 것을 확인할 수 있었다.

전체적인 흐름은 다음과 같이 이해하였다.

```
vulnerable.py
     ↓
Python Extractor
     ↓
TRAP
     ↓
Relation Import
     ↓
CodeQL Database

```

## 9. QL Query Pack 구성

이제 직접 QL Query를 작성해보기로 했다.

처음 find-functions.ql 파일만 작성하고 실행했을 때 다음 오류가 발생하였다.

```
ERROR: could not resolve module python
ERROR: could not resolve type Function

```

원인을 확인해보니 커스텀 Query가 어떤 CodeQL Library를 사용하는지 알려주는 Query Pack 설정이 필요했다.

따라서 qlpack.yml 파일을 생성하였다.

```
name: cyh/codeql-lab
version: 0.0.1
dependencies:
  codeql/python-all: "*"

```

그리고 다음 명령을 실행하였다.

```
codeql pack install

```

실행 중 여러 Warning이 발생했지만 마지막에는 다음 메시지가 출력되었다.

```
Dependencies resolved.
Nothing to install.

```

CodeQL Bundle 내부에 필요한 Python Pack이 이미 존재하고 있었기 때문에 별도의 다운로드는 필요하지 않았다.

이 과정을 통해 커스텀 Query를 작성할 때도 필요한 CodeQL Library 의존성을 설정해야 한다는 것을 알게 되었다.

## 10. Python 함수 조회

처음부터 복잡한 보안 Query를 작성하기보다 CodeQL Database에서

함수 정보를 실제로 조회할 수 있는지 확인하기로 했다.

find-functions.ql을 다음과 같이 작성하였다.

```
import python

from Function f
select f, f.getName()

```

그리고 실행하였다.

```
codeql query run ~/codeql-lab/find-functions.ql \
  --database=/home/cyh/codeql-db

```

결과는 다음과 같았다.

```
| Function command_injection | command_injection |
| Function sql_injection     | sql_injection     |

```

직접 작성한 command\_injection, sql\_injection 함수가 정상적으로 출력되었다.

처음에는 결과 자체가 단순해 보였지만 이 실습을 통해 중요한 점 하나를 확인할 수 있었다.

CodeQL은 grep처럼 단순히 command\_injection이라는

문자열을 검색한 것이 아니라 **CodeQL Database에 저장된 Python Function 객체를 조회한 것**이었다.

즉 CodeQL에서 말하는 "소스 코드를 Query한다"는 개념을 처음으로 직접 확인할 수 있었다.

## 11. 위험 API 탐색

다음에는 단순한 함수 목록 조회에서 한 단계 더 나아가 보안상 위험할 수 있는 os.system() 호출을 찾아보기로 했다.

이를 위한 Query를 작성하고 실행하였다.

결과는 다음과 같았다.

```
| Attribute() | os.system() call found |

```

따라서 CodeQL이 다음 코드의 호출 위치를 정상적으로 찾아낸 것을 확인하였다.

```
os.system(command)

```

여기까지 실습하면서 처음에는 os.system()을 찾으면 Command Injection을 찾은 것이라고 생각할 수도 있었다.

하지만 다음 두 코드를 비교해보았다.

```
os.system("ls")

```

```
command = input()
os.system(command)

```

두 코드 모두 os.system()을 사용하지만 보안적인 의미는 전혀 다르다.

첫 번째는 고정된 명령을 실행하지만 두 번째는 사용자가 입력한 값이 명령 실행 함수까지 전달된다.

따라서 실제 보안 분석에서 중요한 것은 단순히 위험한 API가 존재하는지가 아니라:

```
신뢰할 수 없는 데이터가
위험한 함수까지 전달되는가?

```

를 확인하는 것이라고 생각하였다.

## 12. Data Flow 분석

이제 사용자 입력값이 os.system()까지 전달되는지를 직접 분석해보기로 했다.

처음에는 DataFlow::Global을 이용하여 Source와 Sink 사이의 Data Flow를 추적하였다.

Source는 input()으로 설정하고 Sink는 os.system()에 전달되는 값을 지정하였다.

Query 자체는 정상적으로 컴파일되고 실행되었다.

하지만 결과는 다음과 같이 비어 있었다.

```
| sink | col1 | source |
+------+------+--------+

```

처음에는 Query 작성이 잘못된 것으로 생각했다.

하지만 코드를 다시 살펴보니 사용자 입력값이 바로 os.system()으로 전달되지 않고 중간에 문자열 결합이 존재하였다.

```
host = input()

command = "ping " + host

os.system(command)

```

즉 다음과 같은 변형 과정이 있었다.

```
input()
   ↓
host
   ↓
"ping " + host
   ↓
command
   ↓
os.system()

```

이 과정을 확인하면서 일반적인 Data Flow와 Taint Tracking의 차이를 알아보게 되었다.

## 13. Taint Tracking으로 변경

사용자 입력값이 문자열 결합처럼 변형된 이후에도 위험한 함수에 영향을 주는 흐름을 추적하기 위해 Query를 TaintTracking::Global을 사용하는 방식으로 수정하였다.

다시 실행한 결과는 다음과 같았다.

```
|            sink             |              col1              |           source            |
+-----------------------------+--------------------------------+-----------------------------+
| ControlFlowNode for command | User input reaches os.system() | ControlFlowNode for input() |

```

이번에는 원하는 결과가 정상적으로 출력되었다.

즉 CodeQL이 실제로 다음 흐름을 추적한 것이다.

```
input()
   ↓
host
   ↓
"ping " + host
   ↓
command
   ↓
os.system(command)

```

이번 실습에서 가장 의미 있었던 부분 중 하나였다.

문서에서 Data Flow와 Taint Tracking의 차이를 단순히 읽는 것보다 실제로 DataFlow::Global에서는 결과가 나오지 않았다가 TaintTracking::Global로 변경한 이후 흐름이 탐지되는 것을 직접 확인하였다.

## 14. SQL Injection 흐름 분석

Command Injection에서 사용한 방식을 SQL Injection에도 적용해보았다.

이번에는 input()으로 들어오는 사용자 입력을 Source로 설정하고 execute()에 전달되는 SQL Query를 Sink로 설정하였다.

분석 대상 흐름은 다음과 같다.

```
input()
   ↓
username
   ↓
SQL 문자열 결합
   ↓
query
   ↓
cursor.execute(query)

```

Taint Tracking Query를 실행한 결과 다음과 같이 출력되었다.

```
|           sink            |               col1               |           source            |
+---------------------------+----------------------------------+-----------------------------+
| ControlFlowNode for query | User input reaches SQL execute() | ControlFlowNode for input() |

```

따라서 사용자 입력값이 SQL Query 문자열에 결합된 뒤 cursor.execute()까지 전달되는 것을 확인할 수 있었다.

여기까지 진행하면서 직접 작성한 커스텀 QL Query를 이용하여 Command Injection과 SQL Injection에 해당하는 데이터 흐름을 모두 추적할 수 있었다.

## 15. 공식 Security Query 실행

직접 작성한 Query뿐만 아니라 CodeQL에서 기본적으로 제공하는 Security Query도 실행해보기로 했다.

다음 명령을 이용하여 Python의 security-extended Query Suite를 실행하였다.

```
codeql database analyze /home/cyh/codeql-db \
  codeql/python-queries:codeql-suites/python-security-extended.qls \
  --format=sarif-latest \
  --output=/home/cyh/codeql-results.sarif

```

분석 과정에서 총 52개의 Query가 실행되었으며 그 안에는 다음과 같은 Query도 포함되어 있었다.

```
CommandInjection.ql
SqlInjection.ql
PathInjection.ql
CodeInjection.ql
UnsafeDeserialization.ql
ReflectedXss.ql
...

```

하지만 처음 작성했던 단순한 input() 기반 예제에서는

공식 Command Injection과 SQL Injection Rule이 최종 결과에 나타나지 않았다.

직접 작성한 Query에서는 input()을 Source로 명시적으로 정의했기 때문에 결과가 발생했지만, 공식 Security Query에서는 자체적으로 정의된 Source/Sink 및 Framework 모델을 사용하기 때문이라고 생각하였다.

이를 통해 CodeQL에서 단순히 Taint Tracking 기능을 사용하는 것뿐만 아니라

**어떤 값을 Source로 보고 어떤 API를 Sink로 모델링하는지가 굉장히 중요하다**는 것을 알 수 있었다.

## 19. 취약 코드 수정

취약점을 탐지하는 것에서 끝내지 않고 실제로 코드를 수정하고 다시 분석해보기로 했다.

먼저 기존 취약 코드를 백업하였다.

```
mkdir -p ~/codeql-backup

cp ~/codeql-lab/app.py \
  ~/codeql-backup/app_vulnerable.py

```

### Command Injection 수정

기존 코드는 다음과 같았다.

```
command = "ping -c 1 " + host

os.system(command)

```

이를 다음과 같이 수정하였다.

```
subprocess.run(
    ["ping", "-c", "1", host],
    check=False
)

```

Shell에서 실행할 하나의 문자열을 직접 만드는 대신 실행할 프로그램과 각각의 인자를 분리하여 전달하였다.

### SQL Injection 수정

기존 코드는 사용자 입력값을 SQL 문자열에 직접 결합하고 있었다.

```
query = "SELECT * FROM users WHERE username = '" + username + "'"

cursor.execute(query)

```

이를 Parameterized Query 형태로 수정하였다.

```
cursor.execute(
    "SELECT * FROM users WHERE username = ?",
    (username,)
)

```

최종적으로 app.py는 다음과 같은 구조가 되었다.

```
from flask import Flask, request
import sqlite3
import subprocess

app = Flask(__name__)


@app.route("/ping")
def ping():
    host = request.args.get("host")

    subprocess.run(
        ["ping", "-c", "1", host],
        check=False
    )

    return "done"


@app.route("/user")
def user():
    username = request.args.get("username")

    conn = sqlite3.connect("users.db")
    cursor = conn.cursor()

    cursor.execute(
        "SELECT * FROM users WHERE username = ?",
        (username,)
    )

    return "done"


if __name__ == "__main__":
    app.run()

```

## 23. 실습하면서 알게 된 점

이번 실습을 진행하면서 CodeQL에 대해 몇 가지 중요한 점을 직접 확인할 수 있었다.

첫 번째는 CodeQL이 단순한 문자열 검색 도구가 아니라는 점이다.

처음 작성했던 다음 Query를 통해:

```
from Function f
select f, f.getName()

```

Python 코드의 Function 객체 자체를 조회할 수 있었다.

두 번째는 **CodeQL Database 생성 과정**이다.

처음에는 소스 코드 파일에 바로 Query를 실행하는 방식이라고 생각했지만 실제로는:

```
Source Code
     ↓
Extractor
     ↓
TRAP
     ↓
CodeQL Database
     ↓
QL Query

```

과정이 필요했다.

세 번째는 위험한 API가 존재한다고 해서 바로 취약점이라고 판단할 수 없다는 것이다.

예를 들어:

```
os.system("ls")

```

와:

```
command = input()
os.system(command)

```

은 둘 다 os.system()을 사용한다.

하지만 두 번째 코드에는 외부에서 제어할 수 있는 데이터가 Sink까지 전달되는 흐름이 존재한다.

따라서 보안 분석에서는:

```
Source
  ↓
Data Flow
  ↓
Sink

```

를 확인하는 것이 중요하다.

네 번째는 **Data Flow와 Taint Tracking의 차이**였다.

이번에 직접 DataFlow::Global을 사용했을 때는 결과가 나타나지 않았지만 TaintTracking::Global로 변경한 이후 문자열 결합을 거치는 흐름까지 탐지할 수 있었다.

마지막으로 Source와 Sink의 모델링이 굉장히 중요하다는 것도 확인하였다.

커스텀 Query에서는 직접 input()을 Source로 지정했기 때문에 바로 결과를 얻을 수 있었다.

하지만 공식 Security Query에서는 자체 Framework/API 모델을

사용하기 때문에 단순 Python input() 코드와 Flask request.args 코드에서 결과가 다르게 나타났다.

Flask 코드에서는 CodeQL이 웹 요청으로 들어오는 값을

Source로 인식하면서 공식 py/command-line-injection, py/sql-injection Rule이 실제로 탐지되었다.

## 25. 마무리

이번 실습을 시작하기 전에는 CodeQL을 GitHub에서 사용하는 취약점 스캐너 정도로 생각하고 있었다.

하지만 직접 Database를 생성하고 QL Query를 작성해보면서 CodeQL의 핵심은 단순히 미리 만들어진 보안 규칙을 실행하는 것에 있는 것이 아니라 **소스 코드를 분석 가능한 데이터로 만들고 코드의 구조와 관계를 Query할 수 있다는 점**이라고 생각하게 되었다.

특히 단순히 os.system()이라는 위험한 함수를 검색하는 것과 사용자 입력이 여러 변수와 문자열 결합을 거쳐 os.system()까지 전달되는 것을 추적하는 것은 전혀 다른 분석이었다.

처음 Data Flow Query를 실행했을 때 결과가 나오지 않았고 Taint Tracking으로 변경한 후 결과가 나온 과정도 기억에 남았다. 단순히 문서에서 두 개념의 차이를 읽는 것보다 실제 코드를 이용해 결과 차이를 확인하니 어떤 경우에 Taint Tracking이 필요한지 이해하기 쉬웠다.

또 커스텀 Query와 공식 Security Query에서 결과가 다르게 나타나는 과정을 통해 Source와 Sink를 어떻게 정의하는지가 분석 결과에 큰 영향을 준다는 것도 확인하였다.

마지막에는 Flask 애플리케이션에서 CodeQL 공식 Query를 이용하여 실제로 py/command-line-injection, py/sql-injection을 탐지하였고, 코드를 수정한 뒤 동일한 방식으로 다시 분석하여 두 Rule이 더 이상 나타나지 않는 것까지 확인하였다.

이번 실습을 통해 CodeQL을 단순한 취약점 탐지 도구가 아니라 **Source, Sink, Data Flow, Taint Tracking을 기반으로 코드의 관계를 분석하고 원하는 취약점 패턴을 직접 Query로 표현할 수 있는 정적 분석 도구**로 이해하게 되었다.

앞으로 실제 오픈소스 프로젝트나 CVE를 분석할 때도 하나의 취약점 Root Cause를 분석한 뒤 해당 패턴을 QL Query로 만들고 코드베이스 전체에서 비슷한 취약점을 찾는 Variant Analysis까지 진행해보면 CodeQL을 더 실질적으로 활용할 수 있을 것 같다.
