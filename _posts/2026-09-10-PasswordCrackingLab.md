# 비밀번호는 길기만 하면 안전할까? Password Cracking Lab 개발부터 부스 운영까지

패스워드 크래킹 시뮬레이션을 통해 비밀번호의 보안 강도를 분석하고,

사용자가 직접 더 안전한 비밀번호를 만들어 보도록 구성한 체험형 보안 교육 프로젝트

- GitHub: <https://github.com/gyuesecurity/password-cracking-lab>
- 배포 페이지: <https://password-cracking-lab-two.vercel.app>
- 프론트엔드: React, TypeScript, Vite, Vercel
- 백엔드: Python, Flask, Gunicorn, MySQL, Railway

## 프로젝트를 마치며

Password Cracking Lab의 개발과 실제 부스 운영을 모두 마쳤다.

처음에는 사용자가 입력한 비밀번호의 길이와 문자 종류를 확인해 점수를 보여주는 비교적 단순한 프로그램을 생각했다. 하지만 개발을 진행할수록 비밀번호 보안은 `길이가 길다`, `특수문자가 있다` 같은 몇 가지 조건만으로 설명할 수 없다는 사실이 분명해졌다.

`Ulsan2026!`처럼 대문자, 소문자, 숫자, 특수문자를 모두 포함한 비밀번호도 지역명과 연도라는 예측 가능한 정보로 구성되어 있다. 반면 `mint-river-cloud-lamp`처럼 서로 관련 없는 단어를 여러 개 조합한 패스프레이즈는 구성은 단순해 보여도 후보 조합의 수가 훨씬 많다.

이 차이를 글로만 설명하는 대신, 사용자가 직접 비밀번호를 만들고 취약점을 확인한 뒤 다시 개선해 보는 형태로 전달하고 싶었다. 그렇게 기획부터 분석기, 웹 화면, 백엔드, 데이터베이스, 배포, QA 문서와 부스 운영까지 하나씩 구현했다.

이 글에서는 완성된 기능만 소개하는 것이 아니라 개발 중 실제로 발견했던 문제와 수정 과정, 

그리고 부스 운영까지 마친 뒤 느낀 점을 함께 정리한다.

## 1. 프로젝트 목표

프로젝트의 목표는 비밀번호에 점수 하나를 붙이는 것이 아니었다. 

사용자가 다음 과정을 짧은 시간 안에 직접 경험하도록 만드는 것이 핵심이었다.

1. 비밀번호 보안에 관한 간단한 퀴즈를 푼다.
2. 테스트용 비밀번호를 직접 만든다.
3. Brute Force, Dictionary, Pattern 공격 관점에서 결과를 확인한다.
4. 어떤 문자열이 감점되었고 왜 위험한지 확인한다.
5. 분석 결과에 맞는 개선 힌트를 받는다.
6. 더 강한 두 번째 비밀번호를 만든다.
7. 1차와 2차 점수 및 탐지 결과를 비교한다.
8. 원하는 경우 익명 닉네임과 점수만 랭킹에 등록한다.

전체 체험 시간은 한 사람당 약 3~5분을 목표로 잡았다. 

점수 경쟁보다는 참가자가 자신의 비밀번호 습관에서 문제 하나를 발견하고, 그것을 직접 개선하는 경험을 우선했다.

또 하나의 중요한 원칙은 **실제로 사용 중인 비밀번호를 수집하지 않는 것**이었다. 

입력한 문자열은 브라우저 안에서만 분석하고, 서버에는 닉네임과 점수만 전송하도록 설계했다.

## 2. Git 브랜치로 작업 영역 분리하기

한 저장소 안에서 기능별 작업을 분리하기 위해 다음 브랜치를 사용했다.

```text
main
├─ frontend
├─ backend
├─ password-analyzer
├─ content-qa
└─ integration
```

- `frontend`: React 기반 체험 화면과 사용자 흐름
- `backend`: Flask API, MySQL 연동과 랭킹 기능
- `password-analyzer`: Python 비밀번호 분석 기준 구현
- `content-qa`: 퀴즈, 설명, 개선 힌트, 테스트 계획, 운영 문서
- `integration`: 각 기능을 안전하게 합치고 실제 배포를 검증하는 브랜치
- `main`: 초기 기준점과 원본 보존

처음부터 모든 코드를 한 브랜치에서 수정했다면 어느 변경 때문에 문제가 발생했는지 확인하기 어려웠을 것이다. 기능별 브랜치를 유지하고 원본 브랜치를 삭제하지 않은 덕분에, 통합 과정에서 변경 전후를 비교하면서 필요한 코드만 가져올 수 있었다.

특히 백엔드 브랜치의 과거 커밋에서 데이터베이스 접속정보가 코드에 직접 포함된 문제를 발견했다. 

해당 기록을 그대로 `integration`에 병합하면 민감한 값까지 통합 브랜치의 Git 기록에 남게 된다. 

그래서 백엔드 브랜치는 직접 병합하지 않고 기능과 API 구조만 참고해 `server/`에 안전한 구현을 다시 작성했다. 

노출되었던 비밀번호는 교체하고, 최종 구현에서는 모든 접속정보를 Railway 환경변수로 이동했다.

통합 브랜치는 다음 순서로 정리했다.

```text
프론트 화면 확보
→ 콘텐츠·QA 문서 병합
→ Python 분석기를 reference 폴더에 보존
→ 안전한 Flask·MySQL 서버 재구성
→ 웹 분석기를 실제 결과 기반으로 교체
→ API 및 랭킹 연결
→ 배포 후 회귀 테스트와 모바일 수정
```

이 과정에서 Git 브랜치는 단순한 작업 사본이 아니라, 

문제가 생겼을 때 원인을 추적하고 안전하지 않은 기록이 최종 배포에 섞이지 않도록 막아 주는 장치가 되었다.

## 3. 사용자 체험 흐름 구현

프론트엔드는 React와 TypeScript로 구현하고 Vite로 빌드했다. 

한 화면에서 모든 내용을 한꺼번에 보여주지 않고 체험 단계에 따라 화면을 전환하도록 구성했다.

```text
시작
→ 체험 안내
→ 보안 퀴즈
→ 퀴즈 해설
→ 1차 비밀번호 입력
→ 공격 시뮬레이션
→ 분석 결과
→ 개선 힌트
→ 2차 비밀번호 입력
→ 결과 비교
→ 랭킹 등록
→ 완료
```

### 시작 및 안내 화면

첫 화면과 안내 화면에는 실제 사용 중인 비밀번호를 입력하면 안 된다는 내용을 반복해서 배치했다. 

참가자가 체험 내용을 읽지 않고 바로 진행할 가능성도 고려해 입력 화면과 하단 고정 안내에서도 같은 원칙을 확인할 수 있게 했다.

안내 문구 역시 실제 구현과 일치하도록 수정했다. 초기에는 `입력 즉시 삭제` 같은 표현이 있었지만, 

실제로는 1차와 2차 비교가 끝날 때까지 브라우저 메모리의 상태값으로 입력이 유지된다. 

대신 서버나 저장소에는 남지 않으므로 다음과 같이 정확한 표현을 사용했다.

분석은 브라우저 내부에서 수행되며 입력값은 서버로 전송하거나 저장하지 않습니다.

### 시작 퀴즈

첫 퀴즈는 다음 두 비밀번호를 비교하도록 만들었다.

```text
A. Ulsan2026!
B. mint-river-cloud-lamp
```

정답은 B다. A는 여러 문자 종류를 포함하지만 지역명, 연도, 흔한 끝 특수문자로 구성되어 있어 규칙 기반 공격에 취약하다. 

B는 서로 관련 없는 여러 단어를 조합해 전체 길이와 후보 조합 수를 늘린 패스프레이즈다.

다만 화면에 공개된 예시를 실제 계정의 비밀번호로 그대로 사용하는 것도 위험하다. 

최종 화면에는 공개 예시를 복사하지 말고 자신만의 무작위 단어 조합을 만들라는 안내를 추가했다.

### 두 번의 비밀번호 도전

1차 입력에서는 참가자가 평소 만들 법한 방식의 테스트 문자열을 작성한다. 

분석 결과에서 발견된 약점에 따라 개선 힌트를 보여주고, 2차 입력에서는 해당 문제를 피해서 새로운 문자열을 만든다.

결과 비교 화면은 다음 항목을 실제 분석 결과에서 가져온다.

- 1차·2차 보안 점수
- 비밀번호 길이
- 연도·날짜 포함 여부
- 사전 단어 포함 여부
- 발견된 문제 개수
- 문자 구성
- 예상 해독 시간
- 점수 증가, 동일 또는 감소 여부

2차 점수가 낮아졌는데도 무조건 `향상되었습니다`라고 표시하는 일이 없도록 점수 차이가 양수, 0, 음수인 경우를 각각 나누었다.

## 4. 비밀번호 분석기 설계

분석 로직은 먼저 Python으로 기준 구현을 만들고, 브라우저에서 동일하게 동작하도록 TypeScript로 이식했다.

분석기는 다음 요소를 검사한다.

| 탐지 항목 | 설명 |
|---|---|
| 길이 | 8자, 10자, 12자, 14자 기준으로 단계별 평가 |
| 문자 구성 | 대문자, 소문자, 숫자, 특수문자, 한글·기타 문자 확인 |
| 개인정보 관련 단어 | 입력된 관련 단어와 이름 형태 탐지 |
| 사전 단어 | 지역명, 서비스명, 일반 단어 탐지 |
| 연도 | 19xx, 20xx, 21xx 형태 탐지 |
| 날짜 | YYYYMMDD, YYMMDD, MMDD, 구분자 날짜, `5월12일` 형태 탐지 |
| 반복 | 같은 문자 또는 같은 문자열 블록의 반복 탐지 |
| 순서 패턴 | `123`, `abc`, `qwerty` 등 연속·키보드 패턴 탐지 |
| 흔한 비밀번호 | `password`, `admin`, `123456` 등 우선 공격 후보 탐지 |
| 전체 구조 | 단어+연도+특수문자와 같은 정형화된 구조 탐지 |
| 복합 위험 | 서로 다른 예측 가능한 요소가 여러 개 결합된 경우 탐지 |

### 중복 감점 처리

하나의 문자열이 여러 규칙에 동시에 걸릴 수 있다. 예를 들어 `password123`은 사전 단어, 흔한 비밀번호, 숫자 순서가 겹친다. 

모든 항목을 그대로 더하면 같은 위치를 여러 번 과도하게 감점할 수 있다.

이를 막기 위해 겹치는 문자열 구간에는 우선순위가 높은 탐지를 먼저 적용하고, 같은 위치의 약한 탐지는 추가 감점하지 않도록 했다. 반대로 서로 다른 위치에서 독립된 취약점이 발견되면 복합 패턴 감점을 적용했다.

```text
COMMON_PATTERN
→ DATE
→ REPETITION
→ SEQUENCE
→ SIMILAR_PATTERN
→ YEAR
```

점수는 100점에서 탐지된 위험 요소를 차감하는 방식으로 계산하되 0점 아래로 내려가지 않게 했다.

### 날짜 유효성 확인

숫자 여덟 자리가 보인다는 이유만으로 모두 날짜로 판단하면 오탐이 많아진다. 

`20260231`처럼 실제로 존재하지 않는 날짜는 제외하고, 연도·월·일로 해석 가능한 경우만 날짜 evidence로 반환하게 했다.

지원한 대표 형태는 다음과 같다.

```text
20050621
050621
0621
2005-06-21
2005/06/21
5월12일
```

### 이름 탐지 보완

영문 두 글자는 긴 단어 내부에서도 자주 나타나기 때문에 일반 사전 탐지에 사용하면 오탐이 많았다. 

반면 두 글자 한글 이름은 실제 사용자 입력에서 중요했다. 

따라서 일반 영문 단어는 최소 길이 조건을 높게 유지하면서 두 글자 한글 이름은 별도로 탐지하도록 구분했다.

## 5. 엔트로피만 믿었을 때 생긴 문제

개발 초기에 가장 크게 드러난 문제는 길이와 문자 종류로 계산한 탐색 공간이 

실제 사람이 만든 비밀번호의 예측 가능성을 충분히 설명하지 못한다는 점이었다.

다음 문자열은 18자이고 대문자, 소문자, 숫자, 특수문자를 모두 포함한다.

```text
ababab20050621!!AA
```

단순 무차별 대입 계산만 적용하면 매우 긴 시간이 나올 수 있다. 

하지만 공격자는 모든 조합을 처음부터 확인하기보다 다음 구조를 먼저 시도할 수 있다.

- `ababab`: 문자열 블록 반복
- `20050621`: 생년월일로 해석 가능한 날짜
- `!!`: 흔한 특수문자 반복
- 전체 구조: 반복 문자열 + 날짜 + 접미 문자

그래서 최종 예상 시간은 Brute Force 하나만 사용하지 않고 세 가지 공격 모델을 각각 계산한 뒤, 

공격자에게 가장 유리한 방법을 대표 결과로 선택했다.

### Brute Force Attack

비밀번호 길이와 사용된 문자 집합의 크기로 전체 탐색 공간을 계산한다.

```text
문자 집합 크기 ^ 비밀번호 길이
```

### Dictionary Attack

이름, 지역명, 서비스명, 일반 사전 단어 또는 다단어 패스프레이즈 구조를 반영한다.

### Pattern-based Attack

날짜, 연도, 반복 문자열, 키보드 배열, 흔한 비밀번호와 예측 가능한 전체 구조를 반영한다.

화면에는 하나의 확정 시간을 단정하지 않고 다음 세 환경의 범위를 표시했다.

- 온라인 공격: 초당 100회
- 느린 해시 오프라인 공격: 초당 10만 회
- 빠른 해시 오프라인 공격: 초당 100억 회

실제 시간은 서버의 요청 제한, 해시 알고리즘, 솔트, 하드웨어, 유출된 개인정보와 

공격 규칙에 따라 크게 달라진다는 설명도 함께 표시했다.

## 6. 화면마다 달랐던 결과와 하드코딩 제거

통합 초기에는 같은 비밀번호인데도 화면마다 예상 시간이 다르게 나왔다. 

1차 분석 완료 화면에서는 `수백만 년 이상`이라고 표시되지만 결과 비교 화면에서는 `수 분 이내`라고 표시되는 식이었다.

원인은 각 화면에 예시용 점수, 길이, 감점 요인과 예상 시간 문구가 따로 하드코딩되어 있었기 때문이다. 

분석기는 계산하고 있었지만 일부 화면은 그 결과를 사용하지 않았다.

이를 다음 구조로 바꾸었다.

```text
사용자 입력
→ analyzePassword() 한 번 실행
→ AnalysisResult 생성
→ 시뮬레이션 화면
→ 분석 결과 화면
→ 힌트 화면
→ 1·2차 비교 화면
```

모든 화면이 하나의 `AnalysisResult`를 공유하게 만들고 다음 값을 결과 객체에서 직접 읽도록 했다.

```text
score
grade
issues
attacks
hints
metrics
recommendedAttackName
estimatedTimes
```

이 변경으로 점수, 감점 항목, 공격 저항성, 개선 힌트와 비교 화면이 동일한 분석 기준을 사용하게 됐다.

## 7. 다단어 패스프레이즈 계산 개선

최종 QA 중 사전 단어가 하나라도 탐지되면 Dictionary Attack의 시도 횟수를 고정값으로 처리하는 문제를 발견했다.

그 결과 다음처럼 여러 단어를 조합한 긴 패스프레이즈도 단일 사전 단어와 비슷하게 `수 분` 수준으로 표시됐다.

```text
mint-river-cloud-lamp
violet train orbit canvas maple
```

이는 시작 퀴즈에서 설명한 내용과 실제 분석 결과가 충돌하는 문제였다. 

이를 해결하기 위해 다단어 패스프레이즈를 별도로 판정했다.

다단어 패스프레이즈의 조건은 다음과 같다.

- 전체 길이 16자 이상
- 4개 이상의 단어
- 각 단어가 3자 이상
- 공백, 하이픈 또는 밑줄로 구분
- 동일한 단어가 반복되지 않음

조건을 만족하면 단어 하나의 사전 공격 횟수가 아니라 다음과 같이 단어 조합의 경우의 수를 계산했다.

```text
후보 단어 수 ^ 단어 개수
```

반대로 다음 입력은 동일 단어 반복이므로 강한 패스프레이즈로 인정하지 않았다.

```text
password-password-password-password
```

최종 회귀 테스트의 대표 결과는 다음과 같았다.

| 테스트 입력 | 점수 | 등급 |
|---|---:|---|
| `123456` | 5 | 매우 약함 |
| `Minjun123!` | 30 | 약함 |
| `aaaaaaaaaaaa` | 43 | 약함 |
| `Ulsan2026!` | 52 | 보통 |
| `mint-river-cloud-lamp` | 100 | 매우 강함 |
| `River-Mango_47!Orbit` | 100 | 매우 강함 |

이 점수는 절대적인 보안 인증이 아니라 설정한 교육용 규칙에서 상대적인 차이를 보여주기 위한 값이다. 

높은 점수를 받은 예시도 실제 계정에서 그대로 사용해서는 안 된다.

## 8. Python과 웹 분석 결과 맞추기

처음에는 Python 분석 프로그램에서 나온 결과와 웹 화면의 결과가 달랐다. 

Python에서는 날짜와 반복 패턴을 탐지했지만 웹에서는 일부 항목이 빠지거나 감점 점수가 달라지는 경우가 있었다.

Python과 TypeScript 구현을 눈으로 비교하는 방식만으로는 수정할 때마다 차이가 다시 생길 가능성이 컸다. 

그래서 같은 테스트 데이터를 두 분석기에 넣고 다음 결과를 자동으로 비교하는 스크립트를 만들었다.

- 최종 점수
- 등급
- 적용된 감점 항목과 점수
- 공격 환경별 예상 시간
- 두 글자 한글 이름 탐지
- `5월12일` 형태 날짜 탐지
- 빈값과 공백 입력 차단
- 다단어 패스프레이즈 판정
- 반복 단어 패스프레이즈 차단

대표 테스트 입력은 다음과 같다.

```text
ababab20050621!!AA
Minjun123!
김민준20050512!
0512
123456
aaaaaaaaaaaa
abc123
Ulsan2026!
mint-river-cloud-lamp
River-Mango_47!Orbit
```

Python 구현은 `reference/python-analyzer/`에 기준 자료로 보존하고, 실제 웹은 브라우저용 TypeScript 분석기를 사용한다. 

이후 분석 규칙을 바꾸더라도 비교 테스트가 기존 점수의 의도하지 않은 변화를 바로 알려주도록 했다.

## 9. 빈값·공백·과도하게 긴 입력 처리

입력 화면에서는 스페이스만 네 번 눌러도 문자열 길이가 4로 계산되어 분석 버튼이 활성화되는 문제가 있었다.

다음 입력은 모두 유효한 비밀번호로 인식하지 않도록 수정했다.

```text
""
" "
"    "
"\t\n"
```

단순히 입력값 전체를 `trim()`한 뒤 분석하면 공백이 포함된 정상 패스프레이즈의 원문까지 달라질 수 있다. 

따라서 공백으로만 구성되었는지를 분석 진입 전에 검사하고, 정상 문자열은 입력한 그대로 분석했다.

또한 과도하게 긴 문자열을 붙여 넣었을 때 반복·패턴 탐색 비용이 커지는 것을 막기 위해 

웹과 Python 분석기 모두 최대 256자로 제한했다.

비밀번호 표시 버튼은 마우스로만 사용할 수 있었던 `tabIndex=-1`을 제거하고 

`aria-label`, `aria-pressed`를 추가해 키보드와 보조기기에서도 상태를 확인할 수 있게 했다.

## 10. Flask·MySQL 랭킹 서버 구현

비밀번호 분석은 브라우저에서 끝나지만 부스 참가자끼리 결과를 비교할 수 있도록 닉네임 기반 랭킹 API를 만들었다.

서버에 저장하는 데이터는 다음과 같다.

```text
nickname
first_score
second_score
improvement_score
event_date
created_at
```

비밀번호 원문, 해시와 탐지된 문자열 조각은 API 요청 대상에서 제외했다. 

개선 점수는 클라이언트 값을 신뢰하지 않고 서버에서 계산했다.

```text
improvement_score = second_score - first_score
```

### API 구성

| 메서드 | 경로 | 기능 |
|---|---|---|
| `GET` | `/api/health` | 서버 프로세스 상태 확인 |
| `GET` | `/api/ready` | MySQL 연결을 포함한 준비 상태 확인 |
| `POST` | `/api/participants` | 닉네임과 1·2차 점수 저장 |
| `GET` | `/api/rankings/security` | 당일 2차 점수 랭킹 조회 |
| `GET` | `/api/rankings/improvement` | 당일 개선 점수 랭킹 조회 |
| `GET` | `/api/statistics` | 당일 참가자 수와 평균 조회 |
| `DELETE` | `/api/admin/rankings` | 관리자 인증 후 당일 랭킹 초기화 |

보안 랭킹은 2차 점수가 높은 순서로, 개선 랭킹은 `2차 점수 - 1차 점수`가 높은 순서로 정렬한다. 

동점이면 먼저 참가한 기록을 우선하며 화면에는 당일 상위 100명까지 표시한다.

같은 날짜에 같은 닉네임을 반복 등록하지 못하도록 `(event_date, nickname)`에 UNIQUE 제약을 적용했다.

### 입력 및 오류 처리

- 닉네임은 공백을 제거한 뒤 2~20자만 허용
- 점수는 정수형 0~100만 허용
- JSON 요청 크기는 4KB로 제한
- 참가자 등록은 IP당 분당 10회로 제한
- 전체 API 기본 요청은 분당 60회로 제한
- 중복 닉네임은 HTTP 409 반환
- 잘못된 입력은 HTTP 400 반환
- DB 준비 실패는 HTTP 503 반환
- 내부 예외 내용과 접속정보는 사용자 응답에 포함하지 않음

관리자 초기화 API는 `X-Admin-Token` 헤더가 없거나 일치하지 않으면 HTTP 403으로 거부한다. 

토큰 비교에는 일반 문자열 비교 대신 timing 차이를 줄이는 `hmac.compare_digest()`를 사용했다.

## 11. 개인정보와 배포 보안

보안 교육 프로그램이 참가자의 비밀번호를 수집한다면 프로젝트 목적 자체와 충돌한다. 

그래서 기능 구현보다 먼저 데이터 흐름을 명확히 정했다.

```text
사용자 브라우저
├─ 비밀번호 원문: 브라우저 내부 상태에서만 사용
├─ 분석 결과: 브라우저에서 계산
└─ 닉네임 + 1차 점수 + 2차 점수만 API 전송
                         ↓
                    Flask API
                         ↓
                       MySQL
```

브라우저의 `localStorage`에는 라이트·다크 테마 설정만 저장한다. 

비밀번호는 쿠키, Local Storage, Session Storage, IndexedDB와 서버 DB에 기록하지 않는다. 

체험 완료 후 `처음부터 다시 체험하기`를 누르면 React 상태를 초기값으로 교체해 

이전 참가자의 비밀번호, 닉네임과 점수를 제거한다.

백엔드에는 다음 보안 설정을 적용했다.

- 허용된 Vercel 주소만 접근할 수 있는 CORS
- Content Security Policy
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- Referrer Policy
- Permissions Policy
- HTTPS 환경의 HSTS
- 요청 크기 및 횟수 제한
- SQL 파라미터 바인딩
- 운영 환경 필수 변수 검사

데이터베이스 주소, 계정, 비밀번호와 관리자 토큰은 소스코드가 아니라 Railway 환경변수에 저장했다. 

배포 전 Git 전체 기록과 현재 Railway 비밀번호를 비교해 운영 비밀번호가 과거 기록에 남아 있지 않은 것도 확인했다.

## 12. Vercel과 Railway 배포

프론트엔드는 Vercel, Flask API와 MySQL은 Railway를 사용했다.

### Railway 백엔드

Railway 프로젝트를 GitHub 저장소에 연결한 뒤 다음과 같이 설정했다.

```text
Source Branch: integration
Root Directory: /server
Start Command: gunicorn app:app --bind 0.0.0.0:$PORT
Health Check Path: /api/health
```

등록한 주요 환경변수는 다음과 같다.

```text
APP_ENV=production
DB_HOST
DB_PORT
DB_USER
DB_PASSWORD
DB_NAME
ALLOWED_ORIGINS
ADMIN_RESET_TOKEN
```

처음에는 Railway가 저장소 루트의 프론트엔드를 Node 프로젝트로 인식했다. 

백엔드 코드가 있는 `/server`를 Root Directory로 지정하고 

Gunicorn 시작 명령을 설정한 뒤에야 Python·Flask 서비스로 정상 배포됐다.

단순 프로세스 실행 여부는 `/api/health`, 실제 DB까지 연결할 수 있는지는 `/api/ready`로 분리했다. 

서버는 켜졌지만 DB 연결이 끊긴 상태를 구분할 수 있어 배포 확인과 현장 장애 대응이 쉬워졌다.

### Vercel 프론트엔드

프론트엔드가 Railway API를 바라보도록 Vercel Production 환경에 다음 값을 등록했다.

```text
VITE_API_BASE_URL=https://password-cracking-lab-production-417a.up.railway.app
```

Vite 환경변수는 빌드 시점에 JavaScript 파일에 포함된다. 

변수를 저장하는 것만으로 기존 배포가 바뀌지 않았기 때문에 Production을 다시 배포했다.

이 설정 전에는 랭킹 화면에서 `API 서버 주소가 설정되지 않았습니다`라는 오류가 발생했다. 

재배포 이후 실제 빌드 파일에 Railway 주소가 포함됐는지 확인하고, 

Vercel Origin으로 보낸 CORS 사전 요청도 정상 응답하는지 검증했다.

## 13. 모바일 화면과 접근성 보완

데스크톱 중심으로 만든 초기 화면은 390px 모바일 환경에서 다음 문제가 있었다.

- 퀴즈와 결과 카드가 2열로 고정됨
- 분석 결과가 `280px + 나머지` 구조로 고정됨
- 점수 비교 화면이 3열로 고정됨
- 헤더 진행률과 단계 표시가 화면 밖으로 밀림
- 시작 화면 기능 카드가 전체 페이지 너비를 늘림
- 하단 실제 비밀번호 금지 안내가 잘림

700px 이하에서는 주요 Grid를 한 열로 바꾸고, 헤더의 부가 설명과 진행 표시를 간소화했다. 

푸터 버튼은 화면 너비에 맞춰 접히도록 했고 긴 한글 문구에는 명시적인 줄바꿈 규칙을 적용했다.

수정 후 Chrome DevTools Protocol로 실제 모바일 뷰포트를 강제하고 문서의 너비를 측정했다.

```text
innerWidth: 390
clientWidth: 390
scrollWidth: 390
horizontal overflow: false
```

단순히 스크린샷이 보기 좋은지만 확인하지 않고 

브라우저가 계산한 `scrollWidth`와 `clientWidth`가 같은지 검사해 가로 스크롤이 없다는 것을 확인했다.

## 14. 최종 QA와 자동 테스트

부스 운영 전날에는 코드, 배포, 개인정보, 모바일과 실제 사용자 흐름을 다시 점검했다.

### 분석기 회귀 테스트

약한 비밀번호, 반복 패턴, 이름, 날짜, 한글, 패스프레이즈와 긴 입력을 Python·TypeScript 분석기에 함께 넣었다. 

기존 약한 비밀번호의 점수가 의도하지 않게 올라가지 않았는지, 수정한 패스프레이즈만 올바르게 평가되는지 확인했다.

### 백엔드 테스트

Flask 테스트 클라이언트와 Mock DB를 사용해 다음 8개 테스트를 실행했다.

- 관리자 토큰 없는 초기화 거부
- Health API 및 보안 헤더
- 요청 크기 초과 시 JSON 오류
- 참가자 저장 및 랭킹 계약
- 닉네임·점수 유효성 검사
- 운영 환경 필수 변수 검사
- Ready API의 DB 확인
- DB 장애 시 내부정보 없는 오류 응답

### 실제 배포 API 테스트

```text
/api/health                 200
/api/ready                  200
/api/rankings/security      200
/api/rankings/improvement   200
/api/statistics             200
```

빈 참가자 요청은 400, 관리자 토큰 없는 초기화는 403, 중복 닉네임은 409가 반환되는지 확인했다. 

프론트엔드 Production과 Railway 서비스가 동일한 `integration` 커밋을 배포하고 있는지도 대조했다.

프론트엔드와 백엔드 Python 의존성의 알려진 취약점을 검사했으며 최종 점검 당시 발견된 항목은 없었다.

### 실제 브라우저 End-to-End 테스트

Chrome에서 390×844 모바일 환경으로 다음 흐름을 자동 실행했다.

```text
체험 시작
→ 안내 확인
→ 퀴즈 B 선택
→ 1차에 공백 입력 후 버튼 비활성화 확인
→ 1차에 123456 입력
→ 5점·매우 약함 확인
→ 개선 힌트 확인
→ 2차에 mint-river-cloud-lamp 입력
→ 100점 확인
→ 점수 향상 비교 확인
→ 랭킹 건너뛰기
→ 체험 완료
→ 처음부터 다시 시작
```

전체 과정의 네트워크 요청도 함께 수집했다. 

요청 URL과 본문 어디에도 `123456`이나 `mint-river-cloud-lamp`가 포함되지 않았고, 

마지막 초기화 후 입력 요소와 이전 상태가 남지 않은 것을 확인했다.

행사 직전까지 사용한 테스트 랭킹 데이터는 관리자 API로 삭제했다. 

최종 확인 당시 보안 랭킹과 개선 랭킹은 빈 배열, 참가자 통계는 0명인 상태에서 부스 운영을 시작했다.

## 15. 부스 운영

개발을 마친 뒤 실제 부스에서 Password Cracking Lab을 운영했다. 

부스에서는 한 번의 점수 확인으로 끝내지 않고 1차 결과에서 약점을 발견하고 2차에서 직접 개선하도록 안내했다.

운영 흐름은 다음과 같이 정리했다.

```text
실제 비밀번호 입력 금지 안내
→ 참가자 체험 시작
→ 필요한 경우에만 조작 도움
→ 점수보다 감점 이유를 먼저 확인
→ 2차 비밀번호 개선
→ 1·2차 차이 확인
→ 개인정보가 없는 닉네임으로 랭킹 등록 또는 건너뛰기
→ MFA·비밀번호 관리자·패스키 안내
→ 완료 후 처음 화면으로 초기화
```

시작 전 안내 멘트도 짧게 통일했다.

실제로 사용 중인 비밀번호는 입력하지 말고 지금 새로 만든 테스트용 문자열만 사용해 주세요.

점수와 예상 시간은 교육용 결과이며 실제 해킹 시간을 보증하지 않습니다.

결과 화면에서는 높은 점수 자체보다 왜 감점되었는지 먼저 보도록 안내했다. 참가자가 2차 입력을 어떻게 바꿔야 할지 막히면 정답 비밀번호를 대신 알려주는 것이 아니라 다음 원칙 중 하나를 적용하도록 유도했다.

- 이름, 생일, 지역명과 현재 연도 제거
- 반복 문자열과 `123`, `qwerty` 같은 순서 제거
- 단어 뒤에 연도와 `!`만 붙이는 구조 변경
- 서로 관련 없는 단어를 여러 개 조합해 길이 확보

체험 마지막에는 비밀번호 점수만 믿지 말고 실제 계정에서는 서비스마다 

다른 비밀번호를 사용하며 비밀번호 관리자, MFA와 패스키를 함께 활용해야 한다고 설명했다.

부스 운영까지 진행해 보니 개발 환경에서 기능이 작동하는 것과 여러 사람이 연속해서 사용하는 프로그램은 다르다는 점을 체감했다. 참가자 한 명의 체험이 끝난 뒤 다음 사람에게 이전 입력과 닉네임이 보이지 않는지 확인하는 과정, 네트워크 장애가 발생해도 비밀번호 분석 자체는 브라우저에서 계속할 수 있도록 분리한 구조, 테스트 랭킹을 행사 시작 전에 정리하는 절차가 실제 운영에서는 특히 중요했다.

## 17. 프로젝트를 통해 배운 점

처음에는 비밀번호 분석 규칙을 많이 넣는 것이 프로젝트의 핵심이라고 생각했다. 실제로 가장 많은 시간이 필요했던 부분은 규칙의 개수가 아니라 **같은 입력에 대해 모든 화면이 일관된 설명을 하도록 만드는 것**이었다.

점수가 80점인데 예상 해독 시간이 수 분으로 표시되거나, 

Python에서는 날짜를 탐지했지만 웹에서는 감점 요인에 나타나지 않는다면 사용자는 어떤 결과를 믿어야 할지 알 수 없다. 

보안 프로그램에서는 화려한 공격 애니메이션보다 계산 근거와 안내 문구의 일관성이 더 중요했다.

또한 보안 기능은 백엔드에만 넣는다고 완성되지 않았다. 

브라우저가 어떤 데이터를 보내는지, 프론트 화면이 개인정보 입력을 유도하지 않는지, 

환경변수가 실제 Production 빌드에 들어갔는지, 관리자 기능이 외부 요청을 거부하는지까지 전체 흐름을 확인해야 했다.

특히 다음 내용을 직접 경험했다.

1. **Git에 올라간 비밀 값은 파일에서 지우는 것만으로 해결되지 않는다.**  
   과거 커밋에 남아 있기 때문에 실제 비밀번호를 교체하고 기록까지 확인해야 한다.

2. **환경변수는 등록 위치와 적용 시점이 중요하다.**  
   Vite 변수는 빌드 시점에 고정되며, Railway의 서비스 경로와 실행 명령도 올바르게 지정해야 한다.

3. **분석 로직과 표시 로직을 분리해야 한다.**  
   계산 결과를 하나의 객체로 만들고 모든 화면이 이를 사용해야 하드코딩과 불일치를 줄일 수 있다.

4. **점수는 설명보다 앞설 수 없다.**  
   왜 감점되었고 어떻게 개선해야 하는지 전달되지 않으면 교육용 프로그램의 의미가 줄어든다.

5. **배포 성공은 QA의 끝이 아니다.**  
   실제 URL, DB, CORS, 모바일 화면과 처음부터 끝까지 이어지는 사용자 흐름을 확인해야 한다.

6. **부스 프로그램은 다음 참가자까지 고려해야 한다.**  
   한 번의 체험이 성공하는 것뿐 아니라 이전 상태를 안전하게 지우고 다음 회차를 시작할 수 있어야 한다.

## 18. 아쉬운 점과 개선하고 싶은 부분

이번 버전은 실제 부스 운영까지 가능한 형태로 완성했지만 개선할 부분도 남아 있다.

- 관리자 전용 랭킹 관리 화면
- 날짜별 통계 및 CSV 내보내기
- 행사 종료 후 데이터 보존·삭제 정책 자동화
- Redis 기반 공용 Rate Limit
- 더 넓은 한국어 이름·지역명·서비스명 데이터
- 다단어 패스프레이즈 어휘 규모와 선택 편향에 대한 세분화
- Playwright 기반 전체 화면 E2E 테스트 상시 실행
- 스크린 리더와 200% 확대 접근성 추가 검증
- 서버 장애 시 랭킹만 건너뛰고 분석 체험을 자연스럽게 계속하는 UI
- 실제 해시 알고리즘별 교육 시나리오 선택

예상 해독 시간은 실제 공격 결과가 아니라 가정을 설명하기 위한 교육용 모델이다. 이후에는 해시 종류와 공격 환경을 사용자가 선택하고, 조건에 따라 결과가 왜 달라지는지 비교하는 기능을 추가해 보고 싶다.

## 마무리

Password Cracking Lab은 비밀번호를 대신 만들어 주거나 실제 계정을 공격하는 프로그램이 아니다. 

사용자가 테스트 문자열을 직접 만들고, 그 안에 포함된 이름·날짜·반복·키보드 배열과 흔한 구조를 눈으로 확인한 뒤 

더 나은 방식으로 개선하도록 돕는 체험형 교육 프로젝트다.

개발을 시작할 때는 점수 계산이 가장 어려울 것이라고 생각했다. 

하지만 프로젝트를 끝내고 부스까지 운영해 보니 더 중요했던 것은 분석 결과의 일관성, 

개인정보를 보내지 않는 구조, 실제 배포 환경의 안전한 설정, 

그리고 처음 보는 참가자도 짧은 시간 안에 이해할 수 있는 설명이었다.

프론트엔드, Python 분석기, Flask API와 MySQL이 각각 동작하는 것만으로는 하나의 서비스가 되지 않았다. 

브랜치를 통합하고 데이터 규격을 맞추고, 하드코딩을 제거하고, 

환경변수와 CORS를 연결하고, 실제 모바일 브라우저에서 마지막 화면까지 확인한 뒤에야 하나의 체험으로 완성됐다.

무엇보다 보안 교육 프로그램을 만들면서 비밀번호 원문을 수집하지 않는 원칙을 끝까지 유지했다는 점이 가장 의미 있었다. 

참가자가 점수 하나만 기억하기보다 다음 원칙을 기억하고 돌아갔기를 바란다.

길고 예측하기 어려운 비밀번호를 사용하고, 서비스마다 재사용하지 말자.  
가능하다면 비밀번호 관리자와 MFA, 패스키를 함께 사용하자.

기획에서 시작해 실제 부스 운영으로 마무리한 이번 프로젝트는, 

코드를 구현하는 것과 실제 사람이 안전하게 사용할 수 있는 서비스를 만드는 것 사이의 차이를 배울 수 있었던 경험이었다.
