# EIP-1559 분석, Ethereum Gas Fee 구조는 왜 바뀌었을까?

## 1. 들어가며

Ethereum을 사용하다 보면 거의 모든 Transaction에서 **Gas Fee**를 지불하게 된다.

ETH를 다른 주소로 보내는 단순한 Transaction부터 ERC-20 Token 전송,

NFT 거래, DEX Swap, Smart Contract 실행까지 Ethereum의 연산을 사용하려면 Gas가 필요하다.

처음에는 Gas Fee를 단순히

```
Ethereum을 사용하기 위해 내는 수수료

```

정도로 생각했다.

하지만 Gas 구조를 공부하다 보니 현재 Ethereum에서 사용하는 수수료 방식이 처음부터 지금과 같았던 것은 아니었다.

과거 Ethereum에서는 사용자가 gasPrice를 제시하고 높은 수수료를 제시한 Transaction이

우선적으로 선택되는 **First-Price Auction과 유사한 구조**를 사용했다.

이 방식에는 사용자가 적절한 Gas Price를 예측하기 어렵고,

네트워크가 혼잡해지면 사용자끼리 더 높은 수수료를 제시하면서 Gas Fee가 크게 변하는 문제가 있었다.

이러한 Ethereum의 Fee Market을 개선하기 위해 등장한 것이 **EIP-1559**이다.

EIP-1559에서는 기존의 단일 gasPrice 중심 구조를

```
Base Fee
+
Priority Fee

```

로 분리하고,

사용자가 지불할 최대 가격을

```
Max Fee

```

로 제한할 수 있도록 했다.

또한 Base Fee는 Validator에게 지급되지 않고 **Burn**된다.

이번 글에서는 기존 Ethereum Gas Fee 방식에 어떤 문제가 있었는지부터 시작해서

EIP-1559의 Base Fee, Priority Fee, Max Fee가 각각 어떤 역할을 하는지 살펴보고

실제 Transaction Fee가 어떻게 계산되는지 정리해보았다.

---

# 2. 먼저 Gas란 무엇일까?

EIP-1559를 이해하기 전에 먼저 Gas의 개념부터 정리할 필요가 있다.

Ethereum에서 Smart Contract를 실행하면 EVM이 여러 연산을 수행한다.

예를 들어

```
ADD
SSTORE
SLOAD
CALL

```

같은 연산들이 실행된다.

각 연산에는 필요한 계산 자원이 다르기 때문에 Ethereum에서는

각 작업에 일정한 **Gas 비용**을 부여한다.

따라서

```
Gas = Ethereum에서 연산량을 측정하는 단위

```

라고 생각할 수 있다.

예를 들어 단순 ETH 전송에는 기본적으로 21,000 Gas가 사용된다.

반면 복잡한 Smart Contract를 실행하면 훨씬 많은 Gas가 필요할 수 있다.

```
ETH Transfer
     ↓
21,000 Gas


Smart Contract
     ↓
더 많은 Gas

```

중요한 것은 **Gas와 ETH를 구분하는 것**이다.

Gas 자체는 연산량을 나타내는 단위이고 실제로 사용자가 지불하는 비용은 Gas에 Gas Price를 곱해서 계산한다.

---

# 3. Gas Limit은 무엇일까?

Transaction을 만들 때 자주 볼 수 있는 값 중 하나가

```
Gas Limit

```

이다.

Gas Limit은 해당 Transaction이 사용할 수 있는 최대 Gas의 양이다.

예를 들어

```
Gas Limit = 100,000

```

이라면 Transaction 실행에 최대 100,000 Gas까지 사용할 수 있도록 설정한 것이다.

실제 실행 결과

```
Gas Used = 60,000

```

이라면 실제 비용 계산은 사용된 60,000 Gas를 기준으로 이루어진다.

즉

```
Gas Limit ≠ 실제 Gas Fee

```

이다.

Gas Limit은 어디까지 Gas를 사용할 수 있는지에 대한 한도이고, 실제 비용은 Gas Used와 실제 Gas Price를 기준으로 결정된다.

---

# 4. 기존 Ethereum의 Gas Fee 방식

EIP-1559 이전에는 Transaction을 생성하면서 사용자가 주로 다음 값을 지정했다.

```
gasPrice

```

예를 들어

```
Alice : 20 Gwei
Bob   : 30 Gwei
Carol : 50 Gwei

```

의 Transaction이 Pending 상태라고 가정해보자.

Block Producer 입장에서는 높은 Gas Price를 제시한 Transaction을 먼저 포함시키는 것이 경제적으로 유리하다.

따라서 개념적으로

```
Carol : 50 Gwei
      ↓
Bob   : 30 Gwei
      ↓
Alice : 20 Gwei

```

순으로 우선순위가 형성될 수 있다.

이러한 방식은 사용자가 자신이 지불할 Gas Price를 직접 제시하고 경쟁하는 **First-Price Auction** 형태와 유사하다.

---

# 5. 기존 방식의 문제점

이 방식에서 가장 큰 문제 중 하나는 Gas Price를 얼마로 설정해야 하는가? 였다.

사용자는 현재 다른 사람들이 어느 정도의 Gas Price를 제시하는지 추정해야 한다.

너무 낮게 설정하면

```
Gas Price 너무 낮음
        ↓
Transaction Pending
        ↓
Block에 포함되지 않음

```

이 될 수 있다.

반대로 너무 높게 설정하면

```
필요한 Gas Price : 30 Gwei

사용자가 제시 : 100 Gwei

        ↓

불필요하게 높은 Fee 지불

```

이 될 수 있다.

네트워크가 혼잡할 때는 사용자들이 서로 더 높은 Gas Price를 제시하려고 하면서 수수료 예측이 더욱 어려워질 수 있다.

EIP-1559 공식 제안에서도 기존 경매 방식에서 정확한 수수료 추정이 어렵고

사용자가 필요 이상으로 많은 수수료를 지불할 수 있다는 점을 주요 문제로 설명한다.

---

# 6. EIP-1559의 등장

EIP-1559는 Ethereum Transaction Fee 구조를 크게 변경했다.

핵심은 기존의

```
gasPrice

```

하나를 중심으로 한 구조에서 벗어나 수수료를 여러 요소로 나눈 것이다.

대표적인 값은 다음과 같다.

```
Base Fee

Priority Fee

Max Fee

```

이를 단순화하면 다음과 같다.

```
Transaction Fee

       │
       ├── Base Fee
       │
       │
       └── Priority Fee

```

그리고 사용자는

```
Max Fee

```

를 통해 자신이 Gas 한 단위당 최대 얼마까지 지불할 것인지 제한할 수 있다.

---

# 7. Base Fee

EIP-1559에서 가장 중요한 개념이 **Base Fee**다.

```
baseFeePerGas

```

Base Fee는 사용자가 임의로 정하는 값이 아니다.

Ethereum Protocol이 네트워크의 Block 사용량을 바탕으로 결정한다.

Transaction이 Block에 포함되기 위해서는 기본적으로 해당 Block의 Base Fee를 감당할 수 있어야 한다.

예를 들어 현재 Base Fee가

```
20 Gwei

```

라면 해당 Block에 포함되는 EIP-1559 Transaction은 최소한 이 Base Fee를 충족할 수 있어야 한다.

---

# 8. Base Fee는 어떻게 변할까?

EIP-1559에서는 Block의 Gas 사용량을 기준으로 Base Fee를 조절한다.

기본적인 아이디어는 간단하다.

```
Block 사용량 많음
       ↓
Network 혼잡
       ↓
Base Fee 증가

```

반대로

```
Block 사용량 적음
       ↓
Network 여유
       ↓
Base Fee 감소

```

이다.

즉 Base Fee 자체가 네트워크 수요에 따라 자동으로 조절된다.

사용자들이 직접 적절한 기본 가격을 계속 추측하도록 하기보다는 Protocol이 일정한 규칙에 따라 Base Fee를 조정한다.

---

# 9. Target Block Size

EIP-1559에서는 Block의 **Target Gas Usage**라는 개념이 중요하다.

Block에는 최대 Gas Limit이 존재하지만 EIP-1559는 평균적으로 그 최대치를 항상 채우는 것을 목표로 하지 않는다.

개념적으로

```
Maximum Block Gas
        │
        │
        ├─────────────
        │
Target  │ 약 절반
        │
        ├─────────────
        │
        │

```

와 같은 구조다.

Target보다 Gas 사용량이 많으면 다음 Block의 Base Fee가 증가한다.

```
Gas Used > Target
        ↓
Base Fee ↑

```

반대로 Target보다 적으면

```
Gas Used < Target
        ↓
Base Fee ↓

```

한다.

Target과 정확히 같다면 Base Fee가 유지된다.

```
Gas Used = Target
        ↓
Base Fee 유지

```

---

# 10. 왜 Block 크기를 유동적으로 만들었을까?

항상 고정된 Block 크기만 사용하면 갑자기 Transaction이 몰리는 순간 바로 경쟁이 심해질 수 있다.

EIP-1559에서는 짧은 시간 동안 Transaction 수요가 증가했을 때 Block이 Target보다 커질 수 있도록 했다.

개념적으로

```
평소

████████░░░░░░░░
Target


갑작스러운 수요 증가

██████████████░░
Target 초과

```

가 가능하다.

하지만 계속 큰 Block을 사용하면 Base Fee가 증가한다.

```
큰 Block
   ↓
Base Fee 증가
   ↓
수요 감소 유도
   ↓
Target으로 복귀

```

하는 피드백 구조를 가진다.

EIP-1559에서 최대 Block Gas는 Target의 2배까지 허용되는 구조를 사용한다.

---

# 11. Base Fee는 누가 가져갈까?

EIP-1559에서 가장 특징적인 부분 중 하나다.

사용자가 지불한 Base Fee는 Validator에게 지급되지 않는다.

```
User
 │
 │ Base Fee
 ▼
Burn

```

즉 **소각된다.**

ETH가 특정 주소의 수익으로 지급되는 것이 아니라 유통량에서 제거된다.

예를 들어 Transaction에서

```
Base Fee로 0.001 ETH

```

가 사용됐다면 해당 ETH는 Burn된다.

---

# 12. 왜 Base Fee를 Burn할까?

처음에는 굳이 수수료를 소각할 이유가 무엇인지 궁금했다.

Block Producer가 Base Fee를 그대로 받는다면 자신이 받게 될 Base Fee에

영향을 주기 위해 Fee Market을 조작하려는 경제적 유인이 생길 수 있다.

Base Fee를 Burn하면

```
Base Fee 증가

     ≠

Validator의 직접 수익 증가

```

가 된다.

즉 Base Fee를 Validator가 직접 가져가지 못하도록 하여 Base Fee 조작에 대한 경제적 유인을 줄이는 효과가 있다.

그리고 Base Fee가 Burn되기 때문에 EIP-1559는 Ethereum의 ETH 공급량에도 영향을 미친다.

---

# 13. Priority Fee

그렇다면 Validator는 Transaction을 포함해서 무엇을 받을까?

여기서 등장하는 것이 **Priority Fee**다.

```
maxPriorityFeePerGas

```

Priority Fee는 흔히 **Tip**이라고도 부른다.

사용자가 Block Producer에게

"내 Transaction을 Block에 포함시켜주면 추가로 이만큼 지불하겠다." 라고 제시하는 값이다.

구조를 보면

```
User
 │
 ├── Base Fee ───────→ Burn
 │
 └── Priority Fee ──→ Validator

```

가 된다.

---

# 14. Priority Fee는 왜 필요할까?

Base Fee만 존재한다면 여러 Transaction이 동일한 Base Fee 조건을 충족했을 때

어떤 Transaction을 먼저 처리할지에 대한 추가적인 경제적 인센티브가 부족할 수 있다.

Priority Fee를 이용하면 사용자는 자신의 Transaction 처리 우선순위에 대한 추가적인 Tip을 제시할 수 있다.

예를 들어

```
Alice
Priority Fee = 1 Gwei

Bob
Priority Fee = 3 Gwei

Carol
Priority Fee = 5 Gwei

```

와 같이 설정할 수 있다.

다른 조건이 동일하다면 높은 Priority Fee는 Block Producer에게 더 높은 수익을 제공한다.

---

# 15. Max Fee

EIP-1559에는 또 하나 중요한 값이 있다.

```
maxFeePerGas

```

Max Fee는 사용자가

"Gas 1단위당 최대 여기까지는 지불할 수 있다." 라고 설정하는 상한선이다.

예를 들어

```
maxFeePerGas = 100 Gwei

```

라면 사용자는 Gas 한 단위당 100 Gwei를 초과해서 지불하지 않겠다는 의미다.

이 값에는

```
Base Fee + Priority Fee

```

가 모두 포함된다.

---

# 16. 세 값을 한 번에 정리해보기

예를 들어 사용자가 다음과 같이 Transaction을 생성했다고 가정해보자.

```
Base Fee

30 Gwei


Max Priority Fee

2 Gwei


Max Fee

50 Gwei

```

Base Fee와 Priority Fee를 합치면

```
30 + 2
=
32 Gwei

```

이다.

Max Fee는 50 Gwei이므로 충분하다.

따라서 실제 Gas Price는

```
32 Gwei

```

가 될 수 있다.

---

# 17. Max Fee를 전부 지불하는 것은 아니다

처음에는 maxFeePerGas를 50 Gwei로 설정하면 무조건 50 Gwei를 지불하는 것으로 생각했다.

하지만 Max Fee는 **최대 한도**다.

예를 들어

```
Max Fee       = 50 Gwei
Base Fee      = 30 Gwei
Priority Fee  = 2 Gwei

```

라면

```
실제 Gas Price
=
30 + 2
=
32 Gwei

```

가 된다.

남는

```
50 - 32 = 18 Gwei

```

를 실제 사용 Gas마다 그대로 지불하는 것이 아니다.

Max Fee는 지불 가능한 상한을 설정하는 역할을 한다.

---

# 18. Effective Gas Price

실제로 적용되는 Gas Price는 개념적으로 다음과 같이 생각할 수 있다.

```
Effective Gas Price

= Base Fee
  +
  실제 Priority Fee

```

실제 Priority Fee는 사용자가 설정한 Max Priority Fee뿐만 아니라 Max Fee의 제한도 받는다.

단순화하면

```
Priority Fee

=
min(
    Max Priority Fee,
    Max Fee - Base Fee
)

```

이다.

따라서

```
Effective Gas Price

=
Base Fee
+
min(
    Max Priority Fee,
    Max Fee - Base Fee
)

```

로 이해할 수 있다.

---

# 19. 실제 계산해보기

다음과 같은 ETH Transfer가 있다고 가정해보자.

```
Gas Used = 21,000

Base Fee = 20 Gwei

Max Priority Fee = 2 Gwei

Max Fee = 50 Gwei

```

실제 Priority Fee는

```
2 Gwei

```

가 된다.

따라서 Effective Gas Price는

```
20 + 2

=

22 Gwei

```

이다.

전체 Transaction Fee는

```
21,000 × 22 Gwei

```

이다.

계산하면

```
462,000 Gwei

```

이고

```
0.000462 ETH

```

가 된다.

---

# 20. 이 중 Validator가 받는 금액

Priority Fee는

```
2 Gwei

```

이므로 Validator가 받는 금액은

```
21,000 × 2 Gwei

=

42,000 Gwei

```

이다.

ETH로 변환하면

```
0.000042 ETH

```

다.

---

# 21. Burn되는 ETH

Base Fee는

```
20 Gwei

```

이므로 Burn되는 ETH는

```
21,000 × 20 Gwei

=

420,000 Gwei

```

이다.

즉

```
0.00042 ETH

```

가 Burn된다.

전체를 정리하면

```
User

총 Gas Fee
0.000462 ETH

       │
       ├── 0.000420 ETH
       │       ↓
       │      Burn
       │
       └── 0.000042 ETH
               ↓
           Validator

```

가 된다.

---

# 22. Max Fee가 부족하면 어떻게 될까?

이번에는 다음 상황을 생각해보자.

```
Base Fee = 30 Gwei

Max Fee = 20 Gwei

```

사용자가 지불할 수 있다고 설정한 최대 Gas Price보다 현재 Base Fee 자체가 더 높다.

```
Max Fee < Base Fee

```

이므로 현재 조건에서는 Transaction을 해당 Block에 포함할 수 없다.

즉 Max Fee는 단순한 옵션이 아니라 Transaction이 어느 Base Fee 수준까지 감당할 수 있는지를 결정하는 중요한 값이다.

---

# 23. Base Fee가 갑자기 올라가면?

다음과 같이 설정했다고 생각해보자.

```
Max Fee = 50 Gwei

Max Priority Fee = 2 Gwei

```

처음 예상한 Base Fee는

```
30 Gwei

```

였다.

그런데 네트워크가 혼잡해져 실제 Block의 Base Fee가

```
49 Gwei

```

가 되었다고 가정해보자.

원래 원하는 Priority Fee는 2 Gwei이지만

```
49 + 2 = 51 Gwei

```

가 되어 Max Fee 50 Gwei를 초과한다.

따라서 실제 Priority Fee는

```
50 - 49

=

1 Gwei

```

까지만 가능하다.

즉 Max Fee가 전체 비용의 상한선 역할을 한다.

---

# 24. Type 2 Transaction

EIP-1559는 새로운 Transaction Type도 도입했다.

EIP-1559 Transaction은 일반적으로 **Type 2 Transaction**이라고 부른다.

Transaction에는 다음과 같은 필드들이 포함된다.

```
chainId
nonce

maxPriorityFeePerGas
maxFeePerGas

gasLimit

destination
amount
data

accessList

signature

```

기존 Legacy Transaction에서 사용하던 단순한 gasPrice 대신

```
maxPriorityFeePerGas

maxFeePerGas

```

가 들어간다는 것이 특징이다.

---

# 25. Etherscan에서 확인해보기

실제 Ethereum Transaction을 Etherscan에서 열어보면 EIP-1559와 관련된 여러 정보를 확인할 수 있다.

대표적으로

```
Gas Limit

Gas Used

Base Fee

Max Fee Per Gas

Max Priority Fee Per Gas

Burnt Fees

```

등을 볼 수 있다.

실제 Transaction을 하나 골라

```
Gas Used × Effective Gas Price

```

를 계산해보고 Etherscan에 표시되는 Transaction Fee와 비교해보면 EIP-1559 구조를 이해하는 데 도움이 된다.

또한

```
Gas Used × Base Fee

```

를 계산하여 실제 Burn된 ETH도 확인해볼 수 있다.

---

# 26. EIP-1559가 Gas Fee를 항상 싸게 만들어주는가?

EIP-1559에 대해 처음 접하면 EIP-1559가 Gas Fee를 낮춰주는 업데이트라고 생각할 수 있다.

하지만 정확히는 그렇지 않다.

네트워크에 Transaction 수요가 매우 많으면 Base Fee 자체가 증가한다.

```
높은 Network Demand
        ↓
Block 사용량 증가
        ↓
Base Fee 증가

```

따라서 네트워크가 혼잡하면 여전히 Gas Fee가 높아질 수 있다.

EIP-1559의 핵심은 Gas Fee를 항상 싸게 만드는 것이 아니라

**Fee Market을 더 예측 가능하게 만들고 수수료 추정 문제를 개선하는 것**에 가깝다.

---

# 27. Base Fee 변화의 특징

EIP-1559에서는 Base Fee가 Block마다 무제한으로 갑자기 변하는 것이 아니다.

Block Gas 사용량에 따라 일정한 공식으로 조절된다.

Block이 Target보다 많이 사용되면

```
Base Fee ↑

```

하고,

Target보다 적게 사용되면

```
Base Fee ↓

```

한다.

Target과 같으면

```
Base Fee 유지

```

된다.

현재 EIP-1559 구조에서는 최대 크기의 Block이 연속해서 생성되는 경우

Base Fee가 한 Block에서 다음 Block으로 최대 약 **12.5% 증가**할 수 있다.

반대로 빈 Block에서는 최대 약 12.5% 감소할 수 있다.

이처럼 변화 범위가 정해져 있기 때문에 Wallet에서도 향후 Base Fee를 어느 정도 예측하기 쉬워진다.

---

# 28. EIP-1559와 ETH Burn

EIP-1559에서 개인적으로 가장 흥미로웠던 부분 중 하나가 Base Fee Burn이었다.

기존에는 Transaction Fee가 주로 Block Producer의 수익과 연결됐다.

EIP-1559에서는

```
Base Fee
    ↓
Burn

Priority Fee
    ↓
Validator

```

로 분리된다.

따라서 Ethereum Network 사용량이 증가하면 Burn되는 ETH도 증가할 수 있다.

다만 여기서

```
EIP-1559 = ETH가 항상 Deflation

```

이라고 이해하면 안 된다.

ETH 공급량 변화에는 Burn뿐만 아니라 새로운 ETH의 발행량도 함께 영향을 준다.

따라서 특정 기간에

```
Burn > Issuance

```

라면 순공급이 감소할 수 있고,

```
Issuance > Burn

```

이라면 순공급이 증가할 수 있다.

---

# 29. The Merge 이후에도 EIP-1559는 유지된다

EIP-1559가 도입됐을 당시 Ethereum은 Proof of Work를 사용하고 있었다.

그래서 초기 EIP 문서를 보면 miner라는 표현이 많이 등장한다.

하지만 Ethereum은 이후 The Merge를 통해 Proof of Stake로 전환했다.

현재는 Block 생성 역할을 Validator가 담당한다.

그러나 EIP-1559의 핵심적인 Fee Burn 구조는 그대로 유지되고 있다.

즉 현재도

```
Base Fee
   ↓
Burn

Priority Fee
   ↓
Validator

```

구조로 이해할 수 있다.

---

# 30. 보안 관점 — Fee Manipulation

EIP-1559에서 Base Fee를 Burn하는 이유 중 하나는

Block Producer가 Base Fee 자체를 자신의 직접적인 수익으로 가져가지 못하게 하는 것이다.

만약 Base Fee가 그대로 Block Producer에게 지급된다면

Fee Market에 영향을 주어 자신의 수익을 증가시키려는 유인이 생길 수 있다.

하지만

```
Base Fee → Burn

```

구조에서는 Base Fee를 높이는 것이 Block Producer의 직접적인 Base Fee 수익 증가로 연결되지 않는다.

따라서 Fee Mechanism을 설계할 때 단순히

```
수수료를 얼마나 받을 것인가?

```

뿐만 아니라

```
누가 수수료를 받는가?

그 구조가 참여자의 행동에 어떤 경제적 인센티브를 만드는가?

```

도 중요하다는 것을 알 수 있었다.

---

# 31. 보안 관점 — Gas와 Smart Contract

Smart Contract 보안을 공부할 때도 Gas는 중요하다.

Contract가 불필요하게 많은 연산을 수행하면 사용자의 Gas 비용이 증가한다.

특히 반복문이나 Storage 접근 같은 연산을 많이 사용하면 비용이 커질 수 있다.

예를 들어

```
for (uint256 i = 0; i < users.length; i++) {
    // ...
}

```

와 같이 배열 크기에 따라 반복 횟수가 계속 증가하는 로직은 데이터가 많아지면서 실행 비용이 커질 수 있다.

극단적인 경우 필요한 Gas가 너무 커져 정상적인 기능 실행이 어려워지는 **Gas 관련 DoS 문제**로 이어질 수도 있다.

따라서 Smart Contract를 분석할 때는 기능이 정상적으로 동작하는지만 볼 것이 아니라

```
Gas 사용량이 입력에 따라 어떻게 증가하는가?

```

도 확인할 필요가 있다.

---

# 32. 기존 방식과 EIP-1559 비교

전체 구조를 비교하면 다음과 같다.

구분                                                          Legacy                                            EIP-1559

| 주요 Fee 값         | gasPrice     | Base Fee + Priority Fee |
| ---------------- | ------------ | ----------------------- |
| 기본 가격 결정         | 사용자 추정       | Protocol                |
| 사용자 최대 비용 설정     | gasPrice 자체  | maxFeePerGas            |
| 우선순위 Tip         | gasPrice에 포함 | maxPriorityFeePerGas    |
| Base Fee         | 없음           | 존재                      |
| Base Fee Burn    | 없음           | 있음                      |
| Transaction Type | Legacy       | Type 2                  |
| Fee 예측           | 상대적으로 어려움    | 개선                      |

구조적으로 보면

```
Legacy

User
 │
 │ gasPrice
 ▼
Block Producer

```

에서

```
EIP-1559

User
 │
 ├── Base Fee
 │       ↓
 │      Burn
 │
 └── Priority Fee
         ↓
      Validator

```

로 바뀐 것이다.

---

# 33. EIP-1559를 공부하면서 이해한 점

처음에는 EIP-1559를 단순히 Ethereum Gas Fee를 낮추기 위한 업데이트라고 생각했다.

하지만 실제로 공부해보니 핵심은 단순한 수수료 인하가 아니었다.

기존 Ethereum에서는 사용자가 적절한 gasPrice를 직접 추정해야 했다.

```
얼마를 내야 빨리 처리될까?

```

를 사용자가 계속 판단해야 했고,

네트워크가 혼잡해지면 사용자끼리 높은 Gas Price를 제시하는 경쟁이 발생할 수 있었다.

EIP-1559에서는 이를

```
Protocol이 결정하는 Base Fee

+

사용자가 정하는 Priority Fee

```

로 분리했다.

또한

```
Max Fee

```

를 이용하여 사용자가 자신이 지불할 수 있는 최대 가격을 제한할 수 있게 했다.

특히 Base Fee를 Validator에게 주는 것이 아니라 Burn한다는 점이 흥미로웠다.

처음에는 단순히 ETH 공급량을 줄이기 위한 기능이라고 생각했지만 EIP 문서를 살펴보면서

**Block Producer가 Base Fee를 직접 가져가지 않도록 하여**

**Fee Market을 조작할 경제적 유인을 줄이는 목적**도 있다는 것을 알 수 있었다.

결국 EIP-1559는 단순히 Gas Fee 계산식을 바꾼 것이 아니라

```
Transaction Fee를 어떻게 결정할 것인가?

Network 혼잡을 어떻게 반영할 것인가?

Block Producer에게 어떤 인센티브를 줄 것인가?

사용자가 Fee를 어떻게 예측할 수 있게 할 것인가?

```

를 함께 다룬 Ethereum의 Fee Market 설계라고 이해할 수 있었다.

---

# 34. 정리

EIP-1559의 핵심 내용을 정리하면 다음과 같다.

개념                                                             역할

| Gas                | Ethereum 연산량 단위              |
| ------------------ | ---------------------------- |
| Gas Limit          | Transaction이 사용할 수 있는 최대 Gas |
| Gas Used           | 실제 사용한 Gas                   |
| Base Fee           | Protocol이 결정하는 기본 Gas 가격     |
| Priority Fee       | Validator에게 지급하는 Tip         |
| Max Priority Fee   | 지불할 최대 Tip                   |
| Max Fee            | Gas 한 단위당 지불할 최대 가격          |
| Target Block Size  | Base Fee 조절 기준               |
| Burn               | Base Fee를 유통량에서 제거           |
| Type 2 Transaction | EIP-1559 Transaction 형식      |

전체 구조를 한 번에 표현하면 다음과 같다.

```
                    Network Demand
                          │
                          ▼
                     Block Usage
                          │
                          ▼
                      Base Fee
                          │
              ┌───────────┴───────────┐
              │                       │
        Transaction 포함          다음 Block
              │                  Base Fee 조절
              ▼
             User
              │
       ┌──────┴──────┐
       │             │
   Base Fee      Priority Fee
       │             │
       ▼             ▼
      Burn        Validator

```

실제 Transaction Fee는 기본적으로

```
Gas Used
    ×
Effective Gas Price

```

이고,

Effective Gas Price는 개념적으로

```
Base Fee
+
Priority Fee

```

로 구성된다.

결국 EIP-1559의 핵심은 **Ethereum의 Transaction Fee를 보다 예측 가능한 구조로**

**만들면서 네트워크 수요에 따라 Base Fee를 자동 조절하고,**

**Base Fee를 Burn하도록 Fee Market 자체를 재설계한 것**이라고 정리할 수 있다.

다음 글에서는 지금까지 살펴본 Token이나 Gas Fee보다 한 단계 더 확장해서

Ethereum의 Account 자체를 개선하려는 **ERC-4337 Account Abstraction**을 분석해보려고 한다.
