# ERC-721 분석, NFT는 스마트 컨트랙트에서 어떻게 소유권을 표현할까?

## 1. 들어가며

이전 글에서는 Ethereum의 대표적인 토큰 표준인 **ERC-20**을 살펴보았다.

ERC-20은 USDC와 같은 Fungible Token, 즉 서로 대체 가능한 토큰을 구현하기 위한 표준이다.

예를 들어 같은 종류의 ERC-20 토큰이라면

```
Token 1개 = 다른 Token 1개

```

처럼 각각의 토큰을 별도로 구분할 필요가 없다.

하지만 게임 아이템, 디지털 작품, 멤버십, 인증서처럼 각각의 자산을 개별적으로 구분해야 하는 경우에는 이야기가 달라진다.

예를 들어 게임에 두 개의 검이 있다고 생각해보자.

```
검 #100
- 공격력: 100
- 등급: Legendary

검 #101
- 공격력: 20
- 등급: Normal

```

둘 다 같은 종류의 아이템이지만 동일한 자산이라고 할 수 없다.

Ethereum에서 이러한 **고유한 자산을 표현하기 위해 만들어진 표준이 ERC-721**이다.

ERC-721은 흔히 NFT 표준으로 알려져 있다.

이번 글에서는 ERC-721이 왜 등장했는지부터 시작해서 ERC-20과의 차이점,

tokenId를 이용한 소유권 관리, NFT 전송 및 승인 구조, Metadata와 tokenURI(),

그리고 safeTransferFrom()이 필요한 이유까지 정리해보았다.

---

# 2. ERC-721이란?

ERC-721은 Ethereum에서 **Non-Fungible Token**을 구현하기 위한 표준이다.

Non-Fungible은 우리말로 보통 **대체 불가능**이라고 표현한다.

ERC-20에서는 동일한 토큰끼리 서로 같은 가치를 가진다.

```
ERC-20

Token A 1개 = Token A 1개

```

반면 ERC-721에서는 각각의 Token이 고유한 tokenId를 가진다.

```
ERC-721

NFT #100 ≠ NFT #101

```

같은 NFT Collection에 존재하더라도 서로 다른 tokenId를 가지고 있기 때문에 각각 별개의 자산으로 구분할 수 있다.

예를 들어 다음과 같은 형태다.

```
NFT Contract
│
├── Token #1
│     └── Owner : Alice
│
├── Token #2
│     └── Owner : Bob
│
└── Token #3
      └── Owner : Alice

```

ERC-721의 핵심은 결국 **각각의 고유한 Token ID와 그 Token의 소유자를 연결하는 것** 이라고 이해할 수 있다.

---

# 3. ERC-721은 왜 등장했을까?

ERC-20은 토큰을 표준화하는 데 매우 유용하지만 모든 종류의 자산을 ERC-20으로 표현할 수 있는 것은 아니다.

예를 들어 다음과 같은 자산이 있다고 생각해보자.

```
게임 캐릭터
게임 아이템
디지털 그림
부동산 권리
티켓
인증서
멤버십

```

이러한 자산은 각각의 특성이 다를 수 있다.

게임 아이템을 예로 들면

```
Sword #1
Attack : 100
Level  : 50

Sword #2
Attack : 30
Level  : 10

```

두 개 모두 Sword지만 서로 같은 아이템은 아니다.

ERC-20처럼 단순히

```
Alice = 2 Sword

```

라고 기록하면 Alice가 정확히 어떤 Sword를 가지고 있는지 알 수 없다.

따라서 다음처럼 개별 자산을 구분할 수 있어야 한다.

```
Sword #1 → Alice
Sword #2 → Bob
Sword #3 → Alice

```

ERC-721에서는 이를 tokenId를 이용해 해결한다.

---

# 4. ERC-20과 ERC-721의 차이

두 표준을 비교하면 ERC-721의 목적을 더 쉽게 이해할 수 있다.

구분ERC-20ERC-721

| 종류          | Fungible Token      | Non-Fungible Token |
| ----------- | ------------------- | ------------------ |
| 개별 Token 구분 | 필요 없음               | tokenId로 구분        |
| 소유권         | 수량 중심               | 개별 Token 중심        |
| 대표 사용       | 암호자산, Utility Token | NFT, 게임 아이템, 인증서   |
| 전송 기준       | amount              | tokenId            |
| 잔액          | Token 수량            | 보유 NFT 개수          |

ERC-20에서는

```
Alice → 100 Token

```

이라는 정보가 중요하다.

ERC-721에서는

```
Token #1 → Alice
Token #3 → Alice
Token #7 → Bob

```

처럼 **누가 어떤 tokenId를 가지고 있는가**가 중요하다.

---

# 5. ERC-721의 핵심 인터페이스

ERC-721에는 다음과 같은 주요 함수가 존재한다.

```
balanceOf(address owner)

ownerOf(uint256 tokenId)

safeTransferFrom(
    address from,
    address to,
    uint256 tokenId
)

transferFrom(
    address from,
    address to,
    uint256 tokenId
)

approve(
    address to,
    uint256 tokenId
)

getApproved(uint256 tokenId)

setApprovalForAll(
    address operator,
    bool approved
)

isApprovedForAll(
    address owner,
    address operator
)

```

ERC-20과 비슷해 보이는 함수도 있지만 동작 방식에는 차이가 있다.

---

# 6. balanceOf()

```
balanceOf(address owner)

```

특정 주소가 가지고 있는 NFT의 **개수**를 반환한다.

예를 들어 Alice가

```
NFT #1
NFT #3
NFT #8

```

을 가지고 있다면

```
balanceOf(Alice)

```

의 결과는

```
3

```

이 된다.

중요한 점은 balanceOf()만으로는 Alice가 정확히 어떤 NFT를 가지고 있는지는 알 수 없다는 것이다.

단순히 보유한 NFT의 개수만 반환한다.

---

# 7. ownerOf()

ERC-721에서 상당히 중요한 함수가 ownerOf()이다.

```
ownerOf(uint256 tokenId)

```

특정 tokenId의 소유자를 조회한다.

예를 들어

```
Token #100 → Alice

```

라는 상태가 있다면

```
ownerOf(100)

```

의 결과는 Alice의 주소가 된다.

ERC-721의 소유권 구조를 단순화하면 다음과 같이 생각할 수 있다.

```
tokenId
   │
   ▼
Owner

#1   → Alice
#2   → Bob
#3   → Alice
#4   → Charlie

```

이 구조 덕분에 각각의 NFT에 독립적인 소유권을 부여할 수 있다.

---

# 8. transferFrom()

NFT를 다른 사용자에게 전송할 때 사용할 수 있는 함수다.

```
transferFrom(
    address from,
    address to,
    uint256 tokenId
)

```

예를 들어 Alice가 소유한 NFT #100을 Bob에게 전송한다고 가정해보자.

```
Before

NFT #100
Owner → Alice

```

다음과 같은 전송이 이루어지면

```
transferFrom(
    Alice,
    Bob,
    100
);

```

소유권이 변경된다.

```
After

NFT #100
Owner → Bob

```

ERC-20에서는 amount가 중요했다면 ERC-721에서는 tokenId가 중요하다는 차이가 여기서 나타난다.

---

# 9. NFT에도 Approve가 필요한 이유

ERC-20을 공부할 때 approve()와 transferFrom() 구조를 살펴보았다.

ERC-721에도 비슷한 승인 구조가 존재한다.

왜 NFT에도 Approve가 필요한지 생각해보았다.

NFT Marketplace를 예로 들어보면 이해하기 쉽다.

사용자가 NFT를 판매하려면 Marketplace Contract가 사용자의 NFT를 구매자에게 전달할 수 있어야 한다.

하지만 아무 스마트 컨트랙트나 내 NFT를 마음대로 이동할 수 있게 만들면 안 된다.

따라서 사용자가 특정 주소에 NFT를 관리할 권한을 부여하는 과정이 필요하다.

---

# 10. approve()

특정 NFT 하나에 대해 다른 주소가 관리할 수 있도록 권한을 부여한다.

```
approve(
    address to,
    uint256 tokenId
)

```

예를 들어

```
NFT #100
Owner → Alice

```

상태에서 Alice가 Marketplace에 NFT #100의 관리 권한을 부여할 수 있다.

```
approve(Marketplace, 100);

```

구조는 다음과 같다.

```
Alice
  │
  │ approve
  ▼
Marketplace
  │
  │ NFT #100 관리 가능
  ▼
NFT #100

```

ERC-20에서는 일정 **수량**에 대해 승인했다면 ERC-721에서는 특정 **tokenId**에 대해 승인할 수 있다는 차이가 있다.

---

# 11. getApproved()

특정 NFT에 현재 어떤 주소가 승인되어 있는지 확인한다.

```
getApproved(uint256 tokenId)

```

예를 들어

```
getApproved(100)

```

의 결과가 Marketplace 주소라면 Marketplace가 NFT #100을 관리하도록 승인되어 있다는 의미다.

---

# 12. setApprovalForAll()

NFT에서는 하나의 NFT가 아니라 사용자가 가지고 있는 NFT 전체에 대해 특정 operator에게 관리 권한을 부여할 수도 있다.

```
setApprovalForAll(
    address operator,
    bool approved
)

```

예를 들어

```
setApprovalForAll(
    Marketplace,
    true
);

```

를 실행하면 Marketplace가 사용자의 NFT들을 관리할 수 있는 operator가 된다.

```
Alice

├── NFT #1
├── NFT #2
├── NFT #3
└── NFT #4
       │
       │ setApprovalForAll
       ▼
   Marketplace

```

이 기능은 편리하지만 보안 측면에서는 특히 주의해야 할 부분이기도 하다.

---

# 13. isApprovedForAll()

특정 operator가 사용자의 NFT 전체를 관리할 권한이 있는지 확인한다.

```
isApprovedForAll(
    address owner,
    address operator
)

```

예를 들어

```
isApprovedForAll(
    Alice,
    Marketplace
)

```

가 true라면 Marketplace는 Alice의 ERC-721 자산을 관리할 수 있는 operator다.

---

# 14. transferFrom과 safeTransferFrom의 차이

ERC-721을 공부하면서 가장 흥미로웠던 부분 중 하나다.

ERC-721에는 NFT를 전송하는 함수가 두 종류 존재한다.

```
transferFrom()

```

그리고

```
safeTransferFrom()

```

처음에는 굳이 왜 두 개가 필요한지 의문이 들었다.

문제는 NFT를 **Smart Contract 주소로 전송할 때** 발생할 수 있다.

EOA는 일반적인 사용자 지갑 주소이기 때문에 NFT를 소유할 수 있다.

하지만 Smart Contract는 다르다.

어떤 Contract가 ERC-721을 처리할 기능을 가지고 있지 않은데 NFT를 해당 Contract 주소로 보내버렸다고 생각해보자.

```
NFT
 │
 │ transferFrom()
 ▼
Smart Contract

ERC-721 처리 기능 없음

```

NFT가 Contract에 들어갔지만 이를 다시 꺼낼 수 있는 로직이 없다면 자산이 해당 Contract에 묶일 수 있다.

이 문제를 줄이기 위해 safeTransferFrom()이 존재한다.

---

# 15. safeTransferFrom()

```
safeTransferFrom(
    address from,
    address to,
    uint256 tokenId
)

```

safeTransferFrom()을 이용해 NFT를 Smart Contract로 보내면 수신 Contract가 ERC-721을 받을 수 있는지 확인한다.

핵심이 바로

```
onERC721Received()

```

이다.

구조를 단순화하면 다음과 같다.

```
Alice
 │
 │ safeTransferFrom()
 ▼
NFT Contract
 │
 │ NFT 받을 수 있어?
 ▼
Receiver Contract
 │
 │ onERC721Received()
 ▼
NFT Contract

```

Receiver Contract가 ERC-721을 정상적으로 받을 수 있음을 확인하면 전송이 진행된다.

그렇지 않으면 Transaction이 revert된다.

---

# 16. IERC721Receiver

ERC-721을 안전하게 수신하려는 Smart Contract는 다음 인터페이스를 구현할 수 있다.

```
interface IERC721Receiver {

    function onERC721Received(
        address operator,
        address from,
        uint256 tokenId,
        bytes calldata data
    )
        external
        returns (bytes4);
}

```

정상적으로 NFT를 받을 수 있는 Contract라면 정해진 selector를 반환한다.

예를 들면 다음과 같은 형태다.

```
function onERC721Received(
    address,
    address,
    uint256,
    bytes calldata
)
    external
    pure
    returns (bytes4)
{
    return IERC721Receiver
        .onERC721Received
        .selector;
}

```

이를 통해 NFT Contract는 수신 Contract가 ERC-721을 처리할 준비가 되어 있는지 확인할 수 있다.

---

# 17. ERC-721 Metadata

NFT라고 하면 흔히 이미지부터 떠올리지만 NFT 이미지 자체가 반드시 스마트 컨트랙트 안에 직접 저장되는 것은 아니다.

ERC-721에는 Metadata 관련 확장 인터페이스가 존재한다.

대표적으로

```
name()
symbol()
tokenURI(tokenId)

```

가 있다.

특히 중요한 것이

```
tokenURI(tokenId)

```

이다.

예를 들어

```
tokenURI(100)

```

을 호출했을 때 다음과 같은 URI가 반환될 수 있다.

```
ipfs://.../100.json

```

해당 Metadata에는 다음과 같은 정보가 포함될 수 있다.

```
{
  "name": "Sword #100",
  "description": "Legendary Sword",
  "image": "ipfs://...",
  "attributes": [
    {
      "trait_type": "Attack",
      "value": 100
    },
    {
      "trait_type": "Level",
      "value": 50
    }
  ]
}

```

구조를 정리하면 다음과 같다.

```
ERC-721 Contract
       │
       │ tokenURI(100)
       ▼
Metadata URI
       │
       ▼
JSON Metadata
       │
       ├── name
       ├── description
       ├── image
       └── attributes

```

따라서 NFT를 분석할 때는 **Token 자체의 소유권과 Metadata가 어디에 저장되는지를 구분해서 볼 필요가 있다.**

---

# 18. NFT 이미지는 블록체인에 저장되어 있을까?

처음 NFT를 접했을 때는 NFT 이미지 자체가 Ethereum 블록체인 안에 저장되어 있다고 생각하기 쉽다.

하지만 반드시 그런 것은 아니다.

구조는 프로젝트에 따라 다르지만 다음처럼 구성할 수 있다.

```
Ethereum
   │
   │ tokenId
   │ tokenURI
   ▼
Metadata
   │
   │ image URI
   ▼
Image

```

Metadata나 이미지가 IPFS 같은 분산 저장 시스템에 존재할 수도 있고

외부 서버에 존재할 수도 있으며, 프로젝트에 따라 데이터를 온체인에서 생성하거나 저장할 수도 있다.

따라서

```
NFT = 이미지

```

라고 이해하는 것은 정확하지 않다.

ERC-721 Token은 기본적으로 **고유한 tokenId와**

**그에 대한 소유권을 표현하는 Token**이고, 이미지 등의 정보는 Metadata를 통해 연결될 수 있다.

---

# 19. 직접 ERC-721 만들어보기

OpenZeppelin Contracts를 이용하면 기본적인 ERC-721 Contract를 간단하게 구현할 수 있다.

```
// SPDX-License-Identifier: MIT

pragma solidity ^0.8.20;

import {
    ERC721
} from "@openzeppelin/contracts/token/ERC721/ERC721.sol";

contract MyNFT is ERC721 {

    uint256 private nextTokenId;

    constructor()
        ERC721("MyNFT", "MNFT")
    {}

    function mint()
        external
    {
        uint256 tokenId = nextTokenId++;

        _safeMint(
            msg.sender,
            tokenId
        );
    }
}

```

생성자에서는 NFT Collection의 이름과 Symbol을 지정한다.

```
ERC721("MyNFT", "MNFT")

```

그리고

```
_safeMint(
    msg.sender,
    tokenId
);

```

를 통해 새로운 NFT를 발행한다.

예를 들어 Alice가 첫 번째 NFT를 Mint했다면

```
Token #0
Owner → Alice

```

와 같은 소유 관계가 만들어질 수 있다.

다음 사용자가 Mint하면

```
Token #1
Owner → Bob

```

처럼 새로운 tokenId가 생성된다.

# 20. Mint와 Transfer Event

ERC-721에서는 다음과 같은 주요 Event를 정의한다.

```
Transfer(
    address indexed from,
    address indexed to,
    uint256 indexed tokenId
)

Approval(
    address indexed owner,
    address indexed approved,
    uint256 indexed tokenId
)

ApprovalForAll(
    address indexed owner,
    address indexed operator,
    bool approved
)

```

NFT가 이동하면 Transfer Event가 발생한다.

```
Alice
  │
  │ NFT #100
  ▼
Bob

```

Mint 역시 Transfer Event를 이용해서 표현된다.

개념적으로

```
0x000...000
      │
      │ NFT #100
      ▼
    Alice

```

와 같은 형태가 된다.

반대로 Burn은

```
Alice
  │
  │ NFT #100
  ▼
0x000...000

```

처럼 표현할 수 있다.

이러한 Event를 통해 블록 탐색기나 NFT 관련 애플리케이션에서 Token의 이동을 추적할 수 있다.

---

# 21. NFT Marketplace에서의 ERC-721

ERC-721의 실제 활용을 이해하기 가장 쉬운 사례 중 하나가 NFT Marketplace다.

Alice가 NFT #100을 판매한다고 가정해보자.

먼저 Alice가 Marketplace에 NFT 관리 권한을 부여한다.

```
Alice
 │
 │ approve()
 ▼
Marketplace

```

또는 여러 NFT를 관리하도록

```
Alice
 │
 │ setApprovalForAll()
 ▼
Marketplace

```

를 사용할 수도 있다.

구매자가 NFT를 구매하면 Marketplace Contract는

승인된 권한을 이용해 NFT를 구매자에게 전달하는 구조를 사용할 수 있다.

```
Alice
 │
 │ NFT #100
 ▼
Marketplace
 │
 │ transfer
 ▼
Bob

```

실제 Marketplace의 구현은 이보다 훨씬 복잡하지만

ERC-721의 승인 및 전송 인터페이스가 이러한 NFT 거래 구조의 기반이 될 수 있다.

---

# 22. 보안 관점 — setApprovalForAll

ERC-721을 보안 관점에서 볼 때 특히 주의할 기능 중 하나가

```
setApprovalForAll()

```

이다.

예를 들어 사용자가 공격자의 Contract에 다음과 같은 권한을 부여했다고 생각해보자.

```
setApprovalForAll(
    attacker,
    true
);

```

이 경우 해당 operator는 사용자가 보유한 이 ERC-721 Collection의 NFT를 관리할 권한을 얻게 된다.

그래서 악성 사이트에서 NFT를 탈취하는 공격을 분석할 때 단순히

```
NFT를 전송했는가?

```

만 보는 것이 아니라

```
어떤 Approval을 허용했는가?

```

를 확인하는 것도 중요하다.

특히 서명하거나 Transaction을 실행할 때 setApprovalForAll() 같은 강한 권한을 부여하는 요청인지 확인할 필요가 있다.

---

# 23. 보안 관점 — Metadata

Metadata 역시 생각해볼 부분이 있다.

NFT의 tokenURI()가 외부 서버를 가리킨다고 가정해보자.

```
NFT Contract
      │
      ▼
https://example.com/metadata/100

```

NFT Contract 자체의 소유권 정보가 그대로 있다고 해도

외부 서버의 Metadata가 변경된다면 사용자에게 표시되는 NFT 정보가 달라질 가능성이 있다.

따라서 NFT를 분석할 때는

```
1. Token의 소유권은 어디에서 관리되는가?

2. Metadata는 어디에 저장되는가?

3. Metadata가 변경 가능한가?

4. Image는 어디에 저장되는가?

```

를 구분해서 확인하는 것이 중요하다고 생각한다.

---

# 24. 보안 관점 — safeTransferFrom도 무조건 안전한 것은 아니다

이름이 safeTransferFrom()이라서 모든 보안 문제를 해결해주는 함수처럼 보일 수도 있다.

하지만 여기서 Safe의 의미는 주로 **수신 Contract가 ERC-721을 받을 수 있는지 확인한다는 의미**로 이해해야 한다.

safeTransferFrom() 과정에서는 수신 Contract의

```
onERC721Received()

```

를 호출하게 된다.

즉 외부 Contract 호출이 발생한다.

따라서 NFT 전송을 포함하는 복잡한 Contract를 구현한다면 외부 호출과 상태 변경의 순서도 고려해야 한다.

특히 다른 상태 변경 로직과 결합되어 있다면 Reentrancy 가능성 등을 함께 검토해야 한다.

---

# 25. ERC-721을 공부하면서 이해한 점

처음에는 ERC-721을 단순히 NFT 이미지를 만드는 표준정도로 생각했다.

하지만 실제 ERC-721 인터페이스를 살펴보니 핵심은 이미지가 아니라

**고유한 디지털 자산의 소유권을 표현하고 전송하는 표준**에 가까웠다.

가장 중요한 개념은 tokenId였다.

ERC-20에서는

```
Alice → Token 100개

```

처럼 수량을 중심으로 관리한다.

반면 ERC-721에서는

```
Token #1 → Alice
Token #5 → Alice
Token #10 → Bob

```

처럼 개별 Token과 소유자의 관계를 관리한다.

또 하나 흥미로웠던 부분은 safeTransferFrom()이었다.

처음에는 transferFrom()과 거의 같은 함수라고 생각했지만 Smart Contract가 NFT를

받을 준비가 되어 있지 않은 경우 NFT가 Contract에 묶일 수 있다는 문제를 방지하기 위해

onERC721Received()를 확인한다는 것을 알게 되었다.

그리고 NFT에서 실제로 보이는 이미지와 Token 자체도 구분해서 볼 필요가 있다는 점을 알 수 있었다.

```
ERC-721 Token
     │
     ├── tokenId
     ├── Owner
     │
     └── tokenURI
            │
            ▼
         Metadata
            │
            ▼
          Image

```

결국 ERC-721은 단순한 이미지 표준이 아니라

**고유한 자산의 식별, 소유권, 전송 및 권한 위임을 위한 표준**이라고 이해할 수 있었다.

# 26. 정리

ERC-721의 주요 내용을 정리하면 다음과 같다.

항목                                                                    내용

| 목적                  | Non-Fungible Token 표준화     |
| ------------------- | -------------------------- |
| tokenId             | 각각의 NFT를 식별하는 값            |
| balanceOf()         | 사용자가 보유한 NFT 개수            |
| ownerOf()           | 특정 NFT의 소유자                |
| transferFrom()      | NFT 전송                     |
| safeTransferFrom()  | 수신 Contract 확인 후 안전하게 전송   |
| approve()           | 특정 NFT의 관리 권한 부여           |
| getApproved()       | 특정 NFT의 승인 주소 확인           |
| setApprovalForAll() | operator에게 전체 NFT 관리 권한 부여 |
| isApprovedForAll()  | operator 권한 확인             |
| tokenURI()          | NFT Metadata URI           |
| onERC721Received()  | Contract의 ERC-721 수신 확인    |

ERC-20과 비교하면 두 표준의 차이는 더 명확하다.

```
ERC-20
│
└── 얼마를 가지고 있는가?
        ↓
      amount


ERC-721
│
└── 어떤 Token을 가지고 있는가?
        ↓
     tokenId

```

ERC-721을 공부하면서 NFT에서 가장 중요한 것은 이미지 자체가 아니라

**블록체인 위에서 고유한 자산과 소유권을 어떻게 표현하고 관리하는가**라는 점을 이해할 수 있었다.

다음 글에서는 다시 ERC-20으로 돌아가 기존 approve() 방식의 문제를

개선하기 위해 등장한 **EIP-2612 Permit**을 분석해보려고 한다.
