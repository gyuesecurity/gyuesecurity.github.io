# CTF Agent - CTF 자율 풀이 및 Write-up 생성 AI 에이전트 개발

## 1. 프로젝트 소개

CTF를 풀다 보면 문제를 확인하고, 첨부파일을 내려받고, 소스코드를
분석하고, 필요한 도구를 실행하고, 플래그를 찾아 제출하는 과정을 반복하게
된다.

문제를 해결한 이후에도 Write-up을 작성하려면 사용했던 명령어나 요청,
실패했던 방법 등을 다시 정리해야 한다.

이 과정을 하나의 AI 에이전트가 처음부터 끝까지 자동으로 수행할 수 있으면
어떨까 하는 생각에서 **CTF Agent** 프로젝트를 시작했다.

CTF Agent의 최종 목표는 다음과 같다.

> **CTF 사이트 등록 → 문제 수집 → 문제 분석 → 도구 실행 → 취약점 검증 →
> 플래그 획득 및 제출 → Write-up 생성 → PDF 변환**

단순히 LLM에게 CTF 문제를 전달하고 풀이 방법을 물어보는 것이 아니라,
AI가 실제 파일과 서버 응답을 확인하고 필요한 도구를 선택하면서 문제를
해결하도록 만드는 것을 목표로 했다.

프로젝트는 **자동화가 허용된 CTF 및 개인 실습 환경에서 사용하는 것**을
전제로 개발했다.

## 2. 프로젝트 구성

사용한 주요 기술은 다음과 같다.

-   Python
-   FastAPI
-   SQLite
-   HTTPX
-   Playwright
-   Chromium
-   OpenAI Responses API
-   ChatGPT Plus OAuth
-   AST 기반 Python 코드 분석

처음에는 CTFd 사이트 로그인과 문제 수집, Web 취약점 분석, 플래그 제출
정도만 구현하려고 했다.

개발을 진행하면서 실제 사용에 필요한 기능을 하나씩 추가했고,
최종적으로는 다음 기능까지 연결했다.

-   CTFd 사이트 등록 및 로그인
-   대회 시작 시간에 맞춘 예약 실행
-   문제 목록 자동 수집
-   문제 설명 및 첨부파일 다운로드
-   문제 파일 직접 업로드
-   소스코드 정적 분석
-   AI 기반 문제 분석
-   HTTP 요청을 통한 검증
-   Chromium 브라우저 자동화
-   플래그 후보 탐지
-   플래그 자동 제출
-   작업 중지 및 재개
-   Markdown Write-up 생성
-   PDF Write-up 생성
-   개인 문체 기반 Write-up 후처리
-   Write-up 무결성 검증
-   ChatGPT Plus OAuth 연결

## 3. 전체 동작 흐름

``` text
CTF 사이트 등록
        ↓
CTFd 로그인
        ↓
문제 목록 수집
        ↓
문제 설명 / 첨부파일 / 접속 주소 수집
        ↓
파일 및 소스코드 분석
        ↓
취약점 후보 탐색
        ↓
AI Agent 분석
        ↓
필요한 도구 선택
        ↓
HTTP / Browser / Workspace 분석
        ↓
결과 확인
        ↓
실패 → 새로운 가설 생성 → 재시도
        ↓
플래그 후보 발견
        ↓
플래그 검증
        ↓
CTF 사이트 제출
        ↓
실행 기록 정리
        ↓
Markdown Write-up 생성
        ↓
PDF 생성
```

처음에는 단순한 자동 스캐너처럼 정해진 공격을 순서대로 실행하는 방법도
생각했다.

하지만 실제 CTF 문제는 하나의 Payload를 던진다고 해결되는 경우보다,
**이전 실행 결과를 보고 다음 행동을 결정해야 하는 경우**가 많았다.

그래서 최종적으로는 AI가 현재 상황을 확인하고 필요한 도구를 직접
선택하도록 구조를 변경했다.

## 4. CTF 사이트 등록 및 문제 자동 수집

기본적으로 CTFd 기반 사이트를 지원한다.

사용자는 대회 이름, 사이트 주소, 계정 정보, 대회 시작 시간, 플래그 형식,
요청 간격, 최대 요청 횟수, 제출 전 대기시간 등을 등록할 수 있다.

등록한 대회의 시작 시간이 되면 Scheduler가 자동으로 작업을 시작하며,
바로 실행하거나 작업 중간에 중지하는 것도 가능하게 만들었다.

CTFd 로그인 이후에는 문제 목록, 문제 설명, 카테고리, 접속 주소,
첨부파일을 자동으로 가져온다.

계정 정보는 암호화해서 저장하고, API 응답이나 AI에게 전달되는 분석
내용에는 포함되지 않도록 처리했다.

------------------------------------------------------------------------

## 5. 문제 파일 직접 분석

항상 CTF 사이트를 통해서만 문제를 분석하는 것은 불편했다. 이미
다운로드한 CTF 문제나 수업에서 받은 실습 파일을 분석하고 싶은 경우도
있기 때문이다.

그래서 두 가지 실행 방식을 지원하도록 변경했다.

-   **사이트 모드**: CTF 사이트 로그인부터 플래그 제출까지 수행
-   **파일 모드**: 소스코드 또는 ZIP을 직접 업로드하여 분석

ZIP 파일은 바로 압축 해제하지 않고 Zip Slip, Symbolic Link, 파일 개수,
압축 해제 크기 등을 검사한다.

또한 파일 분석 단계마다 체크포인트를 저장해 프로그램이 종료되거나 작업이
중단되더라도 이어서 실행할 수 있도록 했다.

------------------------------------------------------------------------

## 6. 소스코드 정적 분석

AI에게 처음부터 모든 파일을 전달하지 않고 프로그램에서 먼저 정적 분석을
수행한다.

Python 프로젝트는 AST를 이용하여 Route, Function Call, 사용자 입력, 위험
함수, Framework 등을 확인한다. JavaScript와 PHP 등은 문자열 패턴 분석도
함께 사용한다.

위험 함수나 사용자 입력 처리 부분이 발견되면 해당 위치를 취약점 후보로
기록한다.

또한 Base64, Hex, Single Byte XOR, Integer Array처럼 범위를 정할 수 있는
간단한 인코딩은 자동으로 해석하고 결과가 플래그 형식과 일치하는지
확인한다.

------------------------------------------------------------------------

## 7. AI Agent 기반 자동 풀이

이 프로젝트에서 가장 중요하게 생각한 부분이다.

파일 전체를 AI에게 무조건 전달하는 대신 **Workspace Tool**을 제공했다.
AI는 파일 목록을 먼저 확인하고 필요한 파일과 코드 구간을 직접 선택한다.

실제 서버 검증이 필요하면 HTTP 또는 Browser Tool을 선택할 수 있다.

현재 주요 도구는 다음과 같다.

-   `workspace_inspect`
-   `http_workflow`
-   `browser_action`
-   `docker_sandbox`

AI는 취약점 가설을 만든 뒤 도구를 통해 검증하고, 결과가 예상과 다르면
해당 결과를 다시 분석하여 새로운 가설을 생성한다.

``` text
가설 생성
   ↓
도구 실행
   ↓
결과 분석
   ↓
실패
   ↓
새로운 가설 생성
   ↓
재시도
```

같은 행동을 무한히 반복하지 않도록 최대 Agent Step과 동일 Tool 호출
횟수에도 제한을 적용했다.

------------------------------------------------------------------------

## 8. 플래그 탐지 및 자동 제출

정규식에 맞는 문자열을 발견했다고 바로 정답으로 처리하지 않는다.

소스코드나 테스트 파일에는 미끼 플래그가 포함될 수 있기 때문이다.

플래그 후보가 발견되면 플래그 값뿐 아니라 발견한 파일 또는 서버 응답,
위치, 주변 내용, 정규식 일치 여부를 함께 저장한다.

또한 이미 제출한 플래그인지 확인하여 중복 제출을 방지한다.

자동 제출 결과는 다음과 같이 구분하여 기록한다.

-   Correct
-   Incorrect
-   Already Solved
-   Submission Error

## 9. Write-up 자동 생성

플래그를 찾는 것으로 프로젝트를 끝내지 않고 Agent가 문제를 해결하는 동안
주요 행동을 기록하도록 했다.

기록하는 내용은 다음과 같다.

-   확인한 파일
-   분석한 코드
-   취약점 가설
-   실행한 요청
-   서버 응답
-   실패한 접근
-   성공한 접근
-   발견한 플래그
-   플래그 제출 결과

이 기록을 기반으로 Markdown Write-up을 자동 생성한다.

중요하게 생각한 부분은 **AI가 실제로 수행하지 않은 명령이나 결과를
Write-up에 임의로 만들어 넣지 않는 것**이었다.

성공 과정뿐 아니라 어떤 가설을 세웠고, 무엇을 시도했으며, 왜 실패했고,
그 결과를 바탕으로 무엇을 변경했는지까지 기록하도록 했다.

------------------------------------------------------------------------

## 10. 개인화된 Write-up

AI로 기술문서를 생성하면 비슷한 문장 구조와 표현이 반복되는 경우가
많았다.

그래서 `style_samples` 폴더에 사용자가 기존에 작성한 글을 넣으면 제목
구성과 문장 종결 방식 등을 일부 참고하도록 했다.

현재는 완전히 개인의 문체를 복제하는 수준은 아니며, 반복적인 표현 감소,
제목 구성 참고, 문장 종결 방식 참고, 기술 설명 방식 조정 정도의 후처리를
수행한다.

자동 생성된 문서는 그대로 제출하기보다는 마지막에 사용자가 직접 읽고
수정하는 것을 전제로 만들었다.

------------------------------------------------------------------------

## 11. Markdown → PDF 자동 생성

생성한 Write-up은 Markdown뿐만 아니라 PDF 형태로도 저장할 수 있도록
했다.

``` text
Problem
├── Analysis Log
├── Flag
├── Write-up.md
└── Write-up.pdf
```

문제를 해결한 이후 Write-up을 별도로 처음부터 작성하지 않아도 Agent의
실제 실행 기록을 기반으로 문서까지 생성되는 구조다.

------------------------------------------------------------------------

## 12. Write-up 무결성 검증과 ECC

Write-up 자동 생성 기능을 구현하면서 이후 문서가 수정되거나 데이터
일부가 손상됐을 때 이를 확인하는 기능도 추가했다.

자연어 자체에 LLM Watermarking을 적용하는 것은 프로젝트 기간 내 충분한
검증이 어렵다고 판단해, 우선 문서 무결성과 손상 복구 방향으로 구현했다.

사용한 기술은 다음과 같다.

-   SHA-256
-   Merkle Root
-   Ed25519
-   Reed-Solomon ECC

각 문단에 SHA-256 해시를 생성하고 이를 기반으로 Merkle Root를 만든다.
Ed25519 전자서명을 추가하여 문서의 변경 여부를 검증한다.

Reed-Solomon ECC는 문서 자체를 인증하는 용도가 아니라 manifest 일부가
손상됐을 때 복구 가능성을 높이기 위한 보조 수단으로 사용했다.

## 13. ChatGPT Plus 연결

초기 버전에서는 OpenAI API Key를 이용했지만, 이후 ChatGPT Plus OAuth
연결 기능도 추가했다.

로그인은 OpenAI 화면에서 직접 진행하므로 CTF Agent가 사용자의 OpenAI
비밀번호를 받지 않는다.

OAuth 과정에서는 `state`, `nonce`, `PKCE`를 사용하고, 반환된 ID Token의
Signature, Issuer, Audience, Expiration을 검증한다.

Access Token과 Refresh Token은 암호화하여 저장하도록 했다.

-   `verifier.py`: 플래그 후보 검증

## 15. 실행 범위 제한

CTF Agent는 **자동화가 허용된 CTF 및 개인 실습 환경에서만 사용하는
것**을 전제로 한다.

등록한 문제 범위를 벗어나지 않도록 매 요청마다 URL의 Host를 검사한다.

적용한 제한은 다음과 같다.

### 네트워크

-   등록한 CTF 및 문제 Host만 허용
-   Link-local 주소 차단
-   Cloud Metadata 주소 차단
-   허용되지 않은 Redirect 차단
-   Private/Local 주소는 로컬 테스트 모드에서만 허용

### 요청

-   요청 간격 제한
-   최대 요청 횟수 제한
-   최대 AI Step 제한
-   동일 Tool 반복 제한

### 파일

-   업로드 파일 개수 및 용량 제한
-   압축 해제 크기 제한
-   Zip Slip 차단
-   Symbolic Link 차단

비밀번호, Authorization Header, Cookie, Session, CSRF Token 등의 인증
정보는 Activity Log에 기록하기 전에 마스킹하도록 했다.

## 16. 개발하면서 발생한 문제

### 16.1 Segmentation Fault

Windows 바탕화면에 프로젝트를 두고 WSL에서 `run.sh`를 실행했을 때
`pip install` 과정에서 Segmentation Fault가 발생했다.

Windows Drive에 Linux Virtual Environment를 생성한 것이 원인일 가능성이
높다고 판단하여 소스는 Windows에 두고 가상환경만 WSL 내부의
`~/.local/share/ctf-agent/venvs`에 생성하도록 변경했다.

수정 이후 패키지 검사와 전체 테스트가 정상적으로 실행됐다.

### 16.2 AI 요청은 성공했는데 결과가 비어 있던 문제

ChatGPT Plus 연결 이후 상태는 `completed`였지만 결과 문자열이 비어 있는
문제가 있었다.

Stream Event를 확인한 결과 최종 `response.completed`에는 출력이 없고
이전 `response.output_item.done`에 결과가 존재했다.

완료된 Output Item을 별도로 저장한 뒤 최종 응답에 합치는 방식으로
수정했다.

### 16.3 플래그 오탐

정규식과 일치한다고 해서 모든 문자열이 실제 플래그인 것은 아니었다.

테스트 코드나 설명에 포함된 미끼 플래그가 후보로 탐지될 수 있어, 플래그
후보와 함께 발견 위치, 주변 Context, 출처, 서버 제출 결과를 저장하도록
했다.

------------------------------------------------------------------------

## 17. 테스트 결과

현재까지 총 **54개의 자동 테스트를 통과**했다.

테스트 범위에는 API, 파일 분석, Agent Tool, 보안 제한, Checkpoint /
Resume, 문서 검증 등이 포함된다.

정적 분석 기능 검증을 위해 다음과 같은 합성 문제 8개를 사용했다.

-   Plain Flag
-   No Flag
-   Decoy Flag
-   Web Vulnerable Code
-   Base64
-   XOR
-   Integer Array
-   Encoded Log

결과는 **7/8 정확 일치(87.5%)**였으며, 실패한 하나는 미끼 플래그를 실제
후보로 탐지한 경우였다.

여기서 87.5%는 실제 CTF 자동 풀이 성공률이 아니라 정적 분석 코드가 합성
데이터에서 얼마나 정확하게 동작하는지 확인하기 위한 기준선이다.

ECC 실험에서는 설정 범위 내에서 1, 4, 8, 12바이트 손상을 각각 20회 모두
복구했으며, 보정 범위를 넘은 13바이트와 20바이트 손상은 복구되지 않았다.

------------------------------------------------------------------------

## 18. 현재 한계

아직 모든 Web CTF 문제를 자동으로 해결하는 Agent는 아니다.

현재는 **CTF 입력 → 분석 → Agent Tool 실행 → 플래그 처리 → Write-up
생성**이라는 전체 파이프라인을 구현하고 기능별 동작을 검증한 단계에
가깝다.

실제 공개 CTF 문제를 대상으로 충분한 반복 평가를 진행하지 못했기 때문에
실제 문제 해결률, 문제당 평균 해결 시간, 평균 HTTP 요청 수, 평균 Agent
Step, 취약점 유형별 성공률 등은 추가 측정이 필요하다.

또한 현재 사이트 연동은 기본적으로 CTFd 구조를 기준으로 하고 있어 다른
플랫폼은 별도의 Adapter가 필요하다.

------------------------------------------------------------------------

## 19. 향후 개선 방향

앞으로 실제 공개 Web CTF 문제를 난이도와 유형별로 모아 Benchmark를 만들
계획이다.

예를 들어 SQL Injection, Authentication Bypass, SSTI, File Upload, Path
Traversal, SSRF, JWT, Session, XXE 등의 유형으로 문제를 분류하고 Agent가
어느 유형에서 성공하거나 실패하는지 측정할 수 있다.

성공률뿐 아니라 어떤 가설을 잘못 세웠는지, 어떤 도구 선택이 잘못됐는지,
몇 번째 Step에서 막혔는지, 같은 행동을 반복했는지 등을 기록해 Agent의
판단 과정과 Tool을 개선할 계획이다.

Write-up 개인화 기능 역시 기존에 작성한 기술 블로그와 Write-up 데이터를
더 활용하여 반복되는 표현을 줄이고 개인 작성 스타일에 가까운 문서를
만드는 방향으로 개선할 예정이다.

------------------------------------------------------------------------

## 20. 프로젝트를 진행하면서 느낀 점

처음에는 LLM 하나를 연결하면 생각보다 쉽게 CTF 자동 풀이 Agent를 만들 수
있을 것이라고 생각했다.

실제로 만들어 보니 가장 어려운 부분은 모델 자체보다 **모델이 실제 환경과
어떻게 상호작용하도록 만들 것인가**였다.

AI가 분석을 잘하더라도 파일을 직접 확인할 수 없으면 소용이 없었고,
서버에 요청을 보내지 못하면 자신의 가설을 검증할 수도 없었다.

반대로 도구를 무제한으로 제공하면 같은 요청을 반복하거나 불필요한 행동을
계속 수행하는 문제도 있었다.

결국 자동 풀이 Agent에는 다음 요소가 모두 필요하다고 느꼈다.

``` text
LLM
+
Tool
+
State
+
Evidence
+
Execution Limit
```

또 하나 중요했던 것은 **결과의 출처를 기록하는 것**이었다.

플래그 하나를 발견하는 것보다 어디에서 발견했고, 어떤 요청으로 얻었으며,
그 전에 어떤 실패를 했는지를 기록해야 이후 Write-up 생성과 결과 검증에도
사용할 수 있었다.

아직 실제 CTF에서 모든 문제를 자율적으로 해결할 수 있는 수준은 아니다.

그래도 이번 프로젝트를 통해 CTF 사이트 또는 문제 파일 입력부터 정적
분석, AI Agent의 도구 실행, 플래그 처리, Write-up 및 PDF 생성까지 하나의
흐름으로 연결해볼 수 있었다.

앞으로 실제 문제를 지속적으로 테스트하면서 실패 데이터를 쌓고 Agent의
판단 과정과 Tool을 개선해 나갈 생각이다.
